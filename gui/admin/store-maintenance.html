Store maintenance

You don't have permission to manage backups.

Download a backup

Downloads a JSON file of the selected stores. Account password hashes and sign-in sessions are never included, so restored users must be given a new password. Link passwords are included (hashed) so that restoring keeps protected links protected — treat the file as sensitive and store it somewhere access-controlled.

Include

Restore from a backup

Restoring replaces the links, users and analytics stores covered by the file. This can't be undone, and it signs everyone out — including you.

Check store consistency

Reads the links and users stores and reports anything out of step — a link owned by an account that no longer exists, a user missing from the username index, a session for a deleted account. The check itself only reads. Where a finding has exactly one safe fix, a Repair button appears with it — nothing is changed until you click it. Findings without a button need a judgement call; each one says what to do instead. Most useful straight after a restore. If a finding appears while people are actively creating links, run it again — a report taken during a write can show a finding that isn't real, and a real one shows up on both runs — and prefer a quiet moment for repairs, which share the same write budget as click recording.

Clean up analytics for deleted links

Deleting a link doesn't delete its click data. That data can never be read again — the link is gone — but every key in the store is scanned on every dashboard load, so it makes the app slower for everyone, forever.

Deleting it can't be undone, and restoring an older backup brings it back. Run this when traffic is low: it shares the same write budget as click recording.
