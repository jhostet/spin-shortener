#### Design Specificity Verdict

**LLM assessment**: Reads as an authored system, not generic admin CRUD, but the authorship shows up in engineering details (sticky columns, mono data typography, the slug chip, de-emphasized destructive actions) more than in product voice. The slug-chip-as-pill is a genuine signature — identical treatment as a table cell and as the detail page's `h1` — and the monospace convention is consistent and legible. But there's no moment that says "this is Tire Rack's marketing-ops tool" specifically: no campaign-flavored empty states, no acknowledgment that these links represent live promotions (Black Friday, VIP previews, summer sales). Competent and disciplined, not distinctive in voice.

**Deterministic scan**: `detect.mjs --json gui/` returned exactly 2 findings, both the same pre-confirmed false positives from every prior pass (`broken-image` on `#qr-preview` — verified live, `naturalWidth/Height: 222×222`, loads a real QR PNG at runtime; `layout-transition` in vendored `pico.min.css`). Zero new static findings. However, live browser measurement caught four things the static scan structurally cannot: (1) every `<article>` card resolves a real 7-layer `box-shadow` via `getComputedStyle` — confirmed via source that `theme.css` has never once set `--pico-card-box-shadow` in any commit since the theme's introduction (`e93ac50`), so Pico's stock shadow has rendered on every card, on every page, this entire time; (2) the links table overflows its container by 21px at 1400px with only 4 rows (`table.scrollWidth: 1197` vs `figure.clientWidth: 1176`); (3) at 390px, the sticky action column shipped this session (correctly reachable, as designed) also visually occludes other columns' content at rest — on the dashboard, the sticky column's opaque background fully covers the Owner column (73.6px overlap, confirmed via `getBoundingClientRect`); on admin/users.html it covers most of Permissions and part of Status; (4) the status-active badge measures 4.39:1 contrast against its actual table-cell background (`rgb(238,241,246)`, not the white card background assumed by earlier passes) — just under the 4.5:1 AA minimum for 16px/600-weight text. Zero console errors or warnings were produced by any page load or interaction (create, edit-toggle, cancel, delete-with-confirm) — only a benign, informational `autocomplete`-attribute advisory from Chrome DevTools, confirmed to apply to every input site-wide via direct DOM query.

#### Overall Impression

The single most important finding this pass is that the system's own explicitly-named "No-Shadow Rule" has been violated on every card, on every page, since the theme's very first commit — seven prior critique/audit passes missed it because Pico's default shadow is subtle at a glance, and `theme.css` overrides every other card property (`background-color`, `border-color`, `sectioning-background-color`) except the one that actually governs elevation. It's the same shape of miss as the earlier `:root` specificity bug: a written rule that was never actually mechanically verified against the literal computed style. The rest of the pass is dominated by a related theme — density. With only 4 seeded links, the table already overflows at a realistic desktop width and visibly clips a column header; on mobile, the very fix that made row actions reachable (sticky column) now visually occludes other columns' data at rest rather than just requiring a scroll. None of this is a regression in what was just shipped — the sticky column does exactly what it was built to do (keep actions reachable) — but the interaction between "sticky occluding column" and "already-too-many-columns" is worth addressing together rather than patching the symptom again.

#### What's Working

1. **The confirm-dialog pattern (delete, admin-promotion) is genuinely well-designed, not just present.** `aria-labelledby` correctly announces the actual message (verified in the accessibility tree, not just "dialog"); copy states the concrete consequence ("Admins bypass every permission check") instead of a generic "Are you sure?"; the safe choice is consistently the visually bold one. This is the strongest, most consistently-applied piece of emotional design in the app.
2. **The slug chip is a real signature element**, identical treatment as a table cell and as the detail page's `h1` — a small continuity that makes disparate pages read as one product.
3. **Partial-failure error handling is unusually careful.** When a link's destination/schedule saves but a subsequent password change fails, the copy explicitly says so ("Destination and schedule saved. Could not update link password.") instead of leaving the user guessing — most CRUD UIs get this edge case wrong.

#### Priority Issues

**[P1] Every `<article>` card on every page renders Pico's default drop shadow, silently violating DESIGN.md's own "No-Shadow Rule."** Confirmed via `getComputedStyle` on login, dashboard (both widths), link-detail, and admin/users: every card resolves a real multi-layer `box-shadow` (`rgba(129,145,181,...)` at several blur radii), not `none`. Root cause confirmed in source: `theme.css` overrides `--pico-card-background-color`/`-border-color`/`-sectioning-background-color` but has never set `--pico-card-box-shadow`, in any commit since the theme's introduction. This is a named, explicit rule in the design system ("nothing casts a shadow... depth comes from border + background contrast only") broken everywhere, invisibly, the whole time — subtle enough at a glance that it survived seven prior passes. Fix: add `--pico-card-box-shadow: none;` inside `theme.css`'s existing `:root:not([data-theme="dark"])` block; also audit `--pico-modal-*` and any other shadow-bearing variable for the same gap. → `/impeccable harden`

**[P1] The links table overflows its own container even at a realistic desktop width with a realistic dataset.** At 1400px with only 4 seeded links, `table.scrollWidth` (1197px) exceeds `figure.clientWidth` (1176px) by 21px, clipping the "Expires" column header to "Expire" and forcing a scrollbar that shouldn't be necessary at this data volume. Root cause is column bloat: full-precision timestamps ("Jul 24, 2026, 7:46 PM"), the full `http://host/r/slug` text repeated per row, and 7 sortable columns competing for space. Fix: shorten the Created/Starts/Expires display format, or drop the origin+`/r/` prefix from the table's slug chip (useful once copied, not before), or both. Re-measure with real seeded data, not an empty table. → `/impeccable layout` or `/impeccable distill`

**[P1] At 390px, the sticky action column occludes other columns' content at rest, on both data tables.** This session's sticky-column fix does what it was designed to do — Delete/Edit stay reachable — but on a viewport narrow enough that overflow exceeds the sticky column's own width, the sticky element's opaque background paints directly over other cells rather than simply requiring a scroll to reach them. Confirmed pixel-precise: on `dashboard.html`, the sticky column (`left: 142.6, right: 351`) fully covers the Owner column (`left: 277.6, right: 351.6` — 73.6px complete overlap); on `admin/users.html`, it covers 58px of Permissions and 39px of Status, leaving only 35px of Status visible. Given the product brief names marketers "sometimes on mobile" checking link status as a core scenario, and Status/Expires are exactly the fields answering "is this still live," having them occluded (not merely requiring a scroll) at the default resting state is a real gap, not just a visual quirk — this table has too many columns to serve mobile well even with the reachability fix in place. Fix: on narrow viewports, either collapse to a card/list layout (label:value stacked per link) or reduce to 2-3 priority columns (Status, Expires) alongside Short link, deferring the rest to the detail page. → `/impeccable adapt` or `/impeccable layout`

**[P2] Clicking Edit on a row near or below the fold gives no scroll-into-view, so the interaction visually does nothing.** Verified live on both tables: opening the edit form for a lower row (e.g. the last user in a 3-row table) expands the form entirely off-screen with zero visible change until the user manually scrolls. The app already has the right pattern for this — `links/detail.html`'s cross-page deep-linked Edit uses `scrollIntoView({ block: "center" })` — it just isn't applied to the ordinary in-page Edit click on either table. Fix: call the same `scrollIntoView` inside `handleEditToggleClick` (dashboard.html) and the `.edit-btn` handler (admin/users.html) when opening (not closing) a row. → `/impeccable polish`

**[P2] Deleting a link leaves a stale "Link created" success banner referencing the now-deleted slug, with a live Copy button pointing at a dead link.** Reproduced live: create a link (success banner appears with slug chip + Copy), then delete that same link — the banner and its Copy button remain visible and functional, silently handing out a link that no longer resolves. Fix: clear/hide `#create-success` on any successful delete, or scope its lifetime to the session that created it. → `/impeccable harden`

#### Minor Observations

- Every `<input>` site-wide (login, create/edit forms on both tables) lacks an `autocomplete` attribute — confirmed via direct DOM query, not just Chrome's advisory; minor, mostly affects browser autofill/password-manager integration.
- The create-user form's two-column grid (Role / Permissions) leaves visible empty space under the shorter Role column once Permissions' 4 checkboxes make the right column taller.
- On mobile, the Users table's Permissions column word-wraps a comma-joined list across 3+ lines inside a narrow cell — correct but not glanceable.
- The "Owner" column reads "admin" on every row in a single-admin viewing session — zero-information repetition in this context, presumably more useful once multiple owners' links are visible together.
- Recent-events timestamps lack seconds precision, so near-simultaneous clicks display identically — consistent with the documented WASI clock-resolution limitation, not a GUI defect.

#### Questions to Consider

1. Two of this session's seven prior passes missed rule violations only caught by directly reading `getComputedStyle` against the literal CSS custom property (the earlier `:root` specificity bug, now this box-shadow gap) — should every future pass include a mechanical `getComputedStyle` sweep of each DESIGN.md-named rule's actual computed values, not just a visual skim?
2. The links table is the app's busiest surface and the one place density keeps causing problems — overflow at desktop scale, occlusion at mobile scale. Is a single table layout the right pattern at every width, or would a card-per-link layout on mobile (with the table reserved for desktop) serve the "quick campaign-link check on the go" scenario better than continuing to patch one table to work everywhere?
3. The sticky-column technique trades "unreachable" for "occluding" on narrow enough viewports — is that trade worth it given this table's current column count, or does it only become the right trade once the table itself sheds columns on mobile?
