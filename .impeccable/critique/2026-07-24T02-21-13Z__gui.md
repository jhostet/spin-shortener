## Overall Impression

Real, measurable progress: 20/40 → 26/40. The three targeted fixes landed cleanly and integrated into the existing design system rather than fighting it — this is exactly what a good fix pass should look like. But the re-critique surfaced something the first pass couldn't have caught: applying `friendlyError()` to three named handlers left an identical bug sitting one page over, in `admin/users.html`'s create-user flow, which was never touched. The lesson isn't that the fix was wrong — it's that "raw error codes leak" was treated as three call sites instead of one systemic pattern. The two features most central to what this product promises marketing users (self-serve URL/password edits, and a legible view of scheduling/custom-slug state) remain the biggest open gap.

## Priority Issues

**[P1] Admin "Create a user" error handling bypasses `friendlyError()`/`ERROR_MESSAGES` — a gap the fix pass's own pattern should have caught**
- **Why it matters**: `admin/users.html:234` still reads `errorEl.textContent = (data && data.error) || "Could not create user"` while every sibling handler (link create/edit/delete, user edit/delete) now routes through `friendlyError()`. A duplicate username — routine for a small admin population — will surface the raw string `username_taken` verbatim, the exact class of bug this pass targeted.
- **Fix**: Route this handler through `friendlyError()`; add `username_taken`/`invalid_username`/`invalid_role` to `ERROR_MESSAGES`.
- **Suggested command**: `/impeccable harden`

**[P1] Still no self-serve way to edit a link's destination URL or password, despite full backend support**
- **Why it matters**: `api/links.py`'s `handle_update` already accepts `target_url`, and a password-set endpoint already exists — but neither `dashboard.html`'s edit row nor `links/detail.html` exposes either field. Directly undermines PRODUCT.md's own principle that routine link operations shouldn't need engineering.
- **Fix**: Extend the edit-row pattern (or `links/detail.html`'s Details card) with `target_url` and a password set/clear control.
- **Suggested command**: `/impeccable layout`

**[P2] No visual cue for expiring links, custom-vs-auto slugs, or password-protection, plus raw unformatted timestamps**
- **Why it matters**: `link.custom` and `link.password_protected` are both in the API response but never rendered; `Starts`/`Expires`/`Created` show raw ISO8601 UTC with no relative formatting or "expiring soon" state — a real gap for a marketing persona whose top concern is scheduled campaigns.
- **Fix**: Add a custom-slug badge, a password-lock indicator, and relative/locale-formatted dates with an expiry-proximity warning state.
- **Suggested command**: `/impeccable clarify`

**[P2] Delete-confirmation copy is inconsistent between the two destructive flows the fix pass touched**
- **Why it matters**: Link delete warns "This can't be undone"; user delete only asks "Delete user \"x\"?" with no equivalent warning — despite being at least as consequential. Inconsistent risk signaling for two structurally identical actions.
- **Fix**: Standardize confirm-dialog copy across both flows.
- **Suggested command**: `/impeccable polish`

**[P3] No `aria-live` on `.form-error`/`.form-success`**
- **Why it matters**: Dynamic state changes are silent for screen-reader users — no `role="alert"`/`aria-live` anywhere in the codebase.
- **Fix**: Add `aria-live="polite"` (or `role="alert"` for errors) to both classes.
- **Suggested command**: `/impeccable harden`
