## Priority Issues

**[P1] Copying a link's URL from the dashboard table fires a real redirect and inflates its own click analytics**
- **Why it matters**: The only way to grab an existing link's URL from the table is the slug-chip anchor itself, which navigates through `/r/{slug}` and increments the real click count. Every time a campaign manager opens the dashboard to sanity-check or share their own link, they silently corrupt the number they'll later report to stakeholders — directly undermining the product's own click-analytics value proposition.
- **Fix**: Give existing rows the same dedicated Copy affordance the creation success banner already has; keep the chip itself non-navigating or move real navigation to an explicit secondary action.
- **Suggested command**: `/impeccable clarify`

**[P1] Primary-button text fails WCAG AA contrast — the same failure just fixed on the badge, unfixed at the root**
- **Why it matters**: White text on Signal Blue measures ~4.16:1, below the 4.5:1 AA minimum — the identical color pair flagged and fixed for the badge last pass. The badge got patched; the underlying token never did, so it persists on every primary button (Log in, Shorten, Create user, Save) across all four pages.
- **Fix**: Darken the button fill for text contexts, or deliberately size/weight the label into the "large text" 3:1 AA tier.
- **Suggested command**: `/impeccable audit`

**[P2] Scheduled (not-yet-started) links look identical to live links**
- **Why it matters**: The expiry treatment only covers `end_at`; a link with a future `start_at` shows a plain date with no "not live yet" cue and still reads "active" — exactly the kind of scheduling visibility PRODUCT.md says the marketing persona cares most about.
- **Fix**: Mirror the `end_at` treatment for `start_at` when it's in the future.
- **Suggested command**: `/impeccable clarify`

**[P2] Partial-save success message isn't reflected in the visible row**
- **Why it matters**: The "Destination and schedule saved." message is correct, but `loadLinks()` is never called on that path, so the table row still shows pre-edit data — the message and the screen now disagree.
- **Fix**: Call `loadLinks()` (or re-render the row) before returning on the partial-failure branch.
- **Suggested command**: `/impeccable polish`

**[P3] `role="button"` + `aria-sort` on the same `<th>` is an ARIA misuse**
- **Why it matters**: `role="button"` overrides the cell's implicit `columnheader` role that `aria-sort` depends on — the mouse/sighted-keyboard fix works, but a screen-reader user may lose column-header context on exactly these 7 cells.
- **Fix**: Drop `role="button"`; a `<th tabindex="0">` is already focusable without it, and `aria-sort` stays valid on the default `columnheader` role.
- **Suggested command**: `/impeccable harden`
