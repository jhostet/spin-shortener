#### Design Specificity Verdict

**LLM assessment**: This is not a generic unthemed Pico panel. The dark-navy chrome, the pill-shaped monospace slug chip (reused as the literal `h1` on the detail page), and the "Signal Room" restraint (one accent color, used only on hover/primary-fill, never as a resting fill) are specific, deliberate choices carried consistently across all four pages. Copy is product-specific too — `friendlyError()` maps machine error codes to marketing-team-legible sentences ("A link can't expire before it starts.") rather than shipping framework boilerplate. Where it slips back into generic-admin territory is the *behavior* layer, not the visual layer: native `confirm()` dialogs, unstyled native `datetime-local` pickers, and concretely — `admin/users.html`'s Status column drops the very Status Badge component DESIGN.md names as a cross-table convention. Specific skin, generic skeleton in a few load-bearing spots.

**Deterministic scan**: The CLI scan (`detect.mjs --json gui/`) returned exit code 2 with exactly 2 findings, both false positives for this codebase: a `broken-image` flag on `links/detail.html:31`'s `#qr-preview` (its `src` is populated dynamically by JS at line 93 — a known, previously-documented false-positive pattern here), and a `layout-transition` flag on `gui/vendor/pico.min.css:4` (vendored third-party CSS, not authored app code). Net: **zero actionable first-party findings from the static scan.**

The live browser-injected detector (run against the actual rendered pages, not source) found more: on the dashboard, `cramped-padding` (1.734px vertical padding on the short-link pill badge — needs ≥4.0px for its 11.56px text), `nested-cards` ×2 and `edge-flush-cards` (the View/Copy/Edit/Delete button group renders as a card nested inside a table-cell card, flush against the scroll container's edge) — these independently corroborate Assessment A's finding that row actions overflow the viewport even at ordinary desktop widths. It also flagged `overused-font`/`single-font`/`flat-type-hierarchy` (a 1.5–1.7:1 ratio between smallest and largest text) across all three authenticated pages — this is largely DESIGN.md's own deliberate choice (Pico's viewport-scaling type pinned flat for admin density), so treat it as a documented tradeoff rather than a blind defect, though a slightly taller step for primary headings is worth considering without abandoning the density goal.

One methodological note: Assessment B observed its Playwright browser session being mutated by a concurrent process partway through (tab switching it didn't initiate, stray screenshots appearing from elsewhere) — almost certainly this session's shared single browser instance rather than a real bug. The dashboard and admin/users results were captured before this interference and are internally consistent; the link-detail result was re-verified after recovery. Findings from all three are reported as-is.

#### Overall Impression

The system is holding its 20-26/40 historical band for a real reason: the visual identity is genuinely specific and well-executed, but two structural cracks keep resurfacing under any tool that actually looks rather than reads code — a design-system component (Status Badge) that exists on paper and one page but not the other, and a table/action-button layout that breaks down under horizontal space pressure at both mobile *and* ordinary desktop widths, not just the narrow-viewport case already tracked. The single biggest opportunity: audit every DESIGN.md-documented component for "does every page that needs this actually use it," since the badge gap suggests the fix-and-critique cycle so far has been page-by-page rather than component-by-component.

#### What's Working

1. **Keyboard-operable sortable table headers** (`dashboard.html`, `tabindex=0` + Enter/Space handlers + live `aria-sort`) — real, uncommon effort toward efficiency that most Pico-based admin tools skip entirely.
2. **`friendlyError()`'s partial-failure honesty** — explicitly saying "Destination and schedule saved" before reporting a password-step failure, rather than a blanket "Something went wrong," is a subtle but real UX-writing win.
3. **The slug chip as a genuine signature component** — consistently deployed as the detail page's `h1`, the success banner, and the table, giving the product a recognizable visual anchor a generic admin panel wouldn't bother with.

#### Priority Issues

**[P1] No visible keyboard focus indicator on the persistent nav.**
Why it matters: confirmed via computed styles — the "Manage users" link shows `outline: none` and a fully transparent box-shadow on focus, literally zero visual difference from resting state; "Log out" fares only slightly better with a low-opacity ring. For a keyboard-only user, tabbing through the one piece of chrome present on every authenticated page gives no reliable "where am I" signal.
Fix: add a real `:focus-visible` treatment to `#app-header nav a`/`button` in `theme.css` — a full-opacity 2px Signal Blue outline would also read as on-brand.
Suggested command: `/impeccable harden`

**[P1] Row-action buttons overflow the viewport at ordinary desktop widths, not just mobile.**
Why it matters: at 1440×900 — an entirely typical laptop resolution — `#links-figure`'s `overflow-x:auto` still requires horizontal scrolling to reach Delete. The browser-injected detector independently corroborates this from a different angle: the button group renders as a `nested-cards`/`edge-flush-cards` pattern, a card nested inside a table-cell card sitting flush against the scroll container's edge. For a power user managing dozens of campaign links, every delete/edit costs an extra scroll gesture on hardware nobody would call narrow.
Fix: let the action-button group become its own scroll-independent column (e.g. sticky-right within the figure), or drop lower-priority columns (Owner, empty Starts/Expires) before the actions column under width pressure.
Suggested command: `/impeccable layout`

**[P1] The Status Badge component isn't applied on `admin/users.html`.**
Why it matters: DESIGN.md documents Status Badges as a shared, colored, capitalized convention. Confirmed via DOM inspection: the users table's Status column is plain `<td>active</td>` in default body-text color, no `.status-badge` class — while the identical semantic concept on the links table renders as a bold green `<span class="status-badge status-active">Active</span>`. This is a design-system fidelity regression on the one other page with an analogous active/disabled concept, not a one-off styling nitpick.
Fix: wrap the users table's status cell in `<span class="status-badge status-${...}">` exactly as `dashboard.html` already does.
Suggested command: `/impeccable extract`

**[P2] The dashboard edit row's password input visually overlaps its neighboring grid column.**
Why it matters: measured directly — the "New link password" input renders at x=641–1247 while its own label box is at x=138–744, overlapping into the "Remove password protection" checkbox's column. Root cause: this is the one spot in the codebase that puts a `<small>` hint *before* the `<input>` (`New link password <small>...</small><input>`), which sidesteps Pico's `:where(input,...)+small{display:block}` sibling rule that normally forces stacking everywhere else in the app. This is a distinct, previously-unflagged bug from the known Save-button-width issue, and it sits on a security-sensitive control.
Fix: move the `<small>` hint after the `<input>` to match the order used everywhere else in the codebase.
Suggested command: `/impeccable layout`

**[P2] Cramped padding on the slug-chip badge fails a basic legibility threshold.**
Why it matters: the browser-injected detector measured 1.734px vertical padding for 11.56px text on the dashboard's short-link pill (needs ≥4.0px) — this component renders on every row of the links table and doubles as the page's signature element, so the shortfall is small in isolation but touches the product's single most-repeated piece of UI.
Fix: bump `.slug-chip`'s vertical padding to at least ~4px in `theme.css`.
Suggested command: `/impeccable polish`

#### Persona Red Flags

**Sam (Accessibility-Dependent User)**: Confirmed zero focus indicator on the "Manage users" nav link (P1 above) — a hard blocker for confidently navigating the one persistent piece of chrome without a mouse. Additionally, none of the row-action buttons (`Copy`/`Edit`/`Delete`) carry an `aria-label` disambiguating which row they act on — with more than one row, a screen reader's controls list reads as repeated, indistinguishable "Delete, button" entries.

**Alex (Impatient Power User)**: No bulk operations, no export, and the confirmed desktop-width horizontal-scroll-to-Delete friction (P1 above) compounds badly across dozens of campaign links — exactly the workload this persona represents per PRODUCT.md.

**Casey (Distracted Mobile User)**: At 375px the persistent nav's four items each independently word-wrap into a cramped two-line stack with no collapse/hamburger strategy. #### Minor Observations

- `links/detail.html`'s "Recent events" table renders raw `2026-07-24T04:18:21Z` timestamps instead of running them through the app's own `formatDateTime()`, unlike every other date shown elsewhere in the product — cheap, high-value fix.
- The filter/search input on the dashboard has a correct `.visually-hidden` label but no keyboard shortcut (e.g. `/`) to jump to it, a small efficiency miss for a table-heavy tool.
- Every page examined leaves 60–80%+ of a normal viewport height as flat, unstyled space below the last card — compositional, not functional.
- The users page's "Permissions" fieldset has no visual boundary (no border/background), relying solely on its `<legend>` text for grouping.
- The type scale's 1.5–1.7:1 ratio between smallest and largest text (flagged by the browser detector) is largely intentional per DESIGN.md's pinned-scale rule, but a slightly more distinct step for primary headings is worth considering without abandoning the density goal.

#### Questions to Consider

1. If the Status Badge is important enough to name and document as a cross-page rule, why did it ship on one of the two pages that need it and not the other — was `admin/users.html` simply built before the badge existed, or is status for a person considered lower-stakes than status for a link?
2. Deleting a user account can revoke someone's ability to do their job; deleting a link just breaks a stale campaign QR code. Should these really share the exact same unstyled native `confirm()` with no distinction in weight or wording?
3. The team invested real effort in keyboard-operable sortable headers — genuinely above-average accessibility care for this class of tool — so why doesn't that same care extend to focus visibility on the nav present on every single page?
