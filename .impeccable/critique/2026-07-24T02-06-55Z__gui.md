## Design Specificity Verdict

**LLM assessment**: A partial pass. Real product character exists in surface treatment — the slug-chip pill, monospace-for-data, and QR web/print size options are genuinely tailored to a marketing team producing physical collateral. But strip the tokens and this is "form + sortable table + inline edit + View/Edit/Delete," indistinguishable from any generic CRUD admin scaffold. Nothing in the *structure* reflects that these are time-boxed marketing campaign links: no visual weight on "expires soon," no distinction between a hand-picked custom slug (the thing this audience specifically asked for) and an auto-generated one. The one moment that should feel bespoke to this product — "you just made a shareable link" — has zero payoff. The frame is authored; the moments of use are not.

**Deterministic scan**: `detect.mjs` ran clean structurally (exit 2, 2 findings, both low-stakes) — no design-system-consistency crisis, no dozens of contrast/gradient/pattern violations. One real, minor finding: `dashboard.html:19`'s `font-size: 0.8rem` on the table's compact row-action group doesn't match any step in `DESIGN.md`'s documented type ramp (Display/Headline/Title/Body only — no compact/caption step defined). This reads as a missing token in `DESIGN.md`, not a stray magic number, since it's confined to deliberately-shrunk UI chrome. The other flagged finding (`broken-image` on `links/detail.html:29`'s `#qr-preview`) is a confirmed false positive — its `src` is populated dynamically by JS after the slug is known, exactly the dynamic-content pattern that isn't a real bug (this was already flagged and accepted as a false positive earlier this session too).

**Visual overlays**: not available. No browser-automation tool (Playwright/Puppeteer/chromium-cli/MCP screenshot) is exposed in this session, and the local dev server wasn't running at scan time either — Assessment B confirmed this via `ToolSearch` and a failed `curl` before falling back cleanly to CLI-only scan. No overlay exists in any browser tab; this critique's design judgment rests on source reading, not rendered inspection.

## Overall Impression

The visual system is genuinely disciplined — better than most internal admin tools get. But the critique surfaces a real split-personality: the *chrome* (nav, chips, badges, empty states) is polished and consistent, while the *workflows underneath* stop halfway. Two forms (login, admin/users) got the full error-handling and confirmation treatment; the two forms marketing actually lives in day-to-day (create/edit a link) didn't. The single biggest opportunity: close that gap on link creation specifically — it's the product's entire reason for existing, and it's currently the flattest, least-guarded moment in the app.

## What's Working

1. **A real, consistently-applied design system, not a reskinned template** — the slug-chip pill, monospace-for-data rule, and flat/no-shadow surface treatment show up identically across all four pages exactly as `DESIGN.md` specifies. Unusually disciplined for an internal tool.
2. **Empty-state copy correctly distinguishes "nothing exists" from "nothing matches"** (`dashboard.html:152`) — small, applied consistently across the links, users, and analytics tables.
3. **The QR download options are tailored to real marketing workflows** (`links/detail.html:30-33` — separate web-preview vs. print-quality SVG/PNG), not a generic afterthought.

## Priority Issues

**[P0] No confirmation before deleting a link**
- **Why it matters**: A link may already be embedded in a printed QR code, an ad buy, or a sent email. Deleting it is irreversible and one accidental click away — worse consequences than the user-delete flow, which *does* get a `confirm()`.
- **Fix**: Add the same confirmation pattern used in `admin/users.html:185` to the link-delete handler in `dashboard.html:182-187`.
- **Suggested command**: `/impeccable harden`

**[P1] No self-serve way to change a link's destination URL or set/clear its password after creation**
- **Why it matters**: "The landing page moved" is a routine marketing request, and password-protecting a link is a real, shipped capability with zero path to it in the GUI. Both currently require engineering help, directly contradicting the product's own principle that routine link operations shouldn't need it.
- **Fix**: Extend the PATCH-backed edit row (`dashboard.html`'s `editRowHtml`) to include `target_url` and a password set/clear control.
- **Suggested command**: `/impeccable adapt`

**[P1] Zero success feedback and no copy-to-clipboard on link creation**
- **Why it matters**: This is the product's entire reason for existing, and it's the flattest moment in the app — the create-form handler (`dashboard.html:221-245`) silently clears and refreshes the table with no banner, highlight, or copy affordance. Users must manually hand-select their new link out of a table that can hold dozens of rows.
- **Fix**: Show an inline success banner with the new short URL and a Copy button on creation; consider highlighting/scrolling to the new row.
- **Suggested command**: `/impeccable delight`

**[P1] Raw API error codes leak to users on the two most common forms**
- **Why it matters**: `dashboard.html:213` and `:237` fall back to the raw `data.error` code instead of `friendlyError()`, unlike every error path in `login.html`/`admin/users.html` — bypassing the exact anti-pattern the app's own `ERROR_MESSAGES` map exists to prevent, on the highest-frequency actions in the app.
- **Fix**: Route both call sites through `friendlyError()`; populate `ERROR_MESSAGES` with the link-specific codes (slug conflicts, invalid URL, etc.).
- **Suggested command**: `/impeccable clarify`

**[P2] No visual cue for expiring links or custom-vs-auto slugs**
- **Why it matters**: A marketer managing several time-boxed campaigns needs to spot "this lapses tomorrow" at a glance and recognize her deliberately-branded slugs among system-generated ones — neither is supported; both render through the identical `.slug-chip` style with no distinguishing treatment or expiry-proximity indicator.
- **Fix**: Add a subtle badge/color state for links expiring within N hours; give custom slugs a distinct chip variant.
- **Suggested command**: `/impeccable layout`

## Persona Red Flags

**Alex (Power User)**: No keyboard shortcuts anywhere. Every action is single-row (`dashboard.html:182-194`, `admin/users.html:161-193` attach one listener per row) — no multi-select, no bulk edit/delete, no batch time-window update across several campaign links, no export. Sorting is single-column only. Alex abandons "update 20 links' expiry dates" after the third manual Edit→Save cycle.

**Sam (Accessibility-dependent User)**: Zero ARIA attributes across all four pages — no `aria-expanded` on Edit toggles, no `aria-live` region for `.form-error`, no announcement when the table re-renders. Deleting a row destroys the very button that had focus (`loadLinks()` rebuilds `#links-body` from scratch), dropping focus to `<body>` with no landmark to recover to. The tightly-packed View/Edit/Delete group with zero confirmation on Delete is a high-risk combination for switch access or voice control users.

**Morgan (Campaign Marketer, project-specific)**: synthesized from `PRODUCT.md` — a non-technical marketing team member creating/scheduling promo links and generating QR codes for print. Grabbing her new link requires manually selecting mono text out of a table (no copy button) — friction on the product's single core deliverable. The `datetime-local` start/end fields show no timezone label at all, while `datetimeLocalToIso` silently converts using the *browser's* local time — real risk for a precisely-timed midnight launch if her browser locale doesn't match the intended campaign timezone. She cannot set a link password from the GUI despite it being a real capability. If a campaign's landing page changes post-launch (routine in marketing), she has no way to repoint the existing slug/QR — she'd have to create a new link, orphaning every already-printed QR code.

## Minor Observations

- Sortable column headers give no affordance until hover — no resting-state sort icon, so sortability isn't discoverable without experimentation.
- The custom-slug `pattern` constraint has no visible helper text; a violation only surfaces the browser's generic native validation bubble.
- `admin/users.html`'s permission-fieldset relabeling on role change is a nice, specific touch worth reusing elsewhere in the app.
- `dashboard.html:19`'s `0.8rem` control-group font-size is off `DESIGN.md`'s documented type ramp (flagged by the detector) — likely a missing "compact/caption" token in the design system rather than a real bug; worth a deliberate decision either way.
- No account-lockout/recovery guidance on `login.html` — reasonable given the documented no-rate-limiting tradeoff, but the "what do I do if locked out" copy gap is unaddressed.

## Questions to Consider

- What would it feel like if link creation ended in "here's your link — copy it, scan it, ship it" instead of a form quietly clearing itself?
- Should deleting a link that's actively receiving traffic require a materially different confirmation than deleting a dormant one — given both currently get none?
- If "the landing page moved" is a routine marketing request, why does this product's own admin console make it unreachable without engineering help?
- Does rendering custom and auto-generated slugs identically serve a team that specifically asked for custom slugs to be recognizable?
