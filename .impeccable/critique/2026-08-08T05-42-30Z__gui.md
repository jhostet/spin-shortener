## Design Specificity Verdict

**Partially authored — and the authored part is one component on one page.**

**LLM assessment.** What is genuinely this product: the slug chip (navy `999px` monospace pill, reused as the detail page's `<h1>` at full URL length and truncated to `/r/slug` in the table), tag chips placed inside the Short-link cell rather than in a Tags column, `.not-yet-live`, `.lock-badge`, the nav domain selector. These are decisions by someone who knows what a URL shortener is.

What is category-interchangeable: **everything added since the last critique.** `renderViolations()` renders a slug as plain sans-serif `<a>` — no slug chip, no mono — and renders status as bare text while `.status-badge` exists three files away. `renderConsistencyFindings()` emits `<li>slug: winter · owner: admin</li>`, raw key/value pairs joined by a middot. `#rules-table` has neither the sticky action column nor the mobile column collapse that DESIGN.md documents as a **Do** and that both other tables implement.

Structural sameness: every page is `header > main.container > article(h2 + form/table)`. Fine as an app shell — but the stakes never change the structure. `backup.html` renders "Download a backup" (safe), "Restore from a backup" (irreversible, destroys all data, signs everyone out) and "Check consistency" (read-only) as three visually identical cards, with the irreversible one in the middle of the scroll path, differentiated only by a red paragraph.

Biggest missed product character: **the links table has no Clicks column.** The headline feature per PRODUCT.md is invisible from the list surface; comparing four campaign links takes four page loads. An unrelated admin tool could use four of the six pages unchanged.

**Deterministic scan.** `detect.mjs --json gui/` → exit 2, **2 findings, both false positives**:
- `broken-image` at `gui/links/detail.html:40` — `#qr-preview` gets its `src` from JS at runtime; verified live `complete: true`, `naturalWidth/Height: 222`, zero failed requests. Static scan cannot see a JS-assigned src.
- `layout-transition` at `gui/vendor/pico.min.css:4` — vendored third-party CSS, not ours.

**Net: zero real findings from the mechanical detector on first-party markup.** Worth stating plainly — the detector contributed no signal on this run. Every real finding below came from design review or from direct browser measurement. Notably it emitted no `box-shadow` and no stray-`999px` findings, so nothing in the scan fights the No-Shadow Rule or the pill reservation.

**One case where the detector pointed at the right line for the wrong reason:** it flagged `detail.html:40` as a broken image on the happy path, where it is a false positive — but the design review found a *genuinely* broken QR image at that same element in the `?slug=doesnotexist` state, where the `src` resolves to a 404. The line is right; the reasoning is not; the defect is real in a state the scanner never reached.

**Visual overlays: none, and this is the correct outcome.** Injection was blocked by the app's own CSP. Verbatim: `Loading the script 'http://localhost:41999/detect.js' violates the following Content Security Policy directive: "script-src 'self'"`, and the inline variant blocked identically. No live server was started, CSP was not disabled, no workaround attempted. There is no user-visible overlay in your browser — everything below is direct `getComputedStyle` / `getBoundingClientRect` measurement instead. A hardened CSP defeating instrumentation is the app behaving correctly.

## Overall Impression

This is a competently built admin tool with one genuinely excellent layer, one genuinely excellent component, and a widening seam between the pages that have been critiqued before and the pages that have not.

The excellent layer is error handling and confirmation. The excellent component is the slug chip. The seam is everything shipped since the last audit: five surfaces that use Pico defaults with nouns swapped, don't reach for the app's own components, and in two cases fail functionally on a phone.

**The single biggest opportunity is not visual.** It is that the Status column shows a stored field and labels it a fact. A link whose scheduling window has not opened renders a green "active" badge and returns 404 — confirmed live during this synthesis. Everything downstream inherits the conflation: the mobile column collapse, the CSV export, the bulk Enable/Disable copy.

Deterministic quality is genuinely high and deserves saying: **zero contrast failures in either theme across all five pages** (lowest measured 4.58:1, against a 4.5:1 bar), **zero console errors**, **zero page-level horizontal overflow** at 1400/768/480/390 in both themes, and **zero focus-indicator gaps** — every interactive element takes a 2px outline. The accessibility floor this app claims, it largely meets. Where it fails is where the floor was never extended.

## What's Working

**1. The error-copy layer.** `ERROR_MESSAGES` maps 23 API codes to human sentences, with a documented `overrides` parameter so one call site can win where a code's meaning differs (link passwords need 4 chars, accounts need 8). `backup.js` and `url-policy.js` extend the pattern locally with explicit fallback to the raw code, so a server-side addition renders as itself and never as `undefined`. It works because the machine vocabulary never reaches a user *and* the layer degrades instead of breaking.

**2. The confirmation system.** `confirmDialog()` deliberately inverts the row-level convention: Cancel is the plain filled button, the destructive action is `outline secondary`, so the visually loud button is the safe one. It sets `aria-labelledby` (a native `<dialog>` gets no accessible name from content), treats the native `cancel` event and a backdrop click as "no", and gets a real focus trap from `showModal()`. Verified live: cancelling preserves the selection. It works because the rule "reversible actions don't confirm" is applied consistently — so the confirms that do fire still carry weight.

**3. The measured accessibility floor.** Not a design flourish, but it is the thing most projects claim and few hit: 18.13:1 on nav text, 5.18:1 on primary buttons, 4.90:1 on inline code, all passing in both themes; a single sitewide `:focus-visible` rule with a documented equal-specificity override for `details summary`; `aria-sort` correctly cycling. The two apparent focus gaps found were both false — elements inside closed `<details>`, and one genuinely disabled button.

## Priority Issues

### [P1] The Status column shows a stored field and calls it a fact
**What:** `bf2026` (window opens 25 Nov 2026) renders a green `status-active` badge, while the `(not yet live)` qualifier lives in the separate **Starts** cell — which `dashboard.css` hides below 600px. **Confirmed live during synthesis: the badge reads green "active" and `GET /r/bf2026` returns 404.**
**Why it matters:** "does this link work right now" is computed from status AND `[start_at, end_at)`. The table shows one input and labels it the answer. A campaign manager checking her Black Friday link before a 40,000-recipient send sees green "Active" and hands out a URL that 404s. On a phone the qualifier is not merely hidden — it is absent from the accessibility tree.
**Fix:** derive the badge — `active` / `scheduled` / `expired` / `disabled`. Colour `scheduled` with the existing `--ss-slate-500` (matching `.not-yet-live`, no new token) and `expired` with `--ss-danger-500` (already used by `.expired`). Keep dates in Starts/Expires; move the *state* into the column that claims to carry it.
**Suggested command:** `/impeccable harden`

### [P1] `admin/url-policy.html` silently discards staged policy edits
**What:** `#rule-add`, `.rule-remove` and the `#default-action` handler all mutate an in-memory `stagedPolicy`. Nothing reaches the server until `#policy-save`. No dirty indicator, no `beforeunload`, and a staged rule renders identically to a saved one — the only tell is `—` in the Added column. Flipping Default action instantly rewrites the summary to a present-tense sentence asserting the new behaviour.
**Why it matters:** an admin flips the default to Block, reads a sentence confirming everything is now blocked, and leaves. Nothing changed. Removing a competitor deny-rule, watching it vanish, and believing it gone is the same lie in the safer direction. This is the app's only security-policy surface and its only silent data-loss path.
**Fix:** track a `dirty` flag; render staged rows with a "Pending" marker; change `#policy-save` to "Save 2 pending changes" with the primary fill; phrase the summary as "Will apply on save: …" while dirty; add a `beforeunload` guard. Auto-run the violations check after a successful save.
**Suggested command:** `/impeccable harden`

### [P1] `links/detail.html` renders a confident page of nothing, and a chrome-less dead end
**What:** with `?slug=doesnotexist`, `loadLinkInfo()` writes the error and returns — leaving every field label with a blank value, `#qr-preview` pointed at a 404 (browser broken-image icon plus alt text), both download anchors live, `#total-clicks` at 0, and both tables showing headers with zero rows and no empty state (those only render inside `loadAnalytics`'s success path). The message says to refresh, which can never help. With no `slug` at all, `document.body.textContent = "No link specified."` destroys the nav, the styling and every route out.
**Why it matters:** these are the states reached from a bookmark, a truncated Slack paste, or a link a colleague deleted — by people already confused. The page's answer is to look like it worked and offer two buttons that will fail.
**Fix:** on `not_found`, hide `#link-info`, `#qr-section` and `#analytics-section` and render one `.form-error` plus a `role="button"` link back to the dashboard; add a page-local `not_found` override ("That short link doesn't exist — it may have been deleted."). For the missing-slug case keep the shell and render the same empty state.
**Suggested command:** `/impeccable harden`

### [P2] The 44px tap-target floor covers four selector families, and bulk actions are unreachable on a phone
**What:** both assessments agree, and Assessment B measured it. Buttons, `nav a` and `.domain-select` are exactly 44.0px — the rule genuinely applies. Everything else is under: every text/url/password/datetime/search/file input and every `<select>` at **40.4px** (21 named IDs); all checkboxes at **20×20**; `<summary>` at **16px**; sortable `th` at **36.2px**; the in-body "Backup and restore" anchor at **18px**. `theme.css:336` even documents the gap and closes exactly one instance. Separately, at ≤480px the select-checkbox column computes to width 0, so **row selection — and therefore all six bulk actions — is impossible on a phone**, on a table the product expects to hold every campaign link the team has made.
**Why it matters:** the checkbox is the entry point to the entire bulk workflow and is 24px under the app's own published standard. The mobile collapse doesn't shrink the feature, it removes it, with no message saying so.
**Fix:** extend the existing floor block to `select`, `input[type=checkbox]`, `input[type=radio]`, `summary` and `th.sortable`; give the checkbox a padded hit area rather than a bigger box. Decide deliberately whether bulk is a desktop-only feature — and if it is, say so on the page instead of silently hiding the control.
**Suggested command:** `/impeccable adapt`

### [P2] The design system stops at the pages added since the last critique
**What:** `renderViolations()` renders slugs as plain `<a>` and status as bare text; `renderConsistencyFindings()` emits raw `key: value · key: value` list items; `#rules-table` has no sticky action column and no mobile collapse, so at 390px its figure is `scrollWidth 614 / clientWidth 327` and **the Remove button sits at x=542, entirely off-screen with no affordance indicating it exists**; three date formats coexist; `#export-csv` gives no `.form-success` while `#export-btn` does; `.form-error` red is reused as a permanent static advisory on `backup.html`, so a real `#restore-error` is visually identical to the warning 150px above it; and `#links-filter` is a 1176px `border-radius: 80px` pill directly contradicting the Pill-Is-For-Links Rule.
**Why it matters:** individually small; together the newest ~40% of the app doesn't look like the same product, and two items (the off-screen Remove button, the checkbox targets) are functional failures rather than cosmetic ones.
**Fix:** promote `slugChip(slug)` and `statusBadge(status)` into `app.js` and use them in `renderViolations`, `renderConsistencyFindings` and the users table; route every timestamp through one `formatDateTime`; give `#rules-table` the `#users-table` sticky + collapse treatment; override `#links-filter`'s radius to `var(--pico-border-radius)`; introduce a `.form-note` class so `.form-error` red means "something just failed" again.
**Suggested command:** `/impeccable extract`

## Minor Observations

- **No favicon.** `GET /favicon.ico` → **404, confirmed during synthesis**, and no page carries a `<link rel="icon">`. Assessment B reported zero console errors, which is also correct — a 404 is a completed HTTP transaction, not a failed request, and Chromium does not log favicon misses to the console. Both reports were accurate about different things. For a tool that lives in a pinned tab this is the cheapest identity win available, and the brand mark already ships a hand-authored navy link glyph.
- **`#restore-btn` is disabled but computes `cursor: pointer`** (should be `not-allowed`), with `opacity: 0.5` — it reads as clickable while inert. It is the only disabled control in the app.
- The three export `Include` checkboxes have no consequence hint; unchecking Users produces a file whose restore leaves accounts untouched — useful, and entirely unstated.
- `url-policy.html` doesn't flag a no-op rule: the seeded allow rule for `tirerack.com` under a default of Allow does nothing.
- The clean consistency report collapses 12 checks into one sentence ("No inconsistencies found — 34 keys scanned"), so the operator cannot see what was checked and "no inconsistencies" is unfalsifiable to them.
- `renderConsistencyReport()` emits an `<h2>` inside an `<article>` whose title is already an `<h2>`.
- **The sticky action column paints a wide slab when the table doesn't overflow** — on `users.html` at 1440px the last `th` is 459px of a 1176px table (39%), so the header tint stops 39% short with a vertical rule floating mid-table.
- `users.html` renders `—` in Permissions for admins, who implicitly hold everything.
- One contained edge case: `users.html` at 390px puts `.delete-btn`'s right edge at 380px against a 375px viewport — reachable only by scrolling the table sideways.
- `.expiring-soon` / `.expired` exist and use the right pattern (text suffix carries the distinction, colour is secondary) but no seeded link exercises them.
- **Do not act on any same-tick dark-mode measurement.** Assessment B's first dark sweep, read in the same tick as the theme switch, reported `details summary` at 1.00:1 and inputs still white-on-navy; a screenshot disproved both. Every number here is post-settle and re-verified.
- `login.html` correctly places the theme control outside the card so the auth page keeps its no-chrome character while staying themeable. Good judgement.

## Questions to Consider

1. **If the links table had a Clicks column, would the detail page still need to exist?** The headline feature is currently behind a page load per link, and that page is 60% empty labels. What if the table carried clicks plus a 7-day sparkline, and `detail.html` became the QR/edit/deep-analytics surface it is actually good at?
2. **`status` is stored; "does this resolve right now" is computed. Why does the UI show the field and label it the fact?** Every downstream surface inherits that conflation.
3. **The app has a beautiful `<details>` idiom and uses it exactly twice — both on the page with the least prose.** What would `url-policy.html` and `backup.html` look like if the explanation collapsed and the controls came first?
4. **DESIGN.md justifies omitting slug names from the delete dialog because they are "visible behind the dialog" — but the backdrop blur makes them unreadable.** Is the rule wrong, or is the backdrop wrong, and how many other rules in that file were reasoned about but never re-verified against shipped pixels?
5. **The nav is documented as "at its item budget", the sanctioned escape hatch is in-body anchors, and that hatch is already used twice with the file itself warning a third should trigger a rethink.** At 390px it is four stacked rows and 43.6% of the viewport. Is the honest reading that the budget was exceeded two items ago, and this app wants a left rail or a page-level admin sub-nav?
6. **`.slug-kind-badge`, `.lock-badge`, `.tag-chip` and `.not-yet-live` are one visual treatment doing four semantic jobs**, deliberately, to avoid inventing tokens. But "this link is password-protected" and "someone typed the word promo" are not the same class of fact. What is the smallest addition that separates properties of the link from labels a human applied, without introducing a second pill?
7. **Every high-stakes flow is well-confirmed except the one that silently loses work.** Restore demands a typed word; bulk delete states its scale; deny-default asks twice. Meanwhile Add rule stages invisibly. What if "unsaved" were as loud here as "irreversible" already is?
