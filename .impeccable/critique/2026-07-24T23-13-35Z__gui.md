#### Overall Impression

The theming fix mattered more than a color correction — it's the first time any critique has actually seen this app's intended identity, and it holds up well: the signature components (nav, slug chip, button de-emphasis convention) are genuinely well-executed, verified by computed style, not just described in DESIGN.md. The score jump to 30/40 reflects real, cumulative work, not measurement noise. What's left is a specific, recurring theme: the app is very careful about *low-stakes* reassurance (link deletion, partial-save error copy) but inconsistent about *high-stakes* reassurance — promoting someone to admin gets less ceremony than deleting a link, and the self-delete guard shows the same "are you sure, permanent" ritual for an action that's already known to be impossible.

#### What's Working

1. **The button de-emphasis convention is shipped, not just documented** — verified by computed style: Delete really is slate-muted (`rgb(93,107,137)`) while Edit/View/Copy are really signal-blue, exactly as DESIGN.md prescribes.
2. **Partial-success error messaging** in the link edit flow ("Destination and schedule saved. Could not update link password.") is unusually considerate for an internal tool.
3. **Honest permission-gating**: `canEditLink()` hides Edit/Delete exactly where the server would 403 — a limited-permission user never sees a button that lies about what it can do.

#### Priority Issues

**[P1] Self-delete confirmation gives no advance warning that the action is doomed.** `admin/users.html`'s delete handler shows the identical generic confirm dialog for every row, including the logged-in admin's own — forcing a "yes, permanent" commitment moments before the server rejects it with `cannot_delete_self`. Fix: compare the row's username against the principal from `initHeader()` and hide/disable Delete on the viewer's own row. → `/impeccable harden`

**[P1] Promoting a user to admin has no confirmation at all.** The role `<select>` triggers only a live fieldset-disable, then a plain Save — no distinct "you are granting full access" moment, despite this being more consequential than link deletion (which does get a confirm dialog). Fix: route admin-role saves through the already-built `confirmDialog`. → `/impeccable harden`

**[P2] Row actions fall outside the visible table on realistic viewports, not just narrow ones.** Confirmed at both 1400px desktop (Delete clipped) and 390px mobile (~3.6× scroll to reach any action) — independently corroborated by the detector's `nested-cards`/`edge-flush-cards` findings. Fix: sticky-position the action column within the scrolling figure, or collapse actions into a single menu. → `/impeccable layout`

**[P2] User creation has no completion payoff, unlike link creation.** `admin/users.html`'s create-user handler just resets the form and reloads the table — no success message, directly contradicting DESIGN.md's own "give a real completed action visible payoff instead of a silent form-clear" rule, which the link-creation flow follows correctly. Fix: add a matching success message. → `/impeccable harden`

**[P3] No progressive disclosure on the primary create-link form.** Starts/Expires/Password render unconditionally even though they're occasional-use fields for the primary persona's modal action (paste URL, submit). Fix: collapse behind a disclosure toggle, consistent with the edit-row collapse pattern already established elsewhere. → `/impeccable distill`

**Casey (non-admin with `links.view_all` but not `edit_all`)**: genuinely well-served, not a red flag — verified the app never shows Edit/Delete controls the API would reject.

#### Minor Observations

- Auto-generated slugs mix case (`08ud9CC`) — a display concern even though generation is server-side.
- The "expiring soon" annotation wraps to two lines in the Expires column while sibling cells stay single-line, breaking row-height rhythm.
- Nav wraps awkwardly at 390px — "spin-shortener" breaks to two lines, consuming ~180px of vertical space before any page content.
- No pending/disabled button state during async submits — a double-submit risk on slow connections.
- The confirm dialog's Delete button uses the same blue hue as Cancel (differentiated only by fill vs. outline) — this is *consistent with DESIGN.md's own documented de-emphasis-not-warning-color rule* for destructive actions, not an oversight, but worth naming as a real, deliberate tradeoff a reader might otherwise assume was accidental.

#### Questions to Consider

1. DESIGN.md documents a "give a visible payoff" rule, apparently generalized from the link-creation flow — but the user-creation flow doesn't follow it. What ensures a documented rule gets checked against every flow it applies to, not just the one that produced it?
2. Promoting someone to admin is strictly more powerful than deleting a link, yet the app spends a whole confirm-dialog ceremony on the lesser of the two actions. Was that a deliberate risk assessment, or did confirmation just happen to get built for "delete" because that was the obvious destructive verb?
3. Is phone-based link management actually in scope for this team? If not, should the table hide non-critical columns on narrow viewports instead of shipping a scroll nobody's meant to use?
