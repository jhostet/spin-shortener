## Considered and rejected

- [x] Client-side destination-URL reachability check on link creation — considered 2026-07-18, decided against, not deferred. The idea: before/without blocking link creation, check that a submitted `target_url` is actually reachable, run from the *browser* rather than server-side (since a real user's browser is far less likely to get bot-blocked by the destination site than a server making the same request). Rejected because neither `redirect` nor `api` has any `allowed_outbound_hosts` entries (confirmed empty/absent in `spin.toml` for both), so the server-side half of that reasoning is moot — the check can only ever run client-side. And a browser-side check against an arbitrary cross-origin URL is limited to a `fetch(..., {mode: "no-cors"})` opaque request, which can detect a hard DNS/connection failure but can never distinguish a real `200` from a `404`/`500` (no readable status across origins without CORS headers from the destination) — not enough signal to justify the added complexity, especially since the check could never be allowed to block submission anyway. Revisit only if a genuinely new mechanism becomes available (e.g. an outbound-allowed validation proxy), not as a plain client-side nudge.

- [x] Per-request CSP nonce injection in `gui-pages` (and its hash-based sibling) — considered 2026-07-31 while planning `docs/plans/csp-drop-unsafe-inline.md`, decided against, not deferred. The idea, and the one the older "Future work" entry reaches for first: generate a fresh nonce per response, put it in both the `content-security-policy` header and every inline `<script>`/`<style>` tag, so the GUI's inline code could stay where it is. Rejected on four counts, the third being fatal: (1) it forces `build_response` to stop being a pass-through and instead do byte-level markup surgery (`body.replace(b"<script>", …)`) on every request, in the one component whose entire job is to be a trustworthy header attacher — a page reformatted to `<script >` or given an extra attribute would silently stop receiving a nonce and start being blocked, a failure that surfaces as a dead page in a browser, not a failing test; (2) it needs a CSPRNG under `componentize-py`, which is unconfirmed and not safe to assume given `hashlib.pbkdf2_hmac`'s documented absence in that runtime; (3) **it does not finish the job** — confirmed against MDN's `style-src-attr` page that nonces apply to `<script>`/`<style>` *blocks* only, so the 7 static `style="display: none"` attributes (6 in HTML + 1 in an `app.js` `innerHTML` template) would still be blocked and `style-src 'unsafe-inline'` would have to stay, buying a hardened `script-src` and nothing else; (4) it makes every HTML response uncacheable by construction and leaves 925 lines of JS/CSS stranded inside `.html` files where no editor or linter treats them as JS and CSS. The hash (`'sha256-…'`) variant avoids the per-request work but replaces it with a permanent tax — recompute the hash and hand-edit the CSP string on every edit to any inline block, failing silently — and shares defect (3) exactly. Revisit only if a future page genuinely cannot externalize its script (e.g. server-templated JS), which is not the case for any of the five pages today.
- [x] Serving the new per-page `.js`/`.css` from `gui-pages` instead of the `gui` static component — considered 2026-07-31 while planning `docs/plans/csp-drop-unsafe-inline.md`, decided against. Genuinely attractive: `gui-pages` already owns the `/...` catch-all, so it would add **zero** `spin.toml` routes (versus the 8 exact routes the chosen approach adds) and would express the whole asset list as new entries in `routing.py`'s already-host-tested `ROUTES` dict, sidestepping the `spin_static_fs` path-resolution gotchas entirely. Lost because it routes every subresource request through a `componentize-py` Python Wasm component instead of the purpose-built static fileserver — a Python component instantiation per asset per page load, for zero benefit — and because it would need a new content-type map in `routing.py` (which hardcodes `text/html` today) purely to serve files it has no business serving. More fundamentally it inverts the architecture the 2026-07-25 security-headers pass deliberately established: `gui-pages` serves navigated documents that need headers, `gui` serves static subresources that don't. `CLAUDE.md` already sanctions the chosen path in as many words — "Stick to exact routes for this component if any more assets are ever added to it." A related sub-alternative was also rejected: appending the three pages' CSS blocks to the already-routed `theme.css` to save 3 of the 8 routes. All three blocks are scoped tightly enough (`#links-table`, `#users-table`, `.detail-heading`) that nothing would collide, but it would make every page download 206 lines of rules that apply to one other page, and it would blur `theme.css` — the design-system file `DESIGN.md` describes — with three pages' worth of table-layout workarounds. Route entries are cheap and inert; the muddied boundary is not. Revisit only if the `[[trigger.http]]` list becomes genuinely unmanageable.

(1) **An inline `<head>` snippet whitelisted by a `'sha256-…'` CSP hash** — zero new routes, zero new requests, and the CSP stays a static string, but this reopens a decision settled the same day in the entry above: the hash must be hand-recomputed on every edit with a silently dead page as the failure mode, and that entry says to revisit only for a page that genuinely cannot externalize its script, which a 15-line theme-init snippet obviously can. - [x] Backing up KV to S3 or any cloud object storage — considered 2026-08-02 while planning `docs/plans/kv-backup-restore.md`, dropped by the user before planning began and recorded here in full because it is the first thing any future reader will reach for. The attraction is real: a backup that lives somewhere other than the operator's Downloads folder, can be scheduled, and survives the laptop. It loses on a structural fact, not a preference — **`api` has no `allowed_outbound_hosts` entry, and Spin denies all outbound HTTP when the key is omitted** (confirmed, `CLAUDE.md`'s "Security tradeoffs"). That exact property is the *stated reason* this app has no brute-force rate limiting on login or link passwords, so punching an outbound hole for a convenience feature would spend the component's most load-bearing security property on the least urgent requirement, and `PRODUCT.md` principle 2 ("avoid adding infrastructure … unless a real incident or requirement forces it") says the same. - [x] Including `password_hash` in the backup file — considered 2026-08-02 while planning `docs/plans/kv-backup-restore.md`, decided against; hashes are stripped and every restored account needs a password reset. Attractive because it makes restore a genuine one-step recovery where everyone's password still works and nobody has to be contacted. It loses on what the artifact becomes: a PBKDF2 hash is offline-attackable at the attacker's leisure, and this file's whole distribution model is "a JSON document in a Downloads folder, emailed around, dropped in a shared drive, committed to a repo by mistake". The 100,000-iteration cost factor is documented as the *only* mitigation against password guessing, and it only slows an *online* attacker. Stripping hashes also buys something concrete — **the file needs no encryption, no key management and no special handling**, which is the entire reason "no encryption" is a defensible non-goal rather than an omission. The cost is bounded and visible: the admin users table flags exactly who still needs a reset, and the reset flow (`PATCH /api/users/{username}` with `{"password": ...}`) already exists and is already tested. - [x] Encrypting the backup file — considered 2026-08-02 while planning `docs/plans/kv-backup-restore.md`, rejected as a direct consequence of stripping hashes. Once hashes, `session:*` keys and `_meta:bootstrapped` are excluded, the file holds link destinations, owners, schedules, click counts and the username/role/permission list — internal, not secret: any `links.view_all` user can already CSV-export most of the link half from the dashboard, and the user half is `users.manage`-gated exactly like the endpoint. Encryption would need a key, which means key management, which this app has none of; and componentize-py's WASI CPython is already missing `hashlib.pbkdf2_hmac` (confirmed by a build/run spike, see `api/auth.py`'s hand-rolled PBKDF2), a strong signal not to bet a recovery feature on its crypto surface. **The file holds no secrets by construction — that is the reason, and it is only true while hashes are stripped.**
- [x] Merge semantics for restore, and wipe-then-write ordering — both considered 2026-08-02 while planning `docs/plans/kv-backup-restore.md`, both rejected in favour of **replace, implemented as write-then-prune**. A merge ("write what's in the file, leave everything else") never empties a store and feels safer, but after a corruption event the operator cannot tell whether a record they see is restored-good or corrupt-surviving, and the indexes end up a union of two eras — `all_links` from the file naming slugs whose records were not in the file, plus surviving slugs absent from the restored index. That is exactly the index/record drift `bulk.py`'s write-ordering rule exists to avoid, manufactured deliberately. Wipe-then-write is the naive reading of "replace" and is simpler, but a failure between the wipe and the writes leaves an **empty** store — strictly worse than the pre-restore state. Write-then-prune (write every entry from the file, then delete every pre-existing key not in the file) gives the same end state on success and a recoverable superset on failure. Revisit only if a real "restore just these links" requirement appears, and then as a separate selective-import feature, not by loosening this one.
- [x] Requiring the operator's password to confirm a restore, instead of a typed `REPLACE` — considered 2026-08-02 while planning `docs/plans/kv-backup-restore.md`. A password re-prompt is the stronger anti-mistake control and has precedent in other admin tools. It loses on cost and fit: a second PBKDF2 verification on the request path, a password field in a form whose whole purpose is "do not do this by accident", and a new failure mode (wrong password on the one action you take when things are already broken). The typed literal is server-validated (`400 confirmation_required`), costs one string comparison, cannot be triggered by a stray click or a replayed request, and is testable in `pytest` with no crypto — with the count-bearing `confirmDialog` already established by the Bulk Action Bar on top of it. Also rejected in the same pass: **a different permission bar for restore than for backup**, because there is no higher tier to promote it into — `users.manage` is already equivalent to the `admin` role by escalation (`users.handle_update` has no self-promotion guard, so a `users.manage` holder can PATCH their own record to `role: "admin"`). If a self-promotion guard is ever added, revisit and require `role == "admin"` for restore specifically.
- [x] Putting the backup/restore UI on `admin/users.html` instead of a new admin page — considered 2026-08-02 while planning `docs/plans/kv-backup-restore.md`, and it was close. Genuinely cheaper: no new page, no new `spin.toml` route, no `ROUTES` entry, no nav item, and — the real prize — **no nav overflow re-measurement**, which DESIGN.md records has bitten this nav twice already (the theme control forced the 480px wrap fallback; the domain selector needed a four-breakpoint re-measure in both themes). It loses on placement: the users page is routine, frequent work (reset one password, flip one permission), and restore is the one action in the app that replaces three KV stores with no undo and ends the session. One page puts the most destructive control a mis-click from the most routine one, and `PRODUCT.md` principle 5 asks for admin surfaces to stay distinct. Recorded rather than silently dropped because it is the closest neighbour to the plan's own pre-approved fallback — if the nav measurement fails, the nav item is dropped and `admin/users.html` gains a plain in-body link, with the separate page kept.
- [x] Restore rebuilding or repairing the indexes, and a per-value "JSON or base64" encoding discriminator — both considered 2026-08-02 while planning `docs/plans/kv-backup-restore.md`. Index repair is attractive because it would turn restore into a fix for exactly the corruption that motivates backups; it requires deciding whether an unindexed `slug:X` is orphaned junk to drop or a live link to re-index, and whether an `all_links` entry with no record is a dangling reference or a failed write — getting either wrong deletes data, silently, in the one operation an operator runs when they are already in trouble. Restore therefore reproduces the file faithfully, inconsistencies included; a read-only consistency-check endpoint is the honest shape for repair and is filed under Future work below. The encoding discriminator would make most of the file human-readable (nearly every value in these stores is already JSON) but costs a per-entry discriminator, doubles the encode/decode branches and the test matrix, and creates a real ambiguity where a value that *is* valid JSON but was written as opaque bytes round-trips through a different path than it arrived on. Uniform base64 costs ~33% of file size on an already-capped file and keeps exactly one code path; keys stay plaintext, which is enough to eyeball a file without decoding it.

## KV backup and restore

Operator-invoked backup and restore of the `links`, `users` and `analytics` stores, downloaded to and uploaded from the browser. Plan: `docs/plans/kv-backup-restore.md`. Six fixed constraints from the user: **no S3 or cloud storage of any kind** (the plan adds no `allowed_outbound_hosts`, preserving the no-outbound property `CLAUDE.md` cites as the reason there is no rate limiting); the file carries **no credential material at all** — user records are included but `password_hash` is stripped, and session keys and `_meta:bootstrapped` are excluded, which is also why the file is not encrypted; restore **replaces** the stores it covers rather than merging; users are restored **last** and the operator is warned they will be logged out; recovery works because omitting `_meta:bootstrapped` lets `ensure_bootstrap_admin` re-seed the admin from `SPIN_VARIABLE_ADMIN_BOOTSTRAP_PASSWORD` on the next start, who then resets everyone via the existing flow; and a restored account with no hash **can never authenticate** and is flagged in the users table so it is visible who still needs a reset. The first task is a spike that blocks the rest: whether `store.get_keys()` works at runtime decides if this is a true full-fidelity backup or a logical export that can only see what the app's own indexes know about — and the plan is explicit that it must not be called something it is not.
