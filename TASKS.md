# TASKS

Tracks the phased build-out described in the approved plan (see conversation/plan history). Phases ship in order; do not start a phase's tasks until the prior phase's tasks are all checked off.

## Phase 1 — Foundations (KV wiring, auth skeleton, minimal link CRUD)

- [x] Declare `links`, `users`, `analytics` KV stores and grant them per component — file(s): spin.toml, runtime-config.toml — done when: `[component.redirect]` has `key_value_stores = ["links", "analytics"]` and `[component.api]` has `key_value_stores = ["links", "users", "analytics"]`, and `spin up --build --runtime-config-file runtime-config.toml` starts without KV-related errors — **note:** contrary to the original plan assumption, Spin does NOT auto-provision named (non-`default`) stores; a `runtime-config.toml` mapping each to `type = "spin"` is required even for local dev, added here and referenced from CLAUDE.md's Commands section
- [x] Add bootstrap-admin and session/cookie Spin variables — file(s): spin.toml — done when: `admin_bootstrap_username`, `admin_bootstrap_password` (secret), `cookie_secure` are declared and wired into `[component.api.variables]`
- [x] Implement real slug lookup + redirect in `redirect` (no password/analytics yet) — file(s): redirect/main.go — done when: `GET /r/{slug}` for an existing `slug:<slug>` KV record returns `302` to `target_url`; missing/disabled slug returns `404`
- [x] Implement local password hashing + verification helpers (Python) — file(s): api/auth.py — done when: a function hashes a password into `pbkdf2_sha256$<iter>$<salt>$<hash>` using stdlib `hashlib`/`hmac`/`secrets` only, and a matching verify function round-trips correctly, verified with a quick script/spike — **note:** `hashlib.pbkdf2_hmac` is not available in componentize-py 0.23.0's WASI CPython; implemented PBKDF2-HMAC-SHA256 manually from `hmac.new`+`hashlib.sha256` instead (confirmed working under `spin up`)
- [x] Implement bootstrap-admin seeding on first run — file(s): api/auth.py, api/app.py — done when: on a fresh KV store, the first request seeds one `user:<username>` admin record from the bootstrap variables, and subsequent runs do not reseed
- [x] Implement `AuthProvider`/`LocalAuthProvider` + session issuance — file(s): api/auth.py — done when: `authenticate(username, password)` returns a `Principal`/`AuthResult` or `None`, and `create_session(username, auth_provider)` writes a `session:<token>` KV record and returns a token
- [x] Implement `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me` — file(s): api/app.py, api/auth.py — done when: login sets the session cookie (`HttpOnly`, `Secure` gated by `cookie_secure`, `SameSite=Lax`) and returns `csrf_token`; `me` returns 401 without a valid session and the user/permissions with one; logout clears the session KV record and cookie
- [x] Implement session-validation middleware/helper used by all authenticated endpoints — file(s): api/app.py, api/auth.py — done when: a shared helper resolves the session cookie to a `Principal` or raises/returns 401, re-reading the user record fresh (not cached) each call
- [x] Implement link CRUD (random slug only, no password/custom slug yet) — file(s): api/links.py, api/app.py — done when: `POST/GET/DELETE /api/links` and `GET /api/links/{slug}` work against the `links` KV store, enforce session auth, and enforce owner-or-admin on get/delete
- [x] Build bare-bones `gui`: login, dashboard list, create-link form — file(s): gui/login.html, gui/dashboard.html, gui/index.html, gui/app.js — done when: a user can log in, see their links, and create a new random-slug link, all via `fetch` against `/api/...`
- [x] End-to-end manual verification of Phase 1 — file(s): (none — verification step) — done when: `spin up --build` runs cleanly; a fresh admin can log in via `gui`, create a link, and clicking `/r/{slug}` redirects correctly — verified via a headless-Chromium (Playwright) drive of the real login→dashboard→create→redirect flow, screenshots confirmed, zero console errors. **Note:** local browser testing over plain HTTP requires `SPIN_VARIABLE_COOKIE_SECURE=false` (the session cookie's `Secure` flag otherwise blocks the browser from storing/sending it over non-HTTPS) — production/HTTPS deployments should leave `cookie_secure` at its default `true`.

## Phase 2 — Custom slugs, permissions, password gate, QR

- [x] Add `permissions` list + `links.create_custom_slug` enforcement — file(s): api/auth.py, api/links.py — done when: creating a link with a custom slug returns `403` for a user lacking the permission and succeeds for one who has it (or is `admin`) — verified the admin-bypass and 400/409 paths via curl; the true non-admin-without-permission 403 path can't be exercised until Phase 4 ships user management (no way yet to create a restricted user), noted as a follow-up check once that lands
- [x] Add custom-slug validation (charset/length) and collision handling — file(s): api/links.py — done when: invalid custom slugs are rejected with a clear error and slug collisions return a conflict error instead of overwriting an existing link
- [x] Add `password_hash` field to link records + `POST /api/links/{slug}/password` — file(s): api/links.py — done when: an owner/admin can set/change/remove a link's password via this endpoint, stored in the shared `pbkdf2_sha256$...` format — also scrubbed `password_hash` from every API response (`create`/`get`/`list`/`set password` now return a `password_protected` boolean instead)
- [x] Implement password-prompt page in `redirect` (embed + html/template) — file(s): redirect/main.go, redirect/prompt.html, redirect/passwordgate.go — done when: `GET /r/{slug}` for a password-protected link renders the prompt instead of redirecting, with the slug safely escaped
- [x] Implement password verification on `POST /r/{slug}` — file(s): redirect/main.go, redirect/passwordgate.go — done when: correct password redirects (`302`), incorrect password re-renders the prompt with an error (`401`), and every request re-fetches the link fresh from KV (no unlock cookie, per the confirmed re-prompt-every-time decision) — verified cross-language (Python-hashed, Go-verified via stdlib `crypto/pbkdf2`) via curl, including that removing a link's password takes effect on the very next request with zero stale state
- [x] Spike: add `qrcode`/`pypng` deps and confirm componentize-py build still works — file(s): api/pyproject.toml — done when: `uv run componentize-py -w spin:up/http-trigger@4.0.0 componentize app -o app.wasm` succeeds with the new deps and the resulting `.wasm` runs under `spin up` — no Pillow/C-extensions pulled in (confirmed via uv.lock: only `qrcode`, `pypng`, `colorama`, all pure Python)
- [x] Implement `GET /api/links/{slug}/qr` (svg + png, web/print sizes, download) — file(s): api/qr.py, api/app.py, spin.toml — done when: both `format=svg` and `format=png` return valid, scannable QR images at both `size=web` and `size=print`, and `download=1` sets `Content-Disposition` — verified under `spin up`; **note:** added a `public_base_url` Spin variable so the QR encodes the short link (`{public_base_url}/r/{slug}`) rather than the raw `target_url` — encoding the target directly would let a scan bypass the redirect, analytics, and password gate entirely
- [x] End-to-end manual verification of Phase 2 — file(s): (none — verification step) — done when: a permitted user creates a custom-slug, password-protected link; visiting it prompts for a password and only redirects on a correct entry; the QR code for the link scans correctly with a phone camera — verified via curl: created a combined custom-slug + password-protected link, confirmed the password prompt/reject/accept flow and a well-formed QR (visually inspected, encodes the short link per source review — no physical phone/camera available in this environment to scan it)
