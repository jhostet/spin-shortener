# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`spin-shortener` is a polyglot WebAssembly URL shortener built on [Spin](https://spinframework.dev) (Fermyon's WASI HTTP framework), with three independently-built components composed via `spin.toml`. Shipped functionality: auto-generated and permission-gated custom short links, optional per-link passwords, optional start/end time windows, per-link QR codes (SVG/PNG), click analytics (totals, per-day, a best-effort recent-events sample), local username/password auth with session cookies, and admin user management. See `TASKS.md` for the full phase-by-phase build history and `README.md` for a user-facing overview.

## Architecture

`spin.toml` is the single source of truth for routing and build wiring. It defines four Wasm components across six HTTP triggers (two components — `gui` and `gui-pages` — split the GUI's routes between them):

- `route = "/r/..."` → **`redirect`** component (`redirect/`, Go) — resolves short links and issues redirects; the hot path, hit on every click. Built with `go tool componentize-go build`, compiling `redirect/main.go` (+ `passwordgate.go`, the embedded `prompt.html`, and the pure-logic `redirect/linkgate/` package) to `redirect/main.wasm`. Uses `github.com/spinframework/spin-go-sdk/v3/http` and registers a handler via `spinhttp.Handle`. `allowed_outbound_hosts = []` — no outbound network access, by design (see "Security tradeoffs" below for what this rules out). `key_value_stores = ["default"]` — see "KV store: the single `default` store and the prefixing view" below.
- `route = "/api/..."` → **`api`** component (`api/`, Python) — all authoring/auth/analytics logic: link CRUD, custom slugs, passwords, time windows, QR generation, analytics aggregation, local auth/sessions, and user management. Built with `uv run componentize-py -w spin:up/http-trigger@4.0.0 componentize app -o app.wasm`, compiling `api/app.py` (the WASI entrypoint/router) plus `auth.py`/`links.py`/`qr.py`/`analytics.py`/`users.py`/`responses.py`. Uses `spin_sdk.http.Handler`. `key_value_stores = ["default"]` — see "KV store: the single `default` store and the prefixing view" below.
- `route = "/app.js"`, `route = "/theme.css"`, `route = "/vendor/pico.min.css"`, `route = "/theme-init.js"`, plus one route per page-scoped asset (`/index.js`, `/login.js`, `/dashboard.js`, `/dashboard.css`, `/admin/users.js`, `/admin/users.css`, `/links/detail.js`, `/links/detail.css`) → **`gui`** component — a prebuilt static file server (`spin_static_fs.wasm`) serving only these genuinely-static, non-HTML assets. Its `files` mapping covers all of `gui/` (narrowing it broke file resolution), but only these 12 exact routes are reachable. The 8 page-scoped routes exist because the CSP dropped `'unsafe-inline'`; adding a page's asset without its route serves a page whose script silently 404s. `/theme-init.js` is loaded by every page (the theming bootstrap — see "Theming"), not scoped to one. **Route gotcha, confirmed live:** once this component has more than one trigger route, `spin_static_fs`'s path resolution breaks specifically for wildcard (`/...`) routes — stick to exact routes here if more assets are ever added.
- `route = "/..."` (catch-all) → **`gui-pages`** component (`gui-pages/`, Python, same `componentize-py` toolchain as `api`) — serves the GUI's actual HTML pages via a fixed path→file allowlist (`gui-pages/routing.py`), and attaches the security response headers below to every response. Introduced because `spin_static_fs` has no custom-header capability, and security headers are only meaningful on the navigated document, not a `.js`/`.css` subresource. **A path outside that allowlist, and a `ROUTES`-vs-filesystem read failure, both render a styled HTML page** (`gui-pages/errorpages.py`, zero `spin_sdk` imports, renders its `ERROR_PAGES` bytes constants **at import time** so the 500 branch performs no I/O of its own — it cannot fail the way the read it's handling just did). Every asset reference in these pages uses a leading-slash absolute path, unlike every real page here, because this catch-all serves a 404 at arbitrary depth — a relative path would resolve under the requested depth instead of `gui/`'s root.

A fifth component exists for local development only and is **deliberately absent from `spin.toml`**:

- `route = "/internal/kv-explorer/..."` → **`kv-explorer`** — [Fermyon's prebuilt KV explorer](https://github.com/fermyon/spin-kv-explorer) (v0.10.0), third-party and unmodified. Browses raw key-value contents during development. Lives in `dev/kv-explorer.toml`, which `dev/kv-explorer-up.sh` concatenates onto a copy of `spin.toml` to produce a gitignored `spin-dev.toml` on every local run, so the dev manifest can never drift from the real one and `spin deploy` has nothing to pick up. **The reviewer's check is `grep -c kv-explorer spin.toml` → `0`**, and `gui-pages/tests/test_manifest_components.py` fails CI if the committed manifest ever gains a fifth component (a `tomllib` set comparison, not a grep — sub-tables like `[component.api.build]` would make a grep guard never fire).
  - **It has full CRUD over the single `default` store** — every key in the app, `links:`/`users:`/`analytics:` prefixes included. It can overwrite and delete any key with no undo. That is deliberate (repairing bad local test data is half its value), but a stray click destroys local data.
  - **Since the KV store consolidation collapsed the three named stores onto Spin's single `"default"` label (required by Akamai Functions), there is no longer any store-level separation for this component to respect.** Before that, `users` was deliberately withheld via the `key_value_stores` list — the explorer takes the store name straight from the request path and hands it to `kv.OpenStore` with no allowlist of its own, so that list was the only thing enforcing it. Granting `["default"]` grants everything, `users:user:*` PBKDF2 hashes and `users:session:*` tokens included. This is accepted, not overlooked: preserving the old separation would need a config seam whose deployed-vs-dev mismatch is a worse property to own than a dev-only credential exposure in a tool that already has full CRUD over everything else. Acceptable *only* because this fragment is never part of a deployed manifest — `gui-pages/tests/test_manifest_components.py` fails CI if that ever stops being true.
  - `allowed_outbound_hosts = []`, narrowed from upstream's `["redis://*:*", "mysql://*:*", "postgres://*:*"]` (those exist only for externally-backed KV; this app's store is sqlite-backed). Verified sufficient live.
  - Basic auth is required even locally rather than using upstream's `SPIN_APP_KV_SKIP_AUTH=1`: `--env` reaches every component, and unauthenticated CRUD on localhost is reachable from a cross-origin `text/plain` POST, since upstream's `AddKeyHandler` never checks `Content-Type`. Username defaults to `kv`; the password is a required secret variable.
  - **Whether local KV persists depends entirely on whether you pass `--runtime-config-file`, and the counter-intuitive part is that passing it is the NON-persistent option.** Measured on Spin 4.0.2, 2026-08-07, reading the startup log line each time:

| command | Spin logs | persists across restarts? |
|---|---|---|
| `spin up --build` (no runtime config) | `Storing default key-value data to ".spin/sqlite_key_value.db"` | **yes** |
| `spin up --build --runtime-config-file runtime-config.toml` | `Storing default key-value data to a temporary in-memory store.` | **no** |
| same, but with `path = "..."` added under `[key_value_store.default]` | `Storing default key-value data to "<path>"` | **yes** |

  **`type = "spin"` with no `path` means in-memory in Spin 4.0.2** — `runtime-config.toml`'s own comment calling it "Spin's built-in sqlite-backed local store" is wrong. **The documented command passes the flag, and `dev/kv-explorer-up.sh` always passes it**, so anyone following the docs — and every KV-explorer session — gets a store wiped on every restart. A `path` is resolved **relative to the runtime-config file's own directory**, not the working directory. Adding one to `runtime-config.toml` would make the documented command persistent; that has not been done, because a wiped-per-run dev store is a defensible default and changing it is a behaviour decision, not a typo fix.
  - **When it is sqlite-backed, the file is an ordinary SQLite database** with a single `spin_key_value(key, value)` table, so `sqlite3` or Python's `sqlite3` module reads it directly — often faster than the KV explorer for a one-off check, and how the sharded click counter's key distribution was verified. `.spin/` is gitignored.

Each component is built independently and only in its own `workdir`; there is no shared build step or root-level package manifest. When editing one component, you generally don't need to touch the others' toolchains.

**Why Go for `redirect` but Python for `api`/`gui-pages`:** the redirect path is the hot path (every short-link click) and is written in Go for raw performance. The `api`/`gui-pages` surfaces (link creation, management, frontend) aren't on that hot path, so they're written in Python to prioritize developer velocity and code understandability over raw speed — the performance tradeoff isn't worth it there. Keep this split in mind when adding new functionality: if it's on the redirect hot path, it likely belongs in the Go component; otherwise default to Python for velocity.

`redirect/main.wasm`, `api/app.wasm`, and `gui-pages/app.wasm` are all build artifacts and are gitignored — they must be rebuilt via `spin up --build` (or the per-component build commands in `spin.toml`) after any source change; they are not checked into the repo.

### KV store: the single `default` store and the prefixing view

Since `docs/plans/kv-store-consolidation.md`, both `redirect` and `api` declare `key_value_stores = ["default"]` — Spin's single auto-provisioned store, required because Akamai Functions (the intended production target) allows only that one label. The app still has three logical namespaces (`links`, `users`, `analytics`); they're kept apart by prefixing every physical key (`links:slug:<slug>`, `users:user:<username>`, `analytics:count:<slug>:<shard>`, …) rather than by store name.

- **`api/kvprefix.py` is the only Python module that knows prefixes exist.** It exposes `PrefixedStore` (a `get`/`set`/`delete`/`exists` view over one namespace), `open_views(physical_store)` (returns the `{"links", "users", "analytics"}` view dict `api/app.py` binds once per request), and `scoped_list_keys(raw_list_keys)`. `links.py`, `auth.py`, `users.py`, `bulk.py`, `backup.py`, `consistency.py`, `urlpolicy.py` and `analytics.py` are all unaware of it and take a `store` parameter exactly as before.
- **`scoped_list_keys` is a security control, not tidiness.** It filters a raw physical-key enumeration down to one namespace's keys (prefix stripped) before any caller sees them. `backup.py`'s redaction/exclusion guards and `consistency.py`'s key-shape classification are all written against unprefixed keys, so an unfiltered enumeration would silently defeat every one of them — the concrete failure being a full PBKDF2 account hash written into a links-only backup.
- **`PrefixedStore` deliberately has no `get_keys` method.** Omitting it turns "a caller tried to enumerate through a view" into an `AttributeError` instead of a cross-namespace credential leak; enumeration only ever happens through `scoped_list_keys`, which additionally raises `TypeError` if handed the physical store directly instead of a view.
- **`redirect/linkgate/keys.go`** mirrors the Go side: `LinksPrefix`/`AnalyticsPrefix` constants (deliberately no `users:` one — the redirect component has no business constructing a users key) and `LinkKey`/`CountShardKey`/`EventKey` builders. It must stay byte-identical to `kvprefix.STORE_PREFIXES`, or the API writes links the redirect path can't find with no error anywhere — `api/tests/test_kvprefix.py` reads `keys.go` from the Python test suite and pins the two sides' equality as a CI-time guard rather than a runtime one.
- **`keys.go` also holds `CountShards = 64`, which is a second cross-language value with the same pinning obligation** — it must stay equal to `api/analytics.py`'s `COUNT_SHARDS`, and the same test file pins it by the same technique. It is not a prefix, but it fails the same way: silently, at runtime, with no error anywhere. **RAISE ONLY, NEVER LOWER** — a reader lower than the writer drops every click recorded into a higher shard. See "Click counting is sharded across 64 keys" under Analytics for why 64, and note that `gui/links/detail.html`'s accuracy caveat quotes a rate figure derived from it.
- The `api`/`gui-pages`/redirect suites cover this mechanism directly: `api/tests/test_kvprefix.py` (the view's four-method surface, the non-overlap invariant, the cross-language guard) and `api/tests/test_store_isolation.py` (the four cross-namespace hazards: a links-only backup can't leak a users hash, a links-only restore prunes only `links:` keys, a pre-consolidation backup fixture restores unchanged, and the consistency check never sees `analytics:` keys sharing the same physical store).

## Security response headers

Every response from `redirect`, `api`, and `gui-pages` sets `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, and `Strict-Transport-Security`. Each component's CSP is scoped to what it actually serves:

- `gui-pages` (the real HTML pages): `default-src 'self'` plus `script-src 'self'` and `style-src 'self'` — **no `'unsafe-inline'`.** Every page's script and style live in a sibling `.js`/`.css` file served by the `gui` component, so no served page needs an inline `<script>`/`<style>`/`style="…"` allowed. `gui-pages/tests/test_no_inline_code.py` enforces that — a CSP violation fails a page silently in a browser rather than failing a test. Hiding uses the native `hidden` attribute plus `theme.css`'s `[hidden] { display: none !important; }` (`!important` is load-bearing — Pico sets `display` on several elements this app hides). `img-src` includes `data:` because Pico CSS renders several UI affordances as inline `data:image/svg+xml` background-images. **This component's two styled error pages keep this exact header set unchanged**, so they load `/theme-init.js` and follow OS/stored theme, unlike `redirect`'s error pages below which always render light — deliberate divergence, do not "harmonise" the two.
- `api` (pure JSON): `default-src 'none'` — nothing it returns should ever be rendered, executed, or framed.
- `redirect`'s password-prompt page: the strictest policy in the app — `default-src 'none'`, `script-src 'none'` (loads no script at all — the page where a visitor types a credential always renders light rather than following OS theme), `style-src 'self'`. Links `/vendor/pico.min.css`/`/theme.css` (already exact `gui` routes) and uses `theme.css`'s `.form-error` — the last inline style attribute in the app, retired with this page.
  - **`form-action` must list `https:`/`http:`, not just `'self'`.** A correct password answers the POST with a 302 to the link's target, and Chrome applies `form-action` to that redirect too. With a bare `'self'` the browser silently blocked the navigation — every password-protected link was a dead end in a real browser while working under `curl`. The two schemes mirror exactly what `api/links.py`'s target-URL validation accepts, so `javascript:`/`data:` form targets stay blocked.
- **`redirect`'s three error pages** (404/500/503) — styled replacements for what used to be a raw `net/http` string, same status/headers. Static, data-free `go:embed`ed files rendered through one shared `errorPageCSP`: `default-src 'none'; script-src 'none'; style-src 'self'; base-uri 'self'; form-action 'none'; frame-ancestors 'none'`. `form-action` is `'none'` here (not the prompt's scheme list) since these pages have no form. **The 404 is the one page here with a security property to protect**: byte-identical for an absent slug, a disabled link and an out-of-window one (see "Security tradeoffs" below), which is why it takes no data at all. All four public `redirect`-served pages carry a bare `<title>` with no product-name suffix — they render under whatever branded domain a link was shared on (see "Multi-domain display"), so the product name would be off-brand infrastructure disclosure there.

The `gui` component (the static asset routes above) gets none of these — headers on a `.js`/`.css` subresource response don't provide any real protection the navigated-document headers don't already cover.

**`/internal/kv-explorer/...` sits outside every guarantee in this section.** It is a separate third-party component that sets its own headers, so none of the above applies to it, and its UI contains an inline `<script>` and `<style>` block and loads jQuery, Bootstrap, Popper, Font Awesome and Google Fonts from external CDNs — the opposite of the vendored, `default-src 'self'` posture everything else holds. `gui-pages/tests/test_no_inline_code.py` **deliberately does not cover it**: the file is not ours to fix, so a guard over it could only ever fail, and failing on an upstream binary's markup would be noise rather than signal. This is acceptable solely because the route exists only in a local `spin-dev.toml` and is unreachable in any deployed manifest. If that ever changes, this is the paragraph that has to change with it.

### Redirect caching: `Cache-Control: no-store` and the 302-not-301/308 requirement

Every `redirect` response (302s, 404s, and the password prompt alike) now carries `Cache-Control: no-store`, set once in `setSecurityHeaders` (`redirect/main.go`) rather than at the three individual redirect call sites, so it covers `http.NotFound` too — a cached "not yet active" 404 would mean a not-yet-started link never starts working when its window opens.

**302 is a hard requirement for `/r/{slug}`; 301 and 308 are forbidden.** Akamai edge servers do not cache HTTP 302 (`Found`) or 307 (`Temporary Redirect`) responses by default, but they **do** cache 301 (`Moved Permanently`) and 308 (`Permanent Redirect`) by default (`techdocs.akamai.com/property-mgr/docs/cache-http-redirects`). `redirect/main.go`'s three redirect sites all use `http.StatusFound` (302) today — do not "simplify" this to a 301 for a URL that never changes; that single-line change would make Akamai start caching the response at the edge.

**The `no-store` header is defence-in-depth, not the actual control.** Akamai edge servers do **not** honour origin `Cache-Control`/`Expires` by default, so this header protects against browsers and intermediate proxies — the 302 status code is what actually keeps Akamai's own edge from caching the response. A cached redirect would silently break every one of: the `status` check (a disabled link keeps redirecting), the `[start_at, end_at)` window (a link keeps redirecting past `end_at`), deletion (a deleted slug keeps resolving), repointing (a repointed link keeps serving its old destination), and the destination-policy remediation path (a bulk-Disabled violator keeps resolving instead of 404ing).

**Akamai Functions itself publishes no caching documentation at all, but the behaviour is confirmed measured against a live deployment: a `*.fwf.app` app does inherit the "302 not cached by default" behaviour.** Twenty requests to one active `/r/{slug}` returned twenty distinct `302`s with no `Age`/`X-Cache` header and consistent ~130-165ms origin service time (a cached edge response would return in single-digit ms), and click totals advanced correctly across them, confirming both KV writes ran on every request. The same held for `404`s against a nonexistent slug — important because a cached "not yet active" 404 would mean a scheduled link never starts working.

**Measured directly via `X-SS-Debug` tracing on a deployed build: KV is ~97% of handler time on Akamai, against 46% locally.** The per-operation split:

| operation | Akamai | local | ratio |
|---|---|---|---|
| `open` | ~154 µs | 12–33 µs | ~7× |
| `exists` | 21.7 ms | 13–18 µs | ~1,400× |
| `get` | 21.2 ms | 5–9 µs | ~2,900× |
| `set` | 26.1 ms | 5–12 µs | ~3,000× |

**Treat absolute milliseconds as a moving target, not a constant** — the same 7 operations were measured at both ~117ms and ~39ms total ten minutes apart on the same day, a 3× regime swing. Only ratios within a single measurement window are trustworthy; quote proportions, not milliseconds.

**The cost is per data operation, not per store handle** — which inverted two conclusions drawn from local measurement. Removing `recordAnalytics`'s second `kv.Open` looked like an 8–20% local win and is ~0.2% on Akamai (not worth doing). Dropping the `Exists` probe from `lookupLink` measured as a genuine ~13.5% win and was done. **`recordAnalytics` is now the dominant cost, ~78% of the redirect's KV time** (the `analytics:count` write is the single slowest operation in every trace). It runs *after* `http.Redirect` (`sendRedirectThenRecord` sets the response, then records) — but under WASI the host may not flush the response until the handler returns, so this ordering is not established to help visitor-perceived latency; it was validated only for click-accuracy reasons (an A/B on write ordering showed no difference, 85 vs 86 of 100). Don't claim a latency benefit from it without a dedicated measurement. See `TASKS.md` Future work on why "just make it async" isn't automatically available under WASI.

### The `/r/{slug}` status contract: 404 is for product states, 5xx is for faults

`lookupLink` used to collapse a KV read failure, a genuinely absent key, and an unparseable record into one `false`, which every caller answered with `http.NotFound`. Measured under load: read-path saturation was being reported to a visitor as "this link does not exist" (43% wrongly-404 at 1,292 rps in one run), indistinguishable from a genuinely dead campaign URL.

**The organising principle: 404 is for product states — absent, disabled, out-of-window. 5xx is for faults — 503 transient, 500 permanent-data. A fault must never be dressed up as a product state.**

| condition | status | leaks about the link |
|---|---|---|
| active, in window, no password | 302 | destination |
| active, in window, password set | 200 prompt | that it is protected (already disclosed) |
| key absent | 404 | nothing |
| `status != "active"` | 404 | nothing |
| outside `[start_at, end_at)` | 404 | nothing |
| `Get` returned an error | **503** + `Retry-After: 2` | nothing — emitted from a state of ignorance |
| `kv.Open` returned an error | **503** + `Retry-After: 2` | nothing |
| record present, `ParseLink` failed | **500** | that the slug has a record |

`linkgate.Resolve` (`redirect/linkgate/resolve.go`) makes this decision and returns a `Disposition`; both `handleRedirectGet` and `handleRedirectPost` in `redirect/main.go` switch on it and are structurally identical except for the `DispositionPrompt` arm. Absent, disabled and out-of-window stay deliberately indistinguishable from each other (see "Security tradeoffs" below) — a probing-resistance property, not an oversight, and `redirect/linkgate/resolve_test.go` pins that the three produce *equal* values, not merely three values that each happen to map to 404. Every `Get`/`Open` error is treated identically regardless of cause (no variant check, no string match) — the SDK exposes no typed error to match on, and a substring match would be control flow a vendor wording change could silently defeat (see "Write-throttle resilience" below for the same rule on the write side). `redirect` still has no retry anywhere: a saturated read cap needs the client to back off, not the origin to spend more of the exact resource that is exhausted.

**Caching favours the fix.** Akamai's Property Manager docs (`techdocs.akamai.com/property-mgr/docs/cache-http-error-responses`, fetched 2026-08-19) list 404 as cached for 10 seconds by default; 500, 502, 503 and 504 are **not** cached unless the "Cache HTTP Error Responses" behaviour is explicitly enabled. The statuses this fix introduces are strictly safer to cache-poison than the 404 they replace. No redirect status changes, so the 302-not-301/308 rule above is untouched, and `Cache-Control: no-store` (set once in `setSecurityHeaders`) continues to cover both new statuses with no new code.

**Hot-path cost: zero.** `Resolve` performs the same single `Get` `lookupLink` did; a successful redirect stays at 5 KV operations and a miss stays at 2.

**Since `docs/plans/redirect-error-pages.md`, all three of 404/500/503 render a styled HTML page (`redirect/error-404.html`/`error-500.html`/`error-503.html` via `redirect/errorpage.go`'s `writeErrorPage`) instead of a raw `net/http` string — no status code and no header changed to do it.** `Retry-After: 2` still lands before the body is written in `serviceUnavailable`, and `Content-Length` is computed from the same `[]byte` that is written so it cannot drift. The 404's copy is part of the indistinguishability property in the table above, not incidental wording: the template takes no data at all, so an absent slug, a disabled link and an out-of-window one are byte-identical by construction, and `gui-pages/tests/test_no_inline_code.py` pins the copy itself against a forbidden-word list (`expire`, `disabled`, `schedul`, …) since no Go test can reach a rendered byte. See "Security response headers" above for the shared CSP these pages use.

**Settled understanding, after two rounds of measurement that initially pointed the wrong way:** a naive load sweep after this fix shipped showed zero wrongly-404s even at rates implying far more reads/second than Akamai's documented 1,000 RPS cap, which briefly put the whole read-cap diagnosis in doubt — because no `503`s were observed either, and it looked like the origin just wasn't failing. **Adding origin-side failure logging (`ev=kv_fail`) overturned that:** the same load shapes showed 15–32% of redirect link reads genuinely failing at the origin, each one correctly running the `DispositionUnavailable` arm and returning `503` — but **the Akamai edge retries a 5xx and serves the retry**, so not one of those failures ever reached a client. Three conclusions that survive:

1. **The read cap binds roughly where the original arithmetic said it did.** The earlier "ran clean at 2.2–2.6× the cap" reading was an absence of instrumentation, not an absence of failures.
2. **Converting 404 → 503 was a functional repair, not a cosmetic one.** A 404 is a valid final answer, so the edge passes it through (hence the pre-fix wrongly-404s); a 503 is retryable, so the edge absorbs it and the visitor gets the correct redirect one retry later instead of "this campaign link is dead."
3. **A clean client-side status distribution is not evidence the origin is healthy on a platform that retries.** Any future capacity claim about this app must rest on origin-side failure counts (`ev=kv_fail`), never on response codes — a controlled sweep found the edge absorbing a measured 50.9% origin failure rate with every client still getting a correct `302`. Failure onset is duration-dependent (a burst allowance, not a flat per-second cap) and tracks the redirect path's own arrival rate rather than total app-wide read demand — concurrent load elsewhere in the app was observed making the redirect path *healthier*, not worse. Alerting on `ev=kv_fail` naively would page on a condition the platform is successfully handling; see TASKS.md's "The edge's absorption cliff was NOT found" for the open question.

**Also settled: Akamai emits TWO throttle messages** — `key-value error: rate limit exceeded` and `too many requests` — both under `Err/Error_Other`, so `api/kvretry.py`'s `classify_write_error` substring match must check both, and the WIT variant alone cannot identify throttling at all.

## Theming

`gui/` ships a light theme and a custom dark theme (derived from the same navy identity, not Pico's stock dark palette), auto-following the OS by default with a manual override persisted client-side. See `DESIGN.md`'s Colors section for the palette and its measured contrast ratios; this section covers the mechanism.

**Three blocks in `gui/theme.css`, in this order:**

1. **Theme-independent** (`:root:not([data-theme="dark"]), :root[data-theme="dark"]`) — density/type-scale tokens (`--pico-font-size`, `--pico-line-height`, `--pico-spacing`, both `--pico-form-element-spacing-*`) plus the raw navy ramp (`--ss-navy-950`, `--ss-navy-800`). These must never live in a theme-specific block: a theme block's selector stops matching the instant the *other* theme's `data-theme` is set, so a density token placed there would silently hand that property back to Pico's own viewport-scaling defaults the moment the app switched themes.
2. **Light** (`:root:not([data-theme="dark"])`) — **this selector must stay exactly this, never a plain `:root`.** Pico's own light block uses the same selector, so matching it exactly makes this an equal-specificity tie that load order (this file loads after `pico.min.css`) breaks in this file's favor. A plain `:root` would silently lose that tie regardless of load order.
3. **Dark** (`:root[data-theme="dark"]`) — new. `(0,2,0)` specificity beats Pico's own bare `[data-theme=dark]` block (`(0,1,0)`) by specificity, not load order, which is strictly more robust than the light block's tie-plus-load-order arrangement.

**`gui/theme-init.js`** is a small (~90-line) script loaded render-blocking as the first real element of `<head>`, before any stylesheet link, on every page except `index.html` (a redirect stub with no stylesheet, which gets `<meta name="color-scheme" content="light dark">` instead). It reads the `ss-theme` `localStorage` key — one of three values, `"system"` (the default), `"light"`, or `"dark"` — and **always sets `document.documentElement.dataset.theme` to a literal `"light"` or `"dark"`, never `"system"` and never left unset**. Setting that attribute at all, to any value, is what disables Pico's own `@media (prefers-color-scheme: dark)` block entirely (that block is scoped to `:root:not([data-theme])`, which stops matching the instant any `data-theme` is present) — so once `theme-init.js` has run once, the app's own dark block is the only thing driving dark mode, not Pico's. It exposes `window.ssTheme` (`KEY`, `get()`, `set(mode)`, `resolve()`, `apply()`) as the one source of truth for the storage key and the resolution rule; `gui/app.js`'s nav theme control calls these rather than reimplementing them.

**No-JS fallback:** if `theme-init.js` never runs at all (blocked, 404, JS disabled), no `data-theme` attribute is ever set, and the app falls back to whatever `theme.css`'s unconditional light-block declarations render — light, regardless of OS preference. This is why those declarations must never be deleted even though they're no longer the sole defense against Pico's dark-mode leak (see `DESIGN.md`'s Inputs/Fields note for the full history).

**Two Pico dark-block traps**, both must be re-fixed in `theme.css`'s dark block independently of the light block's existing fixes: Pico's own `[data-theme=dark]` block (1) re-enables `--pico-card-box-shadow`/`--pico-dropdown-box-shadow` (both default to a real multi-layer drop shadow, violating the No-Shadow Rule) and (2) sets `--pico-card-border-color` equal to the card background (an invisible border, in a system whose depth comes from a hairline border plus background contrast with no shadow allowed).

**A guard worth knowing about, in `gui/app.js`:** `initHeader()` checks `window.ssTheme` exists before calling into it, because `theme-init.js` is served on its own separate `spin.toml` route (`/theme-init.js`) rather than being bundled into `app.js`. If that route ever 404s, an unguarded call would throw inside `initHeader()`'s async body — a promise no page `.catch()`s — which would silently kill the *entire* page's init chain (nav, identity chip, links table, everything), not just the theme control. The guard turns that failure mode into "the theme control doesn't render and the app stays light" instead of "the whole page is dead."

## Planner / builder subagents

Non-trivial work in this repo goes through two committed subagents in `.claude/agents/`:

- **`planner`** (opus) — explores the code, weighs trade-offs, and writes a plan to `docs/plans/<feature>.md` (kebab-case, descriptive — never a random slug). It also appends the unchecked `- [ ] ... — file(s): ... — done when: ...` lines to `TASKS.md` under a new descriptively-named section at the end of the file, and records rejected alternatives under `TASKS.md`'s "Considered and rejected". It never writes implementation code — its only writable paths are `docs/plans/`, its scratch file, and appends to `TASKS.md`.
- **`builder`** (sonnet) — reads the plan file first, implements it following existing conventions, ticks each `TASKS.md` checkbox immediately after finishing that task, and verifies with the real test suites plus a live `spin up` run for user-visible changes. It stops and reports back rather than silently deviating when the plan turns out to be wrong.

Typical flow: invoke `planner` with the requirement and the relevant file paths → review the plan it writes → invoke `builder` with that plan's path. Skip both for one-line fixes; the overhead isn't worth it. When delegating, give concrete references — file paths, the existing code the change interacts with, the specific requirement and non-goals — not "implement the plan"; anything left unstated gets filled in confidently and possibly wrong.

**A `builder` run that involves `spin up --build` may return early**, mid-verification, with the code already written — observed once during the CSP work, where it returned the bare text "Waiting for the spin build to finish." **Resume it rather than re-running the task**: its transcript is intact, so a follow-up message picks up where it stopped, while a fresh invocation redoes work that is already on disk. Worth saying so in the delegation prompt too. Whatever it produces, verify the diff yourself before committing — check that it touched only the files its task line names, and that `git diff --numstat TASKS.md` shows only the checkbox lines it was supposed to tick.

Plans live in `docs/plans/` and are committed. Multi-round work uses `docs/plans/<feature>-scratch.md` (gitignored via `docs/plans/*-scratch.md`) as an append-only handoff note — one `## Round <n> — <agent> — <date>` heading per round, with Done / Open questions / Next. It is a handoff note, not either agent's memory: anything durable gets promoted into the plan file, `TASKS.md`, or here.

## Commands

Build and run the whole app (all four components) locally:

```bash
SPIN_VARIABLE_ADMIN_BOOTSTRAP_PASSWORD=<some-password> spin up --build --runtime-config-file runtime-config.toml
```

This invokes each component's `[component.<name>.build]` command from `spin.toml` and then serves all routes together. Requires the [Spin CLI](https://spinframework.dev) to be installed.

**`--runtime-config-file runtime-config.toml` is optional locally, and it is NOT a no-op — it decides whether your KV data survives a restart.** Spin auto-provisions the `"default"` store with no runtime config at all, backed by a sqlite file that persists; passing this file instead selects `type = "spin"` with no `path`, which on Spin 4.0.2 is a **temporary in-memory store wiped on every restart** (`runtime-config.toml`'s own "sqlite-backed" comment is wrong). **Drop the flag if you want your local links and users to still be there after a restart; pass it (or use `dev/kv-explorer-up.sh`, which always passes it) if you want a clean store every run.** It has no effect on an Akamai Functions deployment, which ignores runtime configuration entirely. `admin_bootstrap_password` is a required secret variable (seeds the first admin user on a fresh KV store) and has no default.

When testing the `gui` in a real browser over plain `http://localhost`, also set `SPIN_VARIABLE_COOKIE_SECURE=false` — the session cookie's `Secure` flag otherwise stops the browser from storing/sending it over non-HTTPS. Leave `cookie_secure` at its default `true` for any HTTPS deployment.

**Editing any file under `gui/` requires restarting `spin up` — the running server does NOT pick it up.** `spin_static_fs` serves a snapshot of the mapped directory taken at startup, so a `.js`/`.css` edit is invisible until the process restarts — a genuinely correct fix keeps reproducing the *old* error in the browser, which reads as "my fix is wrong" rather than "the server is stale." **When a GUI change appears not to work, diff the served asset against the file on disk before doubting the change** (`curl localhost:3000/<asset>`) — a browser hard-reload does not help, since the staleness is server-side. This doesn't apply to `gui-pages`, `api` or `redirect`, which are rebuilt by `--build`.

To run the same app **plus the local-only KV explorer** at `/internal/kv-explorer/` (see the `kv-explorer` bullet under Architecture for what it can and cannot reach):

```bash
SPIN_VARIABLE_ADMIN_BOOTSTRAP_PASSWORD=<some-password> \
SPIN_VARIABLE_KV_EXPLORER_PASSWORD=<explorer-password> \
SPIN_VARIABLE_COOKIE_SECURE=false \

```

The script regenerates a gitignored `spin-dev.toml` from `spin.toml` + `dev/kv-explorer.toml` and runs `spin up -f spin-dev.toml`, forwarding any extra arguments. Edit `spin.toml` or `dev/kv-explorer.toml` — never `spin-dev.toml`, which every run overwrites. The explorer's basic-auth username defaults to `kv`.

Per-component builds (equivalent to what `spin up --build` runs), if you need to build just one component while iterating:

It's covered by manual `spin up --build --runtime-config-file runtime-config.toml` + curl/browser smoke testing instead. `api/auth.py`, `links.py`, `qr.py`, `responses.py`, and `gui-pages/routing.py` have zero `spin_sdk` imports and are fully unit-tested under `uv run pytest` (`api/` also uses an in-memory `FakeStore`, `api/tests/fakes.py`, standing in for the real KV store — `gui-pages` needs no such fake, since `routing.py`'s `build_response` takes a `read_file` callable as a parameter instead of touching the filesystem directly). New pure logic should follow this same pattern: take `store`/`request`/`read_file`-style dependencies as plain parameters, and (in `api/`) use `responses.Request`/`responses.Response` (not `spin_sdk.http`'s) — these are local dataclasses that behave identically at runtime (the real `Handler.handle()` only ever does duck-typed attribute access, never an `isinstance` check) while keeping the module host-importable.

## Time-windowed links

A link record's `start_at`/`end_at` fields (ISO8601 UTC, e.g. `2026-01-01T00:00:00Z`) make it active only in `[start_at, end_at)` — inclusive start, exclusive end. Either or both may be `null` (unbounded on that side). A link outside its window returns a plain `404`, identical to a nonexistent slug — deliberately no distinct "not yet active"/"expired" messaging, so a probing visitor can't learn a link's existence or schedule. The window is re-checked from a fresh KV fetch on every `/r/{slug}` request (`redirect/linkgate.IsWithinWindow`), the same "never cache" principle the password gate already uses — so editing a link's window via `PATCH /api/links/{slug}` takes effect on the very next request.

## Analytics

Every successful redirect updates one key in the `analytics` KV store, written by `redirect` (`recordClickCount` in `main.go`, pure logic in `redirect/linkgate/analytics.go`) and read by `GET /api/links/{slug}/analytics` (`api/analytics.py`):

- `count:<slug>:<shard>` — one JSON blob `{total, days: {"YYYY-MM-DD": n, ...}}`, read-modified-written on every click (one KV round trip), with `days` trimmed to `analytics_day_retention_days` (default 90) entries. **The counter is sharded across `linkgate.CountShards` (64) keys** — see "Click counting is sharded across 64 keys" below.

**`events:<slug>:<slot>` no longer exists as a live feature.** Since `docs/plans/drop-events-write.md` (2026-08-18), `redirect` no longer writes it at all — see "The recent-events ring buffer" below, now retired. Leftover `events:` keys from before that change still exist on real stores and are harmless; `api/analytics.py`'s `parse_analytics_key` keeps recognising the shape (so `analyticsorphans.classify_analytics_keys` doesn't misclassify them as `unrecognized_key`) and the Store maintenance page reports the residual as `totals.obsolete_event_keys`.

### The Clicks column's read cost scales with traffic, without bound

**`GET /api/analytics/click-totals` reads every existing `count:` key for every visible slug, so its read count grows with traffic toward 64 per link.** `api/analytics.py`'s docstring calls this "proportional to real traffic rather than to links × shard count" — true, but **not a bound**: as a link gets busy, shards-touched → `COUNT_SHARDS`, and the endpoint converges on the full 65×N shape it was designed to avoid. Measured directly (the `get` count in an `X-SS-Debug` trace **is** Σ shards-touched): at 100 clicks/link across 20 seeded links, wall time was 792 ms — a busy 100-link × 200-click dashboard load models to ~6,126 reads, well past what a naive per-key fan-out could sustain against the app-wide read cap. **This is now substantially mitigated**: `handle_click_totals` uses `scoped_get_many` (see "Parallel KV reads"), which collapses that fan-out into a handful of chunked host calls that don't bill per-key against the read cap — but the underlying key count still grows unboundedly with traffic, so re-measure if it's ever a concern again. **Measuring this endpoint requires seeding actual clicks, not just links** — a run that seeds unclicked links creates no count keys and reports a false all-clear.

The rejected denormalised `analytics:total:<slug>` (one extra write per click, avoiding the whole read-side fan-out) deserves re-costing against real numbers if this becomes a problem again — it was rejected early for "adding a third KV write to every click" without weighing it against the read-side cost this section documents.

### Click counting is sharded across 64 keys

The write path (`recordClickCount` in `redirect/main.go`) picks a shard per click and read-modify-writes `analytics:count:<slug>:<shard>`. The read path (`api/analytics.py`'s `handle_analytics`) sums **65** keys: all 64 shards plus the legacy unsharded `count:<slug>`.

- **The shard is chosen from entropy, not from the slug.** `linkgate.ShardFor(clickEntropy(now), linkgate.CountShards)`, where `clickEntropy` XORs `math/rand/v2`'s `rand.Uint64()` with `now.UnixNano()`. Two sources deliberately: the RNG varies within one Wasm instance even if its seed does not, and the clock varies across instances even if WASI's `random_get` is stubbed and every instance seeds identically. A slug-derived shard would defeat the entire point — every click on one hot link would land on the same key.
- **`ShardFor` runs the value through a splitmix64 finalizer (`mix64`) before the modulo, and must not be "simplified" into `EventSlot`'s single multiply-then-reduce.** That is not a style preference: a single multiply is *linear over the modulus*, so clicks a fixed interval apart advance by a constant stride and reach only one additive cycle of the ring. Substituting it puts all 100,000 draws of the timestamp-distribution test into shard 0. `redirect/linkgate/analytics_test.go` pins the timestamp case specifically, and it is the load-bearing test in that file.
- **`CountShards` (Go) and `COUNT_SHARDS` (Python) must stay equal, and the rule is RAISE ONLY, NEVER LOWER.** The asymmetry is what makes it dangerous: a reader *higher* than the writer merely reads empty keys, but a reader *lower* than the writer silently drops every click recorded into a higher shard, with no error anywhere. `api/tests/test_kvprefix.py` pins the equality by reading `keys.go` from the Python suite, the same cross-language guard the key prefixes use.
- **No migration was needed and none should ever be written.** Nothing writes the legacy `count:<slug>` key any more, and the reader sums it in alongside the shards, so pre-sharding click history keeps showing up in the total forever. A slug can never contain a colon (`CUSTOM_SLUG_PATTERN` is `^[A-Za-z0-9_-]{3,32}$`), so a shard key can never collide with the legacy key.
- **A corrupt shard costs only its own clicks.** `_merge_counts` skips a blob that is absent, empty, non-JSON or the wrong shape rather than raising — one bad shard must never blank a link's whole history.
- **The merged `days` map can exceed the retention window, and that is accepted.** Each shard trims its own map independently, so a low-traffic link whose shards collected clicks on different days unions to more than `analytics_day_retention_days` entries. The data is correct and at most a few kilobytes; trimming at read time would mean declaring the retention variable for the `api` component purely to shorten a response.

**Two independent mechanisms lose clicks on Akamai, and sharding addresses exactly one of them.** Conflating them produced a wrong conclusion once, so keep them apart:

| | **M1 — per-key contention** | **M2 — the app-wide write cap** |
|---|---|---|
| cause | `count` is a read-modify-write and Spin's KV has no compare-and-swap, so overlapping clicks *on one key* lose increments | Akamai allows 50 KV writes/second per app; a recorded click costs one write (one count shard — the events-slot write was retired 2026-08-18) |
| scope | one hot link | the whole service, all links combined |
| threshold | measured 25% loss at 9.4 clicks/s on a single slug (fixed by sharding) | ~50 clicks/second app-wide (sharding cannot touch this) |
| fixed by sharding? | **yes** | **no** — only writing less per click would |

Measured proof that these are separate: one hot slug at 9.4 req/s lost 25% while 16 slugs at the identical app-wide write load lost 0% — same writes/second, one hot key versus sixteen.

**`CountShards` is 64**, raised from an initial 16 after the 16-shard build measurably missed its accuracy target (concurrency-driven residual loss, not per-shard rate — collision probability grows roughly as k²/2S in in-flight requests, which quadrupling the shards removed). Click totals are essentially exact below ~10 clicks/second app-wide, drift a few percent by ~20/s, and remain lossy above that (M2). **Raising `CountShards` further remains the lever if ever needed** — RAISE ONLY, NEVER LOWER, cross-language guard (`api/tests/test_kvprefix.py` pins Go/Python equality), no migration needed. The 16→64 raise was paired with gathered reads (see "Parallel KV reads") so the larger shard count didn't cost proportional wall time — re-measure rather than extrapolate if shards are ever raised again. **A single link above ~50 clicks/second is still lossy and sharding will not save it** — that's M2, and only fewer writes per click addresses it.

**Any measurement of counter accuracy must stay under ~50 requests/second aggregate, or it measures M2 rather than M1.** `dev/click-load.sh` prints the implied write rate and warns at 50; use it rather than hand-rolled `curl` loops — a gating probe for this design was once misread as a clean failure purely because it ran over the cap.

**The recent-events ring buffer** (a "recently clicked" sample the dashboard showed) was retired entirely on 2026-08-18 (`docs/plans/drop-events-write.md`) — it was a second write per click that only doubled the write-cap pressure (M2) for a feature nobody read from reliably anyway. Removing it roughly doubled the app-wide click ceiling. Its one surviving legacy: `ShardFor` (which the counter still calls) runs its input through a splitmix64 finalizer rather than a single multiply-then-reduce, because a single multiply is *linear over the modulus* — clicks a fixed interval apart would advance by a constant stride and reach only one additive cycle of the ring (in the ring buffer's case, this pinned reachable slots to one parity, permanently). **Do not "simplify" `ShardFor` back into a multiply** — `TestShardFor_DistributesUniformlyOverTimestampShapedInput` in `redirect/linkgate/analytics_test.go` is the load-bearing, mutation-verified pin on this.

## Bulk link management

`POST /api/links/bulk` (bulk create) and `POST /api/links/bulk-action` (bulk delete/enable/disable), both in `api/bulk.py` and routed from `api/app.py` on exact-path match above the existing `/api/links/...` branches. **Validation is all-or-nothing**: any invalid row/slug in a submission means nothing is written and every problem is reported, never a partial result — with no atomic KV operations available (see "Security tradeoffs" below), a partial-success design would leave the user needing to diff what they submitted against what exists just to know what to retry. **Execution, since "Write-throttle resilience" below, is best-effort and fully reported** rather than all-or-nothing: a throttled write mid-run no longer means nothing landed, it means the response says exactly what did.

- **`POST /api/links/bulk`** takes raw pasted/uploaded text plus batch-level `password`/`start_at`/`end_at` (applied to every link created in that submission, not per-row) and parses it with `parse_bulk_text`/validates it with `validate_bulk_rows`. Text format, briefly: one row per line, `slug,destination` or `slug<TAB>destination` (first delimiter wins; commas after the first stay in the destination); a bare URL line has no slug (blank = auto-generate); `#` and blank lines are skipped; a leading UTF-8 BOM is stripped; a first row whose fields match a small `HEADER_WORDS` set is dropped as a header. Slugs are case-sensitive. Full spec and worked examples are in `docs/plans/bulk-link-management.md`.
- **`POST /api/links/bulk-action`** takes `{"slugs": [...], "action": "delete"|"enable"|"disable"|"tag"|"untag"|"reassign"|"repoint"|"schedule"}`. A row-level `.status-btn` toggle in `gui/dashboard.js` also `PATCH`es `{status}` for a single slug — the bulk actions remain the way to change many at once. **There is no per-action write dispatch any more.** `ACTION_SPECS` maps each action name to an `ActionSpec` (its planner, whether the per-row `can_edit` check applies, its required permission, its response echo fields), and `BULK_ACTIONS` is **derived** from it (`frozenset(ACTION_SPECS)`). A single loop, `_apply_mutations`, performs every bulk write and takes no `action` parameter at all, over a list of `PlannedMutation`s computed by a pure, KV-free planning pass. So a name cannot reach the endpoint without a planner, and cannot fall into another action's write loop — the hazard the older `else: # delete` catch-all created. The `unhandled_action` 500 survives only as a guard against `BULK_ACTIONS` and `ACTION_SPECS` ever being decoupled again. Plan: `docs/plans/unify-bulk-write-loops.md`.
- **`repoint`** (`{"target_url": "https://..."}`) rewrites every selected record's `target_url`, validated through the same `links.target_url_error`/`urlpolicy.evaluate` choke point as the other three authoring paths (see "Destination URL policy" below — this makes it the fourth) — both checks, in that order, or a `links.edit_all` holder could bulk-launder 50 links around the admin's own policy. Unlike `reassign`, it does **not** skip the per-row `can_edit` check. The policy `get` is paid only by this action.
- **`schedule`** (`{"start_at": ..., "end_at": ...}`, either/both) merges each side against the record's *existing* value — key presence decides, exactly like `PATCH /api/links/{slug}`: an omitted key leaves that side untouched, an explicit `null` clears it. The `start >= end` check runs per link against the merged pair (not the raw payload), since one side may come from the stored record; a conflict appends a per-row `invalid_window_range` error carrying both merged dates and blocks the **entire** batch — never a partial write from a validation failure, the same all-or-nothing convention every other bulk error path holds. The write loop consumes the exact merged values the validation loop computed, never recomputing them.
- **Caps: `MAX_BULK_ROWS = 50` rows/slugs per request, `MAX_BULK_BODY_BYTES = 262144` (256 KB) per request body.** Plain module constants in `api/bulk.py`, not Spin variables — one function in one component reads each. Both error responses carry the limit and (for `too_many_rows`) the actual `row_count`. **Raising `MAX_BULK_ROWS` needs real timing evidence from a full-cap submission** — it was deliberately dropped from an original 200 to keep a submission's per-request work (~100 KV ops) comfortably bounded.
- **A record's existence is the only truth — there is no index left to order writes around.** Since "Derived link indexes" (above) removed both link indexes, an interrupted bulk create or delete simply leaves exactly the records that landed, all correctly listed, since listing is derived from the records themselves.

## Multi-domain display

The app can be reachable at more than one base domain (e.g. a branded `go.example.com` alongside `localhost:3000` in dev), and the GUI lets a viewer pick which one every short URL, Copy button, CSV column and QR code is built from. This is display-only: **there is no per-link `domain` field, and nothing enforces a link to a domain.** `redirect/main.go` never reads the `Host` header — resolution is purely `slug:{slug}` → KV → 302 — so every link already works on every domain that points at this deployment, regardless of which one a link was created or shared under. Domains are a **viewer preference**, in the same category as the light/dark theme: chosen in the persistent nav, persisted client-side in `localStorage` (`ss-domain`), and read fresh at the moment each URL is built (`shortUrlFor(slug)` in `gui/app.js`) rather than stored anywhere server-side.

- **`public_base_urls`** (plural) is a comma-separated Spin variable, e.g. `SPIN_VARIABLE_PUBLIC_BASE_URLS="https://go.example.com,http://localhost:3000"`. Each entry is a bare `scheme://host[:port]` — no path, query or fragment — normalized (lowercased, no trailing slash) and de-duplicated by `api/domains.py`. **Order is meaningful: the first entry is the default** — the nav selector's initial choice for a viewer who hasn't chosen one, and what the QR endpoint uses when no `?base=` is supplied.
- **This variable replaced the old singular `public_base_url`, which no longer exists anywhere in `spin.toml`.** Spin's env-var provider looks up declared variables by name, so a deployment that upgrades without renaming its env var (`SPIN_VARIABLE_PUBLIC_BASE_URL` → `SPIN_VARIABLE_PUBLIC_BASE_URLS`) gets the default `http://localhost:3000` **silently** — the stale variable is simply never read, with no warning anywhere in the server log. Confirmed live. Check this first if a deployed app's QR codes or copied links unexpectedly point at `localhost` after an upgrade.
- **`assigned_domains`**, an optional list on each user record, restricts which of the configured domains that user's nav selector offers. Absent or `[]` means **unrestricted** (every configured domain), not "no domains" — no existing user record needs a backfill. It is a convenience guardrail against handing out an off-brand URL by accident, **not a security control**: it is deliberately not in `auth.py`'s `KNOWN_PERMISSIONS` (a small, fixed, hardcoded vocabulary that would lose its "reject anything outside this set" property if permission strings were generated per configured domain), and it gates nothing server-side — a user can still obtain a link or QR code for any configured domain by hand-crafting a request. The admin Users page manages it via `gui/admin/users.html`/`users.js`.
- **`GET /api/links/{slug}/qr`'s `?base=` parameter is allowlist-validated against `public_base_urls`, never trusted directly.** An endpoint that encoded an arbitrary client-supplied base URL into a QR code would be a QR-poisoning vector — the image is printed and handed out, outliving any later fix. A `base` not in the configured list returns `400 {"error": "invalid_base_url"}`; an empty configured list returns `500 {"error": "no_base_url_configured"}` rather than quietly falling back to `localhost`; a valid, differently-cased or trailing-slashed match is accepted and the response always encodes the server's own canonical string, never the caller's.

Local dev with two domains:

```bash
SPIN_VARIABLE_PUBLIC_BASE_URLS="http://localhost:3000,http://127.0.0.1:3000" \
SPIN_VARIABLE_ADMIN_BOOTSTRAP_PASSWORD=<some-password> \
SPIN_VARIABLE_COOKIE_SECURE=false \
  spin up --build --runtime-config-file runtime-config.toml
```

Plan: `docs/plans/multi-domain-display.md` (also records the rejected per-link `domain` field and `Host`-header enforcement designs, and why).

## Link tags and ownership

Links carry free-form tags, and a `users.manage` holder can reassign a link's owner. Plan: `docs/plans/link-tags-and-ownership.md`.

**Tags live only inside the `slug:<slug>` record, as a `tags` array — there is no `tag:` index and no `_meta:tags` registry.** Vocabulary rules are in `api/tags.py`: lowercase, `^[a-z0-9][a-z0-9_-]*$`, 1–32 chars, **max 10 per link**, stored normalized, de-duplicated and sorted. The character set is deliberately narrower than the slug's (no uppercase) so that `Sale` and `sale` can never become two tags; the 10-per-link cap exists because tags render as chips inside the links table's existing Short-link cell, and a row with dozens of them would wreck the column.

**Why no index.** The dashboard already holds every link in `allLinks` (`GET /api/links` has no pagination), so filtering and autocomplete are pure client-side work over data already in memory. A `tag:<tag>` index would have bought nothing for that and cost a two-index read-modify-write on every single-link `PATCH` with no compare-and-swap available. It would also create a new KV key type, obliging a matching `api/backup.py` change (`INDEX_KEYS`, `restore_write_order`) and an `api/consistency.py` shape update (else it reports as `unrecognized_key` on every run). **If either an index or registry is ever added, both changes are mandatory, not optional** — a new key type either module doesn't know about is silently dropped on restore or misreported as drift.

**The cost of that choice:** tag suggestions are ownership-scoped. A user without `links.view_all` is only ever offered tags they have personally used, because the suggestion list is derived from the links they can see. Filtering still works correctly on everything they can see.

**`links.tag` gates bulk tag/untag only.** Setting tags on a single link — at create, or via `PATCH /api/links/{slug}` — needs only the edit rights that link already required. The permission exists for `POST /api/links/bulk-action` with `action` of `tag` or `untag`, which still applies the per-row `can_edit` check on top. `PATCH {"tags": [...]}` is a **full replacement**, not a merge; omitting the key entirely leaves existing tags untouched.

**GUI: a chip input, not a comma-separated field.** Every tag-entry surface uses a shared chip-input component (`gui/dashboard.js`'s `.tag-input`/`.tag-chip-editable`); once a buffer holds exactly one token, `<datalist>`'s native prefix-match works with no rewriting needed. Because `PATCH {"tags": [...]}` is a full replacement, the edit-row save omits the `tags` key entirely unless the committed chip set actually changed from what the row was rendered with (compared against a `data-original-tags` snapshot) — otherwise a save that never touched tags would silently wipe them. **The dashboard's `#tag-filter` is a multi-tag chip input with an explicit all-of/any-of combining rule, defaulting to all-of** — because the filtered set feeds bulk Delete/Reassign, and any-of's over-matching plus select-all is how an operator would touch links they never meant to. Tag suggestions stay client-derived and ownership-scoped (`allKnownTags()` over `allLinks`).

**Owner reassignment is `action: "reassign"` on the same bulk endpoint, gated on `users.manage` alone.** It deliberately **skips the per-row `can_edit` check** every other bulk action applies. That is the point of the feature: the motivating case is an employee leaving, whose links the operator by definition cannot edit. It is not a weaker bar than an `admin` role check either — `api/users.py`'s `handle_update` already lets a `users.manage` holder promote themselves to admin.

- **The permission check runs before the owner lookup, and must stay that way.** Reversed, a caller without `users.manage` gets `400 unknown_owner` for a name that doesn't exist and `403 forbidden` for one that does — enumerating the username list that `GET /api/users` gates behind that same permission. `test_bulk_action_reassign_without_permission_cannot_distinguish_a_real_owner_from_a_fake_one` is the guard.
- **Reassignment is a pure record rewrite — since `docs/plans/derived-link-indexes.md`'s Stage 2, there is no owner index to move a slug between at all.** Before that change, records were written first, then the new owner's index, then the old owners' (`links.move_slugs_between_owners`, since deleted), so an interruption mid-move left a slug listed under *both* owners' indexes — visible, harmless, self-correcting. That whole story collapses now: an interruption partway through a multi-slug reassignment simply leaves some records rewritten to the new owner and some not, and every one of them is correctly listed under whichever owner its record currently names, because listing is derived from the record.
- A **disabled** user is an acceptable reassignment target (parking links on a deactivated account is a legitimate move); a nonexistent one is not.

**`redirect` is untouched.** `linkgate.Link` has no `Tags` field and gains none — Go's `encoding/json` ignores unknown fields unless a decoder opts into `DisallowUnknownFields`, so the new field costs the hot path nothing. `redirect/linkgate/link_test.go` pins both halves of that.

**Bulk tag, untag and reassign share the 50-slug `MAX_BULK_ROWS` cap** with the existing actions, and are all-or-nothing like them: if adding a tag would push any one link past 10, nothing is written and every offending slug is reported. The dashboard disables all six bulk buttons past the cap and tells the user to narrow the filter, since a tag filter is the easy way to select 200 links at once.

## User deletion and link ownership

**`DELETE /api/users/{username}` refuses with `409 {"error": "user_owns_links", "username", "link_count"}` while the user still owns links**, writing nothing to either store. The operator disposes of the links first — reassign or delete, via the bulk actions above — and then deletes the account. Plan: `docs/plans/user-deletion-link-ownership.md`.

**This exists because deleting a user used to leave two things behind, both of which were reproduced against a running app before the fix.**

1. **Link inheritance.** The link records kept `owner: "<deleted-username>"` and `owner_links:<deleted-username>` survived in the `links` store. **There is no user identity anywhere beyond the username string** — `links.can_edit` is `record["owner"] == principal.username` and `handle_list` reads `owner_links:<principal.username>` — so recreating the username handed the new account every link the old one owned, editable and repointable, while the short URL kept resolving for everyone who already had it.
2. **Session revival, the worse one.** `auth.resolve_session` builds the `Principal` from the **current** `user:` record and keys only on the username stored inside the session, and deletion never purged `session:*`. A deleted user's cookie correctly 401'd *while the username was absent* — and then came back to life the moment the name was recreated, carrying **the new account's role and permissions**. A plain user's revoked cookie was observed returning as an admin's, without its holder ever learning the new password. Deleting a user was never actually revoking their sessions; it was making them temporarily unresolvable.

Both scenarios are pinned by `api/tests/test_user_deletion.py` rather than merely fixed, and both are mutation-verified: removing the 409 gate fails the first, removing the session purge fails the second.

**There is deliberately no tombstone or reserved-username list.** Purging sessions at deletion is what makes username reuse *safe*, which is a better property than making it forbidden — a reserved list would grow forever, would need its own admin UI to ever release a name, and would still not have fixed the session bug. `auth.delete_sessions_for_user(store, username, list_keys)` takes the key-listing callable as a parameter, the same way `backup.py` does, so `auth.py` stays free of `spin_sdk` imports and host-testable.

**Cross-store write ordering on the success path** (deletion touches both the `links` and `users` stores, with no transaction and no compare-and-swap): sessions → `user:` → `_meta:usernames`. Every interruption point leaves the stronger invariant — a crash after this point never leaves a live session for a nonexistent user. **Since `docs/plans/derived-link-indexes.md`'s Stage 2, there is no `owner_links:` key to delete here at all** — the original ordering led with `owner_links:` → sessions → `user:` → `_meta:usernames`, and that first step is simply gone now that there's no index for it to touch.

**`links.slugs_owned_by`** (public, the same "shared, not module-private" convention `can_view`/`can_edit` already carry) is what `users.py` calls to make the 409 decision — derived from the records themselves (`links.enumerate_slugs` plus a `get_many` and an `owner` field check), not from a maintained `owner_links:<username>` index, which no longer exists. See "Derived link indexes" for why.

**The GUI turns the refusal into an action.** `gui/admin/users.html` names the username and count, and offers a link to `dashboard.html?owner=<username>` **only when the viewer holds admin/`links.view_all`/`links.edit_all`** — an operator with `users.manage` alone would land on an empty dashboard, so they get the missing permission named instead of a dead link. That is accepted rather than fixed: such an operator can already self-promote through `handle_update`.

- The dashboard's `#owner-filter` is **derived from the `owner` field on the loaded records, not from `owner_links:`**, so it is ownership-scoped for free and additionally surfaces links whose owner no longer exists. **That makes it the repair path** for any deployment that orphaned links before this gate existed; those owners render with a `— deleted account` marker reusing the existing `status-disabled` treatment (no new token).
- `?owner=` is **consumed once**. A reload after a bulk action keeps whatever filter the operator has since chosen instead of snapping back to the URL.

## Destination URL policy

Admin-managed rules on what a link may point at, enforced at authoring time. Pure logic in `api/urlpolicy.py`; the admin page is `gui/admin/url-policy.html`, reached by an in-body anchor on `admin/users.html` (the nav is full). Plan: `docs/plans/destination-url-policy.md`.

**A destination URL is also length-capped, separately from policy.** `links.MAX_TARGET_URL_BYTES` (4096) is enforced at all four authoring paths through the single `links.target_url_error`/`target_url_error_body` choke point, measured in bytes (not characters, since the bound protects stored value size and non-ASCII/percent-encoded URLs cost more bytes than characters). This matters more now that every visible link record is fetched on every dashboard load (see "Derived link indexes") — the population paying for an oversized record is everyone, not just its owner.

**Why it exists:** a short link *launders* its destination. A recipient sees `go.example.com/r/promo` and cannot tell where it leads, so a bad destination borrows the organization's credibility. Before this, `links.is_valid_target_url` accepted any `http`/`https` URL with a netloc, and any account could shorten anything.

**Rules live in one `_meta:url_policy` key in the `links` store.** An absent key means everything is allowed, so no deployment changes behaviour on upgrade and nothing needs a migration. **No rules are seeded** — a list shipped in the repo needs a deploy to change and carries false-positive risk, the same reasoning that retired the banned-word slug list.

**Precedence is one sentence: a deny rule always wins, then an allow rule or a `default_action` of `allow`, otherwise blocked.** This was chosen over "most specific match wins" for one reason — **a misunderstood specificity rule fails open, and deny-wins fails closed.** Do not "improve" it into specificity ordering.

**Matching covers a host and every subdomain of it**, via `host == rule or host.endswith("." + rule)`. The dot is load-bearing: a bare `endswith("example.com")` would also match `notexample.com` and silently mis-scope every rule. Verified live in both directions — under a deny rule for `example.com`, `evil.example.com` and `a.b.example.com` are blocked while `notexample.com` and `myexample.com` are not; and under an allow-list with `default_action: "deny"`, the classic bypasses `example.com.attacker.net` and `user@example.com.evil.net` are both blocked (the host comes from `urlparse(...).hostname`, so userinfo can't spoof it).

**Enforced at all four authoring paths — `links.handle_create`, `links.handle_update`, `bulk.handle_bulk_create`, and `bulk.handle_bulk_action`'s `repoint` branch.** A policy enforced in two of three places is not enforced (now three of four), and `api/tests/test_url_policy_enforcement.py` exists to prove all four reject the same destination and write nothing. **`validate_bulk_rows` takes the policy as a required parameter with no default** — deliberately, because a default is exactly how the bulk path would stay silently open. Rejections carry `host` and `reason` so the GUI can name what caught the link rather than saying "not allowed". The `repoint` branch was the one path genuinely tempting to exempt — `existing links that violate a newly-added rule are reported, never mutated` (below) can read as license to skip enforcement on an edit to an existing record — but `handle_update` already enforces the policy on a single-link destination change, so exempting `repoint` would make the policy trivially bypassable at 50× throughput by anyone with `links.edit_all`. The existing-violator carve-out is about links nobody has touched since the rule appeared, not about new destinations chosen after it.

**Existing links that violate a newly-added rule are reported, never mutated.** `GET /api/admin/url-policy/violations` lists them; remediation is the operator's existing bulk Disable/Delete. Nothing is retroactively protected until a human acts — that is the accepted trade, taken so that a config edit can never become an unpreviewable bulk mutation with no compare-and-swap and no undo. It is the same posture restore and the consistency check already hold. **Violations are deliberately *not* a thirteenth consistency check:** `consistency.py` is scoped to structural drift, a policy finding would pin `ok: false` on a structurally flawless store, and its "re-run to confirm" and "never repairs" framings are both wrong for policy.

**`redirect` is untouched.** Enforcement is at authoring time; the hot path keeps its single KV read per click and never consults the policy. A link created before a rule existed keeps resolving.

**`_meta:url_policy` carries both obligations a new KV key type now imposes** (see "KV consistency check"): `consistency.py` recognises its shape, and `backup.py` round-trips it — verified byte-identically, because otherwise restoring a backup would silently wipe an operator's policy.

## Derived link indexes

`links:all_links` and `links:owner_links:<owner>` used to be maintained, read-modify-write indexes over the `slug:` records — a shared JSON array, no compare-and-swap available anywhere in Spin's KV. Concurrent authoring requests each read the index, added their own slugs, and wrote back: last writer wins, and everyone else's index additions were silently lost. The link *records* all landed and resolved at `/r/{slug}`; only their appearance in `GET /api/links`/`GET /api/analytics/click-totals` and the `owner_links:` gate on user deletion depended on the index surviving the race.

**Measured directly on `751f368-throttle-resilience`, 2026-08-17:** four concurrent 5-row bulk creates (~28 writes, far under the write cap) produced 20 real link records and lost 10 of them from the index with zero write failures anywhere in the trace — proving the loss was the race itself, not write throttling. Since `docs/plans/derived-link-indexes.md`, both indexes are **gone**. `links.enumerate_slugs(store, list_keys)` derives the slug list from a `slug:` key enumeration; `links.slugs_owned_by(store, username, list_keys, get_many)` derives ownership the same way, by reading every record and checking its `owner` field. `GET /api/links`, `GET /api/analytics/click-totals`'s visible set, and `users.handle_delete`'s `409 user_owns_links` gate all use these instead of an index read. **A record's existence is now the only truth** — this replaces "records first, indexes last" everywhere that rule used to apply (bulk create/delete, single create/delete, reassignment): every interruption point leaves exactly the records that landed, all of them listed, none of them advertised-but-missing, because there is no longer a second write that could fall out of step with the first.

**Cost, measured on the deployed trace the day this shipped:** `GET /api/links` swaps one `get` of `all_links` (~25 ms) for one `list_keys` (~24 ms at the store's size that day) — a wash today, but `list_keys` costs `~24 ms + 68.7 µs per physical key in the WHOLE default store` (see "Parallel KV reads" below) and grows without bound as click volume grows, where the old index read did not. **Revisit trigger: a traced `list_keys` inside `GET /api/links` above ~250 ms** (roughly 3,300 physical keys) — the same trigger `docs/plans/derived-link-indexes.md`'s Recommendation section already costs. The `events:` ring-buffer write, one of the levers that section named, was dropped 2026-08-18 (`docs/plans/drop-events-write.md`) — it bent the slope by roughly a third but did not remove the underlying trigger.

**Two residual read-modify-write keys remain, and no others are proposed.** `users:_meta:usernames` (still a maintained index — see `unindexed_user`/`missing_user_record` below) and `links:_meta:url_policy` (a single admin's rule edit, single-writer in practice); both are accepted as-is, on the same reasoning: low frequency, no user-visible authoring hot path depends on them.

**The leftover `all_links`/`owner_links:<owner>` keys are not deleted.** They stay in the store, inert, forever — at ~68.7 µs per key to enumerate, deleting them is a follow-up not worth its own endpoint (see `docs/plans/derived-link-indexes.md`'s "Out of scope" section). `consistency.collect` recognises both shapes as known-and-ignored, the same treatment `_meta:bootstrapped` already gets, so a store that predates this change reports exactly as clean as one that never had the keys at all. `backup.py` needed **no change**: `INDEX_KEYS`/`restore_write_order` already understood both shapes, so a backup taken before this change round-trips byte-identically — `api/tests/test_backup.py` pins it.

## KV consistency check

`GET /api/admin/consistency` walks the `links` and `users` stores and reports where the users index and sessions have drifted, plus corrupt/unrecognized values in either store. **The check itself stays write-free**: there is no `?fix=` on this endpoint, and `collect`/`analyze` perform no writes at all — a separate repair endpoint now exists (see "Consistency repair" below), but it re-derives everything itself rather than trusting this endpoint's output, and this endpoint never gained a mutating side effect of its own. Gated on `users.manage`. Pure logic in `api/consistency.py` (zero WASI SDK imports, `store` objects and the `list_keys` callable passed in, `api/backup.py` as the model); the GUI is a third article on `gui/admin/backup.html`. Plan: `docs/plans/kv-consistency-check.md` for the original twelve-check design, `docs/plans/derived-link-indexes.md` for why six of them were retired.

**Six checks**, always all present in every report at `count: 0` when clean, in this order:

| id | severity | means |
|---|---|---|
| `unknown_link_owner` | warning | a record whose `owner` has no user record |
| `unindexed_user` | warning | a `user:` record missing from `_meta:usernames` — can sign in, invisible to administration |
| `missing_user_record` | info | `_meta:usernames` names a user with no record |
| `orphan_session` | warning | a `session:` naming a user with no record |
| `unreadable_value` | warning | a value that wouldn't parse into its expected shape |
| `unrecognized_key` | info | a key matching none of the known shapes for its store |

**Six checks were retired, not merely renumbered** — they all described drift in `all_links`/`owner_links:<owner>`, indexes that no longer exist (see "Derived link indexes"). A fact with no counterpart can't drift from it. `unknown_link_owner` is the one owner-related check that survives, derived entirely from `link_records` with no index involved.

**The `analytics` store is never opened or scanned.** `links.handle_delete` inline-purges the deleted slug's own analytics keys (see "Orphaned analytics purge" below) but bulk delete still doesn't, so `count:<slug>:<shard>`/`events:<slug>:<slot>` for a deleted slug is **normal state, not drift** — reporting it would make every healthy deployment show findings, which is how a checker gets ignored. **Expired `session:` records are excluded for the same reason.**

**A report can never carry credential material.** A `user:` record's *value* is never read — only its key name; `unindexed_user`/`missing_user_record` need nothing else, and `orphan_session` reads only the `username` field of a `session:` value. A test generates a report over a store holding a real PBKDF2 hash and asserts neither `password_hash` nor `pbkdf2_sha256` appears in the body.

**`MAX_FINDINGS_PER_CHECK = 100`, per check, not global** — one noisy check would otherwise starve every other one out of the report. It is a plain module constant, not a Spin variable, on the same reasoning as `MAX_BULK_ROWS`: one function in one component reads it. **When a check truncates, `count` stays exact and `truncated` is set**, and the GUI says "Showing the first N of M" — a capped list must never read as complete.

**The walk has no snapshot.** Spin KV offers no transaction, so a concurrent write can produce a transient finding. That is why the page tells the operator to re-run: a real finding appears on both runs. Do not "fix" this with locking; there is nothing to lock with.

**A new KV key type now obliges *three* changes, not two** (see also "Link tags and ownership"): `backup.py`'s `INDEX_KEYS`/`restore_write_order`, `consistency.py`'s key-shape recognition — otherwise the new key reports itself as `unrecognized_key` on every single run — **and, since the KV store consolidation, the key must live under one of the three prefixes (`links:`, `users:`, `analytics:`) in `api/kvprefix.py`'s `STORE_PREFIXES`, or it is invisible to the whole application**: no view will ever return it, so it won't appear in a backup, won't be seen by the consistency check, and will be silently pruned by the next restore.

## Consistency repair

`POST /api/admin/consistency/repair` is the write-side companion to the read-only check above. Three of the six checks have exactly one safe, derivable, automatic repair; three never do because repairing them requires a judgment call the store can't answer on its own. Gated on `users.manage`, matching the check, backup/restore and the analytics purge. Pure logic in `api/consistencyrepair.py` (zero WASI SDK imports, `store` views/`request`/`list_keys`/`get_many` taken as plain parameters, `api/consistency.py` and `api/analyticsorphans.py` as the models); the GUI lives inside the existing consistency article on `gui/admin/backup.html`/`backup.js` — no new page, route, or `spin.toml` entry. Plan: `docs/plans/consistency-repair.md` for the original design, `docs/plans/derived-link-indexes.md` for why five of the eight original repairs were retired.

**Why this shipped after the check, not with it:** the plan deliberately deferred a repair tool until a real deployment had shown real drift ("a repair tool designed before anyone has seen a real report is designed from imagination"). The triggering incident — throttled index writes leaving hundreds of findings with no way to fix them — is now structurally impossible (see "Derived link indexes"), but the repair tool survives for the three checks that can still drift.

**The repairable/non-repairable split, and why:**

| check | verdict | repair |
|---|---|---|
| `unknown_link_owner` | **never** | fix is reassign-or-delete, both product decisions with shipped bulk tools and a dashboard owner filter already built for exactly this |
| `unindexed_user` | repair | add username to `_meta:usernames` |
| `missing_user_record` | repair | remove username from `_meta:usernames` |
| `orphan_session` | repair | delete each `session:<token>` |
| `unreadable_value` | **never** | content is unknown by definition — delete and rewrite are both guesses |
| `unrecognized_key` | **never** | deleting an unrecognised key is exactly how a future key type this checker hasn't learned about yet gets destroyed — `analyticsorphans.classify_analytics_keys` already holds the identical rule |

`consistency.REPAIRABLE_CHECKS` names the three, in `CHECKS` order, and is published in every report as `repairable_checks` — the GUI never decides for itself which findings have a button; that is a correctness question the server owns.

**The client submits check ids, never findings — that is what satisfies "re-detect before repairing."** The report the operator is looking at contributes nothing but intent; `handle_repair` always re-runs `consistency.collect`/`consistency.analyze` in-request, calling `analyze(collected, max_findings=None)` so it acts on every finding rather than just the first `MAX_FINDINGS_PER_CHECK` (100) the report happened to display.

**Index repair is O(distinct index keys), not O(findings).** `unindexed_user` and `missing_user_record` share exactly one key (`_meta:usernames`); only `orphan_session` costs one key per finding, since each session is its own key.

**`MAX_REPAIR_WRITES = 100`, a plain module constant**, same reasoning as `MAX_BULK_ROWS`/`MAX_BACKUP_ENTRIES`. Sized from a measured ~75 ms/write on Akamai: 100 × ~75 ms ≈ 7.5 s against the 30 s handler limit, a ~4× margin. Raising it needs real timing evidence from a full-cap repair.

**Deletes are always sequential, never gathered — the same rule the analytics purge and every bulk handler follow.** `apply_repairs` never fans a write out concurrently; `api/kvbatch.py`'s concurrency helper is reads-only by design, and the WASI key-value batch interface's multi-key write functions are already rejected repo-wide (`TASKS.md`, "Considered and rejected", 2026-08-15) — writes are cap-bound at 50/second app-wide while reads have 1,000/second of headroom, so issuing them concurrently would queue against the cap rather than overlap, and would compete with live click recording.

**No new KV key type.** The repair only mutates keys `backup.py`'s `INDEX_KEYS`, `consistency.py`'s key-shape recognition, and `kvprefix.STORE_PREFIXES` already understand — `_meta:usernames`, `session:<token>`. The links store is never read or written by this repair any more. It is stateless: it records nothing about past repairs, exactly like the analytics purge.

**The lost-update window, and why "run it again" is the worst case.** Spin's KV has no compare-and-swap and the consistency walk has no snapshot, so a concurrent write between `collect` and `apply_repairs` can produce a lost update. Three things bound it: every delta write re-reads `_meta:usernames` immediately before writing it, so the window is one `get` + one `set` rather than the whole collect-to-write span; a repair never writes a wholesale computed list, only the specific members `collect` formed an opinion about, so a concurrently-created username survives untouched; and the only reachable residual failure mode is therefore a lost *removal*, which surfaces as ordinary drift on the next consistency run and is fixed by re-running.

## Orphaned analytics purge

`links.handle_delete` and `bulk.handle_bulk_action`'s delete branch remove a `slug:<slug>` record; neither one touches the `analytics` store's shards for that slug by default. That used to be argued as harmless ("orphan analytics are harmless in a way orphan links are not"), but was falsified by measurement: `list_keys` costs ~68.7 µs per physical key in the whole `default` store (see "Parallel KV reads"), `GET /api/analytics/click-totals` makes exactly one such enumeration on every dashboard load, and a measured live store was 96% orphaned analytics keys against only 14 live links. The audience — marketing staff who create and delete links heavily as they correct mistakes — makes this a permanent, unbounded leak, not a curiosity.

**`links.handle_delete` purges the deleted slug's analytics keys inline, in the same request; `bulk.handle_bulk_action`'s delete branch still does not, and that asymmetry is deliberate.** Single-link delete used to ratchet the store up until an administrator remembered to run the manual tool below, and the audience causing it has no reason to ever open the Store maintenance page. Bulk delete stays out because the arithmetic doesn't close: 50 slugs at ~95 analytics keys each is 4,750 sequential writes, ~95–123 s against Akamai's 30 s handler limit.

- **Mechanism**: `links.handle_delete` takes an injected `purge_analytics` callable (avoids a `links.py` ↔ `analyticsorphans.py` import cycle). `api/app.py` wires it to `analyticsorphans.purge_slug_analytics`, which reuses the existing enumerate-then-classify logic (`classify_analytics_keys`) rather than constructing candidate keys, so it picks up the legacy unsharded `count:<slug>` key and any future analytics key type for free. Omitting `purge_analytics` (as `bulk.py`'s delete branch does) reproduces the plain `{"ok": true}` response with zero analytics access.
- **Write ordering is record → analytics, load-bearing.** An interruption before the purge leaves the pre-existing, expected steady state (orphan analytics keys, cleaned up by the manual tool below). Reversing it risks a live, resolving link whose click history silently vanished with no way to restore it. A KV failure inside the purge is caught and reported as `{"status": "failed", ...}` rather than turning a successful deletion into a `500`.
- **`MAX_INLINE_PURGE_KEYS = 128` is a safety rail, not a policy, and cannot fire at shipped configuration** (max possible per-slug count today is 95: 64 shards + 1 legacy key + 30 historical event slots). A policy cap that deliberately deferred expensive links was rejected — those links carry the most keys, so deferring them opts out of most of the benefit. `api/tests/test_analytics_orphans.py` pins `MAX_INLINE_PURGE_KEYS >= COUNT_SHARDS + 1 + 30` so a future raise-only bump to `CountShards` can't silently start deferring the purge.
- Nothing changes in the GUI beyond disabling the Delete button for the request's duration; the response's `analytics_purge` field is never rendered (deleting a link already made its analytics unreachable). Plan: `docs/plans/inline-analytics-purge-on-delete.md`.

**The manual tool**: a cheap report (`GET /api/admin/analytics/orphans`, exactly 2 KV operations regardless of orphan count — one `list_keys` on analytics, one on links) plus a chunked, client-driven purge (`POST /api/admin/analytics/purge`, at most `MAX_PURGE_SLUGS` (50) slugs and `MAX_PURGE_KEYS_PER_REQUEST` (250) deletes per request), both gated on `users.manage`, both on `gui/admin/backup.html` (retitled "Store maintenance", file path unchanged — renaming it would need a new routing entry and route for no functional gain). Pure logic in `api/analyticsorphans.py` (zero `spin_sdk` imports). The report derives liveness from `links.enumerate_slugs` (a `slug:` key enumeration), not a maintained index. Plan: `docs/plans/analytics-orphan-purge.md`.

**No new KV key type.** The purge deletes only keys it just enumerated, never constructing one — so it picks up the legacy unsharded key, ring-buffer leftovers, and any future `CountShards` raise for free.

**Deliberately NOT a 13th consistency check.** Orphaned analytics is expected, normal, intended state between purges — a check over it would pin `ok: false` on every deployment that has ever deleted a link, the same reasoning applied to destination-policy violations. Four independent sources of orphan analytics exist regardless (bulk delete, pre-existing orphans, a `failed` inline purge, a `deferred` one), so the check stays a separate tool.

**The report can be misled by a stale enumeration; the purge cannot be — the load-bearing safety property.** The report's liveness set is a snapshot at report time. The purge does not lean on it: it re-checks `exists("slug:<S>")` on the record itself immediately before deleting, via a bounded `gather_reads` fan-out. That's what makes it safe to confirm with a count-bearing `confirmDialog` rather than a typed field like restore's — a stale report can misinform the operator, but can't make the purge touch a live link's analytics. The one accepted residual: an operator purges a slug and someone recreates that exact slug and gets clicks in the same few seconds — the new link loses a few seconds of its own brand-new clicks, never history (it has none yet).

**Deletes are always sequential, never gathered.** `gather_reads` is used only for the liveness pre-check and the report's enumeration — both reads, never a delete; see "Parallel KV reads" for why that read/write asymmetry is the whole safety argument.

**Caps are plain module constants** (`MAX_PURGE_KEYS_PER_REQUEST = 250`, `MAX_PURGE_SLUGS = 50`), not Spin variables, on the same reasoning `MAX_BULK_ROWS`/`MAX_BACKUP_ENTRIES` carry. 250 sequential deletes is ~5 s of wall clock at measured write cost, well under the 30 s handler limit. Raising either needs real timing evidence from a full-cap purge. Both responses echo the limit that bounded them.

## KV backup and restore

`GET /api/admin/backup` downloads a JSON snapshot of the `links`, `users` and `analytics` stores; `POST /api/admin/restore` replaces them from one. Both live in `api/backup.py` (pure logic, zero `spin_sdk` imports) and are routed on exact paths from `api/app.py`. The GUI is `gui/admin/backup.html` + `backup.js`. Plan: `docs/plans/kv-backup-restore.md`.

**File format.** `{"format": "spin-shortener-kv-backup", "schema_version": 1, "created_at", "created_by", "fidelity", "counts", "stores": {...}}`. Keys are plaintext, **every value is base64** — uniformly, regardless of whether it happens to be JSON, so the format never has to care what a value contains. `?stores=links,users` exports a subset, allowlist-validated against `BACKUP_STORES` exactly the way `qr.handle_qr` validates `?base=` (unknown name → `400 unknown_store` naming `allowed_stores`; empty → `400 no_stores`). `fidelity` is `"full"`: the `get_keys` spike confirmed Spin's KV can enumerate keys, so the planned index-walk fallback (and its `"index-walk"`/`incomplete: true` labelling) was never needed and is not implemented.

**A backup carries no *account* credentials — but it does carry link password hashes. It is a sensitive file.** Three exclusions are applied at export: `redact_user_value` strips `password_hash` from every `user:` record, and `is_excluded_key` drops every `session:*` key and `_meta:bootstrapped`. So the file cannot be replayed into a session and cannot leak an *account* hash. **`validate_backup` independently refuses a file containing any of that material on the way back in** — a second guard on the same property, not a redundant one, since it means a hand-edited file can't inject a session or an account hash either. Both halves are mutation-tested: disabling redaction fails 5 tests, disabling exclusion fails 6, and both additionally fail a *restore* test.

**What is deliberately *not* stripped: a link's own `password_hash`, inside its `slug:` record in the `links` store.** `redact_user_value` is scoped to `user:` keys and `is_excluded_key` returns `False` for every store but `users`, so a password-protected link exports with its full PBKDF2 hash. That is the right call — stripping it would make restore silently *unprotect* every protected link, a security downgrade invisible to the operator — but it means **the file must be treated as sensitive**, not as the freely-shareable artifact the account-hash exclusion alone would suggest. Link passwords are the weaker population, too: the GUI enforces only `minlength="4"`, so a short link password behind PBKDF2-100k is realistically crackable offline by anyone holding the file. Store backups somewhere access-controlled.

**Do not verify this property with `grep password_hash <file>`.** Every value in the document is base64, so that grep cannot see inside a record — it only ever matches the plaintext `excluded` array, which lists `"users/user:*#password_hash"` as documentation and always returns a nonzero count. Decode the values and inspect them instead.

**Restore is all-or-nothing and it replaces, it does not merge.** `validate_backup` runs to completion before a single write. Then each store is written and pruned: any pre-existing key absent from the file is deleted. Store order is `links` → `analytics` → `users` (`RESTORE_STORE_ORDER`) — **users last, deliberately**, so a mid-restore failure leaves the operator's own session intact to retry with. Within each store, **records are written before indexes** (`restore_write_order`, using `INDEX_KEYS` plus the `owner_links:` prefix) — the same rule the bulk handlers follow, for the same reason: an interruption leaves records with no index entry, which resolve at `/r/<slug>` and are merely invisible in the dashboard, rather than index entries advertising slugs that 404.

**Recovery walkthrough, confirmed live end to end.** Restore a backup → the response carries `signed_out: true` and every session is gone, including the caller's. **No `spin up` restart is needed**: `ensure_bootstrap_admin` runs on *every request* (`api/app.py:60`), and since restore deleted `_meta:bootstrapped`, the next request re-seeds the bootstrap admin from `admin_bootstrap_password`. Sign in as that admin and the restored links resolve immediately. **The disclosed corner: that re-seed overwrites a restored user record named `admin`** — same username, but a fresh record with `role: "admin"`, `permissions: []` and `assigned_domains: []`, so any custom permissions or domain assignments that account had are lost. Every *other* restored account survives intact but **has no usable `password_hash` and can therefore never authenticate** — `LocalAuthProvider.authenticate` returns a clean `401`, not a `500`. An admin must set each one a new password; the users table flags them (see DESIGN.md's Status Badges).

**Caps: `MAX_BACKUP_BODY_BYTES = 5_242_880` (5 MiB) and `MAX_BACKUP_ENTRIES = 5_000`,** plain module constants in `api/backup.py`. Export refuses with `500 backup_too_large` naming both the cap and the actual size; restore refuses with `413 body_too_large`. **Raising either needs real timing evidence from a full-cap restore, not a hunch** — the same rule `MAX_BULK_ROWS` carries above, and for the same reason: a restore is a single `componentize-py` request doing thousands of sequential KV writes with no batching available.

**Both endpoints gate on the `users.manage` permission**, the same bar as user administration rather than a `role == "admin"` check — not the weaker of the two, since a `users.manage` holder can already promote themselves to admin via `handle_update`.

**Restore requires `{"confirm": "REPLACE"}` in the body** (`400 confirmation_required` otherwise), and the GUI additionally requires the literal string typed into a field *plus* a count-bearing confirmation dialog. Server-side confirmation is the one that matters — the endpoint is reachable by `curl`.

## Write-throttle resilience

**This section is historical for its index half, and current for its record half — read it with "Derived link indexes" above in mind.** That change deleted `all_links`/`owner_links:<owner>` entirely, so everything below about `add_slugs_to_indexes`, `INDEX_WRITE`, `index_updated` and `"consistency_repair"` describes machinery that no longer exists — the "abandon-and-index-what-landed" rule is moot, because there is no longer an index write to abandon or land. What survives unchanged: the **record**-write retry (`RECORD_WRITE`, the `_RetryBudget`/backoff mechanism, `kvretry.py` itself, the `"partial": true` response contract, and the `redirect`/`backup.py` exceptions below) — a record write can still be throttled and still gets retried exactly as described.

Akamai caps KV writes at 50/second app-wide (see "Deployment: Akamai Functions" below). Before this, a throttled write anywhere in `api/bulk.py` propagated straight to `api/app.py`'s catch-all and became a bare `500 {"error": "internal_error"}` — telling the operator nothing about which rows landed, in a state where retrying could create duplicates or hit `slug_taken`. This happened twice in ordinary operation (TASKS.md's 2026-08-15/17 incidents), both times because `bulk.handle_bulk_create` wrote every `slug:` record and called `links.add_slugs_to_indexes` **last**, so a throttled run left records written and the index never updated. Plan: `docs/plans/write-throttle-resilience.md`.

**Two independent changes, and the second matters more than the first.** Retry (below) makes a throttled write less likely to fail. **Abandon-and-index-what-landed** is what makes its failure harmless: every multi-write handler that writes records then an index breaks its record loop on exhaustion and indexes exactly the records that did land, rather than continuing to hammer a throttled store. If anything here has to be compromised, retry is the thing to compromise — never the index-what-landed rule.

**That "structurally clean" property used to hold per-request only** — concurrent bulk creates could still drift the old `all_links`/`owner_links:<owner>` indexes (measured: six concurrent 50-row creates all returned clean responses and still left dozens of unindexed findings, from concurrent requests silently overwriting each other's index additions). **This is now moot** — those indexes no longer exist (see "Derived link indexes"); the failure mode can't recur.

**Throttling has no dedicated error variant and no wording-independent check exists.** A throttled write arrives as `Err(Error_Other(value='too many requests'))` — the same shape any other KV failure takes, and `componentize_py_types` (which defines the WIT error dataclasses) doesn't exist in the host venv, so a pure module can't `isinstance`-check them. **Consequence: every write error is treated as retryable, unconditionally, in the control path — no variant check, no string match.** `api/kvretry.py`'s `classify_write_error` does a substring check purely to **label** the failure for the log/response (`kvretry.THROTTLE_MESSAGE_MARKERS = ("too many requests", "rate limit exceeded")` — Akamai was measured emitting both, from the same op in the same run) — never to decide whether to retry, since a vendor wording change would otherwise silently revert the app to the bug this section fixes. `api/backup.py` inlines the same tuple rather than importing it; `test_backup_and_kvretry_agree_on_throttle_markers` pins the two literals equal. A pure module *can* still identify the error *variant* without importing WIT types, though — `componentize_py_types.Err.value` is duck-typed via `getattr`, so `type(exc.value).__name__` yields `Error_Other`/`Error_AccessDenied`/etc. with no import at all (`obs.error_type_name`). This is deliberately **not control flow**, only a log field's spelling — promoting it to control flow is filed as Future work.

**`await asyncio.sleep(d)` for any `d > 0` raises inside the component** — componentize-py's substitute event loop leaves `call_later`/`call_at`/`time` all `raise NotImplementedError`. The real primitive is `wasi_clocks_monotonic_clock_0_3_0_rc_2026_03_15.wait_for(nanoseconds)`, confirmed reachable and confirmed to actually sleep via a real `spin up --build`. `api/app.py` imports it at module scope, guarded the same way `wasi_batch` is; `_sleep_ns` is a documented no-op if a future toolchain ever fails to bundle it.

**The retry seam — `api/kvretry.py`.** `make_writer(sleep, collector=None, jitter=random.random)` returns `async def write(make_coro, policy=RECORD_WRITE)`, closing over one `_RetryBudget` per request with two independent nanosecond counters, `record_ns` (`MAX_RECORD_RETRY_SLEEP_NS = 2s`) and `index_ns` (`MAX_INDEX_RETRY_SLEEP_NS = 3s`, still used by the two residual read-modify-write keys — `_meta:usernames` via `consistencyrepair.apply_repairs`, and `_meta:url_policy` — since the link indexes that motivated a separate deeper budget no longer exist). `RECORD_WRITE` is 3 attempts (backoff 100ms, 300ms); `INDEX_WRITE` is 6 attempts (backoff 100ms–2s). Once a counter's budget can't cover the next scheduled backoff, that kind of write gets zero further retries and fails immediately. `kvretry.direct` (the default) calls straight through with no retry. **Raising any of these constants needs real timing evidence from a full-cap run** — the shipped values are modelled: a full 50-row bulk create's worst case is ≈11.2s against Akamai's 30s handler limit, a 2.7× margin.

**The response contract: `200` with `"partial": true`, not `207`.** `gui/app.js`'s `apiCall` returns `{ ok: res.ok, ... }` and `res.ok` is true for every 2xx, so 200 and 207 look identical to every caller — `POST /api/admin/analytics/purge` already established `200` + `complete: false` for a partial run, and this follows the same convention. A successful run's response is byte-identical to before; only a partial run carries `"partial": true`. The rule this extends: **validation is all-or-nothing; execution is best-effort and fully reported.**

**Where retry-and-report applies today:** `links.handle_create`/`handle_update`/`handle_set_password`/`handle_delete` retry their record write under `RECORD_WRITE`; `bulk.handle_bulk_create`/`handle_bulk_action` break their record-write loops on `kvretry.WriteFailed` and report exactly what landed (`partial`/`not_created`/`write_error`); `consistencyrepair.apply_repairs` routes `_meta:usernames`/session writes through `INDEX_WRITE` and **stops** on exhaustion rather than continuing (it's reached for *during* an incident, when retrying into a saturated cap would make things worse); `analyticsorphans.handle_orphan_purge` retries deletes under `RECORD_WRITE` and stops the same way, putting unattempted slugs back into `remaining_slugs` (its GUI purge loop has a no-progress guard so a "0 deleted" response can't infinite-loop).

**Two deliberate exceptions:** `analyticsorphans.purge_slug_analytics` (the inline purge on single-link delete) never retries — it runs after the link is already deleted, so its failure mode is already-accepted orphan analytics, and retrying would spend write budget on the app's least valuable writes. `backup.handle_restore` never retries either — a full-cap restore is already unable to finish inside the 30s handler limit at the write cap, so retry sleeps would only make a doomed request slower; on a write failure it stops and returns `200` with `partial: true` and `next_step: "retry_restore"` (restore replaces rather than merges, so re-running is a genuine next step).

**Writes are still never gathered or batched, and `redirect` is untouched.** Retry makes writes survivable, not faster; `set_many`/`delete_many` stay rejected repo-wide (see "Parallel KV reads"). `redirect`'s analytics writes stay best-effort lossy (M2 above) — a retry there would add wall time to a visitor's redirect for bookkeeping they have no stake in, and would worsen the write cap for every other caller.

## Toggleable structured logging

The app has KV-timing instrumentation in `redirect` (Go) and `api` (Python) only — `gui-pages` and `gui` are untouched (`gui-pages` does no KV work at all; `gui` is a prebuilt third-party binary). Plan: `docs/plans/toggleable-logging.md`.

**Two Spin variables, both read once and cached for the lifetime of the Wasm instance** (`sync.Once` in Go, a module-level cache in Python) — sound because a Spin variable cannot change without a redeploy on Akamai (`spin aka` has no command to change a deployed app's variables) or a restart locally, both of which produce a fresh instance:

- **`log_level`** — `"off"` (default) or `"summary"`; any other value is treated as `"off"`, fail-closed. **This must stay `off` in production.** At ~130 bytes/line and a sustained ~50 redirects/second (the Akamai write-RPS ceiling documented above, since the events write was retired 2026-08-18), baseline logging is on the order of 280 MB/day into a 7-day `spin aka logs` retention window — the same order-of-magnitude figure as before that change, since it was already an approximate "sustained ceiling" estimate rather than a precise one.
- **`log_debug_token`** — a shared secret (default `""`), compared against a request's `X-SS-Debug` header. A match traces that one request and adds a `Server-Timing` response header **regardless of `log_level`** — this is what lets one request be traced with no redeploy, since the variable alone would mean one redeploy to turn logging on and a second to turn it off. **An empty configured token never matches anything**, including an empty or absent header — checked explicitly before any comparison (`crypto/subtle.ConstantTimeCompare` in Go, `hmac.compare_digest` in Python), not as an incidental property of the comparison. Getting this backwards makes the default configuration "anyone can enable tracing." **The token cannot be rotated without a redeploy either** — there is no runtime-variable-update path on Akamai.

**Output: one logfmt line per request to stderr**, prefixed `ss ` so it's greppable and distinguishable from Spin's own output, e.g.:

```
ss comp=redirect route=/r/{slug} slug=M7RyJVC status=302 dur_us=140 kv_ops=5 kv_us=65 kv_bytes=262 open=2/24 get=2/25 set=1/16 slow=open:-:21
```

Per-op-type fields are `count/total_µs`, one per non-empty operation type (`open`/`exists`/`get`/`set`/`delete`/`list_keys`) — a zero-count type is omitted entirely, never `=0/0`. `slow` names the single slowest operation as `type:namespace:µs`. `api` additionally logs `method` and, on the exception path, `err=1` alongside `status=500`. **`Server-Timing` durations are milliseconds as floats** — 80 µs renders as `0.080`, never `80` — and are only emitted for a valid token, never merely because `log_level=summary`, so a baseline-logging deployment never hands internal timing to every visitor.

**This log line does NOT distinguish a read failure from a genuine miss on its own** — `linkgate.TimedStore.Get` records the op regardless of error and discards the error itself, and `redirect`'s log line has no `err` field (`err=1` is `api`-only). A read failure and a genuine miss produce a field-for-field identical line otherwise. **The status code is the signal instead** — grep a `log_level=summary` build for `status=503`; see "The `/r/{slug}` status contract" above.

**The collector structurally cannot log a KV key.** Its record method takes an operation type, a namespace and a duration (plus a byte count) — it has no parameter that could accept a key, the same move `PrefixedStore` makes by having no `get_keys`. This matters because `users:session:<token>` is a live session credential and `spin aka logs` retains 7 days by default; a key-logging design would put working session tokens in a week-long retention window. `redirect` does log the raw **slug** (not the key), deliberately — correlating a slow resolution to a specific link is the entire point of instrumenting that path, and slugs are already treated as non-secret (see "Security tradeoffs" below). `api` logs only a route **template** (e.g. `/api/users/{username}`, `/api/links/{slug}/analytics`) — the actual username or slug embedded in the URL never reaches the log line.

**`redirect`'s off path is deliberately byte-identical to the uninstrumented component**, at **5 KV operations per successful redirect** (2 `open`, 2 `get`, 1 `set`) and **2 for a miss** (1 `open`, 1 `get`) — see "Analytics"/"The `/r/{slug}` status contract" above for how this profile evolved. When no collector is attached, KV calls go straight to the real `*kv.Store` with no wrapper and no timer calls at all — never a wrapped-but-no-op collector — which is what keeps the off path cheap, not merely silent. The collector itself is **never a package-level variable** in either language: it's attached to the Go request's `context` (via a nil-safe `collectorFrom(ctx)` helper) or passed as an explicit `_dispatch(self, request, collector)` parameter in Python, because `componentize_py_async_support.spawn` dispatches each request independently and a shared collector would silently interleave concurrent requests' operations into one another's line — confirmed live: a 20-way concurrent burst against one slug produced exactly 20 correctly-isolated log lines.

**A new pure Python module for this lives at `api/obs.py` — never `logging.py`, and the same rule applies to any future module named after a stdlib module (`time.py`, `json.py`, ...).** `componentize-py` compiles `app.py` alongside its siblings with the component's own directory on the import path, so a module shadowing a stdlib name would break every stdlib module that imports the real one, for the whole component.

### Observable KV failures: unconditional failure lines, independent of `log_level`/`X-SS-Debug`

A SECOND, separate line kind exists alongside the summary line above: one sanitized failure line per distinct KV operation failure or unhandled exception, emitted to stderr on failure only — **completely independent of `log_level` and of whether `X-SS-Debug` was sent.** Deliberate, not an oversight of the toggle doctrine above: the summary line's gating exists because it costs ~130 bytes on *every* request at a sustained rate, while a failure line costs nothing on the success path and only fires on a fault that has repeatedly failed to reproduce on demand under tracing — gating a diagnostic behind the very toggle it exists to catch failures without would defeat the point.

**Vocabulary: `ev=kv_fail` and `ev=exc`.** `ev=kv_fail` is a single KV operation failure (an `open`/`get`/`set`/`delete`/`exists`/`get_many` raising) — `redirect`'s `openTimedStore`/`Resolve` fault arms and `api`'s `PrefixedStore`/`scoped_get_many`. `ev=exc` is `api`'s catch-all `except Exception`, carrying `etype` and `at=<file>:<line>` (the innermost traceback frame — never a traceback, never source text) instead of `op`/`ns`/`op_us`. Neither line kind has an `ev` field on the pre-existing summary line — the two are additive and structurally distinct (`grep 'ev=kv_fail'` and `grep 'ev=exc'` cannot collide with a summary line, which has no `ev` field at all).

**`msg` is always the final field, and NOTHING may ever be appended after it.** The message is unquoted and may contain spaces; any flag about it (`msg_redacted=1`, `msg_truncated=1`) goes *before* `msg`, never after. This is enforced by construction: `render_failure_line`/`RenderFailureLine` are separate functions from `render_log_line`/`RenderLogLine`, specifically so nothing (a `dur_us`, a `kv_ops` summary, anything) can ever land after the message field the way it can on the summary line.

**The message is sanitized by construction — never logged raw — and `msg_redacted=1` is the greppable answer to "does an Akamai KV error string ever embed a key?"** Three rules, in order, in both languages (`api/obs.py`'s `sanitize_error_message`, `redirect/linkgate/obs.go`'s `SanitizeErrorMessage`): redact any key-shaped substring (`[A-Za-z][A-Za-z0-9_-]*:[^\s'")\]]+`) to `[key:<leading-word>]`; redact any `pbkdf2_sha256`-bearing token to `[hash]`; replace control characters/newlines with `_`; then truncate to `MAX_ERROR_MESSAGE_CHARS` (200), setting `msg_truncated=1`. The key-shaped redaction is complete for keys because of an existing invariant, not luck: every physical key this app sends is prefixed (`kvprefix.STORE_PREFIXES`; `keys.go`'s `LinkKey`/`CountShardKey`), so a host that echoes a key echoes a prefixed one. Whenever either redaction fires, `msg_redacted=1` is set — obtainable with no key ever having reached the log, which is the entire point: a raw `str(exc)` could embed `users:session:<token>`, a live 7-day-retained credential, and nobody had checked until this sanitizer made the question answerable without the risk.

**Bounded differently in the two components, deliberately — "rare failure, negligible volume" does NOT hold per-request in `api`.** A single throttled 50-row bulk create can fail the same write up to 150 times in one request, so `make_failure_reporter` deduplicates on `(op, ns, etype, msg)` and caps at `MAX_FAILURE_LINES_PER_REQUEST = 3` distinct tuples per request — a fresh reporter and dedup set built once per request, never module-level. In `redirect`, a read failure is at most one per request by construction, but request rate is 1,000+/s with unbounded instance count, so a per-request cap wouldn't bound anything — instead a package-scope, mutex-guarded `map[string]struct{}` deduplicates on `(op, msg)` per Wasm instance, capped at 32 pairs for the instance's life. **This is not the forbidden shared-collector pattern** — a shared `Collector` is forbidden because it accumulates per-request statistics that must never cross requests; this map accumulates nothing about any request, so it doesn't matter which concurrent request wins the race to insert a tuple. See the comment beside `failureDedupMu` in `redirect/main.go`.

**The collector still structurally cannot accept a key — this section changes nothing about that.** `PrefixedStore.on_error`/`scoped_get_many`'s `on_error` and `redirect`'s `emitFailureLine` all take `(op, namespace, duration_ns, exc)`; nothing here has a parameter that could carry a key, and nothing is recorded into `obs.Collector`/`linkgate.Collector` on a failure — a traced line's `kv_ops`/`kv_us`/`kv_bytes` stay byte-identical to before this section existed, because the whole point of this change is diagnosis, not altering what tracing already measures.

## Parallel KV reads

**On Akamai the host genuinely overlaps concurrent KV reads, and a handler that awaits one read at a time pays full KV latency per key.** Invisible locally (5–20 µs/op vs 5–20 ms deployed) — only verifiable against a real deployment. `api/kvbatch.py` holds two helpers: `gather_reads` (bounded concurrent fan-out, reads only) and `scoped_get_many` (a single `wasi:keyvalue/batch` `get_many` host call for K keys in one namespace). `analytics.handle_click_totals`/`handle_analytics`, `links.handle_list`, `bulk.handle_bulk_create`/`handle_bulk_action` and `consistency.collect` use `scoped_get_many`; `backup.handle_export` deliberately still uses `gather_reads` (see below).

**Which to use:** `gather_reads` for heterogeneous coroutines or `exists` probes, which have no batch equivalent (`analyticsorphans`' liveness pre-check is the one remaining user). `scoped_get_many` for a set of plain key reads in one `PrefixedStore` namespace — it collapses K host round trips into one, which `gather_reads` cannot do.

**`gather_reads`**: bounded at `MAX_CONCURRENT_READS = 100` (empirical — the largest fan-out actually measured working, where effective parallelism was still *rising* rather than saturating; raise only with a fresh measurement, since the read cap is app-wide), order-preserving (load-bearing: `backup.py` zips results against its key list, and `scoped_get_many` uses it as its per-chunk fallback).

**`scoped_get_many` normalises `get_many`'s two hostile host semantics into `dict[str, bytes | None]` containing every requested key.** Requires a `PrefixedStore` (raises `TypeError` otherwise), builds physical keys internally, drops any key not carrying the view's prefix, de-duplicates the request. **Local Spin omits an absent key from the reply; Akamai returns it as `(key, None)`** — both measured, both absorbed into an identical result. **The reply is never assumed to preserve request order** (measured reordered on Akamai) — it's always keyed by name, never zipped positionally; `api/tests/test_kvbatch.py` pins this with a mutation check (swap the keyed merge for a positional zip, confirm three tests fail).

**The bindings are SYNCHRONOUS, unlike Spin's own KV bindings.** `wasi_keyvalue_batch...get_many` and `wasi_keyvalue_store...open` are plain `def`, not `async def`, so `scoped_get_many` chunks **sequentially** at `MAX_KEYS_PER_GET_MANY = 1000` and is `async def` purely for call-site uniformity. That cap was chosen comfortably inside a measured working range of K=100–5,000 (flat ~10 ms latency at K=1,000; K=10,000 fails with `Error_Other`) — raise only with a fresh measurement.

**`get_many(K)` does NOT bill as K reads against Akamai's 1,000 RPS app-wide read cap** — confirmed by a positive/negative control pair (10×200 single gathered reads/s throttled 9/10; 10×`get_many(500)`, 5,000 keys/s, throttled 0/10). This retires `handle_click_totals`'s read-cap problem for every batched path — at the modelled ~6,100-key ceiling for a busy dashboard load, that collapses to a handful of chunked host calls. It does **not** touch the separate `list_keys` enumeration cost below, which `get_many` cannot address at all.

**The `spin.toml` `key_value_stores` allowlist still applies to a wasi-opened bucket.** `get_many` needs a `wasi_keyvalue_store.Bucket`, a different WIT resource from `spin_key_value.Store`, so `api/app.py` opens a second handle lazily, at most once per request, in a per-request closure, never at module level (same reason as `obs.Collector`: `Handler.handle()` dispatches each request through `componentize_py_async_support.spawn`). Opening `"users"`/`"links"` directly through this interface is refused; only `"default"` opens — no new security hole, `kvprefix.py`'s prefixing remains the only namespace boundary.

**Writes are still never batched — the reasoning is unchanged from `gather_reads`'s original rule, and stronger for `set_many`/`delete_many`, which don't exist in this codebase.** A batch of K writes either still counts as K against the 50/s cap (batching hides nothing) or doesn't (one handler could blow the shared write budget), and the WIT disclaims atomicity for batched writes, which would turn every "a record's existence is the only truth" interruption story into a partially-applied batch with no way to know what landed. `backup.py`'s restore loop and every bulk handler's writes stay sequential. **This asymmetry is the entire safety argument for every change in this section.**

**`api/obs.py` diverges from `redirect/linkgate/obs.go`'s op-type vocabulary by design.** `Collector.record` gained `num_keys=1`; `_KV_OP_ORDER` gained `get_many`/`get_many_error`. `redirect/linkgate/obs.go`'s `kvOpOrder` was NOT touched — `redirect` never batches, so a Go-side field would be dead code. Nothing pins the two vocabularies against each other (unlike `keys.go`'s prefixes/`CountShards`) — deliberate and permanent.

**`kv_ops` counts host operations; `kv_keys` is the number to watch for a batched request.** One `get_many` call covers K keys but is one host op, so `kv_ops` alone understates a batched request's cost. `render_log_line` emits `kv_keys=<n>` only when it differs from the op total, so a non-batching request's line is unchanged. `handle_click_totals`'s traced `get` count now reads `1` forever, so the monitoring trigger this file used to name ("a traced `get` count above ~500") moves to `kv_keys`, same threshold (see TASKS.md's cached-totals-blob entry).

**A memoized enumeration records NO operation.** `api/app.py` builds one memoized raw `get_keys` walk per request (`kvprefix.memoized_raw_list_keys`) so `handle_click_totals` pays for one whole-store walk rather than two; `scoped_list_keys` skips recording when the raw callable reports `cache_hit` (read via `getattr(..., False)`, so non-memoized call sites are unaffected). Don't "fix" this by recording cache hits under their own op name — `Collector.totals()` sums every op type into `kv_ops`, and the memoization's effect is already visible as `list_keys=1` instead of 2.

**`backup.handle_export` deliberately still uses `gather_reads`, not `scoped_get_many` — a byte-safety decision.** The `get_many` measurement above only exercised small blobs (~1.9 KB analytics shards); `handle_export` is the one call site whose store can legitimately hold values near Akamai's 1 MB max, and a 1000-key chunk there could be up to ~1 GB in one host call/HTTP response, against Akamai's 10 MiB request/response limit. Export already performs well on `gather_reads` (999 ops, 48,135 ms summed KV time inside 957 ms wall, 50.3× overlap), so there's no latency pressure forcing an unmeasured change. Revisit only with a real byte-ceiling measurement at backup-realistic value sizes, using a materially smaller constant than 1000.

**`consistency.collect` fetches its two stores asymmetrically, on purpose.** The **links** store is fetched wholesale, including keys the loop classifies as `unrecognized` and discards (an allowlist there would have to restate the loop's own branch conditions). The **users** store gets an explicit two-shape allowlist (`_meta:usernames`, `session:*`) instead, because a `user:` record's value holds a PBKDF2 hash and no check needs to read one. **Do not "simplify" the users side to match the links side** — `test_collect_never_even_reads_a_user_record_value` asserts `get()` is never called on a `user:` key at all; `test_handle_consistency_never_leaks_password_hash` would not catch a regression here.

**A key enumeration costs the whole physical store, and gathering cannot hide it.** `scoped_list_keys` calls `raw_list_keys(store.raw)` and filters by prefix afterward, so enumerating any namespace walks every key in the `default` store. Measured linear: **`list_keys` costs ~68.7 µs per physical key, plus a fixed floor of about one KV round trip (~24 ms)** (R² = 0.997 across four store sizes spanning 10.4×; confirmed by purging a store from 968 to 57 keys and seeing the cost drop to the floor, not to the ~1 ms a zero-intercept fit would predict). **There is no prefix-scoped enumeration** — `get-keys()` takes no arguments at all (no prefix, no cursor, in either SDK), so any fix must avoid the enumeration, not narrow it.

**Practical consequence: every key in the store costs ~69 µs on every dashboard load.** ~14,100 keys (~150 links at the up-to-94-keys-per-link ceiling) puts a full second of enumeration on every dashboard load; ~1,000 links puts ~6.5 s there. The `events:` ring-buffer write was dropped 2026-08-18 (see "Analytics"), cutting analytics key growth by a modelled 32–48% — a slope change, not a shape change: the ~250 ms `list_keys` trigger for `GET /api/links` noted in `docs/plans/derived-link-indexes.md` still stands, just reached later.

**Proven by `Server-Timing`, not inferred**: `kv` (sum of per-op durations) exceeding `handler` (wall time) is arithmetically impossible under serial execution. Measured overlap ranges 2.7×–50.3× across `GET /api/links`, `GET /api/admin/backup`, and `GET /api/admin/consistency` — and **wall time for `GET /api/links` stopped scaling with link count** once gathered (~173 ms at 50 links vs ~178 ms at 14, replacing a pre-change ~23 ms/link linear cost). Effective parallelism rises with fan-out rather than saturating in every case measured so far — an empirical property of this host, not a guarantee; re-measure rather than extrapolate if link/shard counts change materially.

**Still unfixed: `GET /api/links` has no pagination.** Gathering converts ~23 ms/link into roughly a constant, but the handler still issues one read per link — a large deployment fires one bounded burst per dashboard load. Pagination is the real answer if link counts ever get large.

## Security tradeoffs (accepted for v1)

These are deliberate, disclosed limitations, not oversights — each stems from a real architectural constraint (no outbound network from either component by default, no atomic KV operations) rather than an easy fix that was skipped.

- **No brute-force rate limiting on login or link passwords.** Neither `redirect` nor `api` has any `allowed_outbound_hosts` entries (confirmed: Spin denies all outbound HTTP by default when the key is omitted from a component's manifest), so neither component can reach an external atomic rate limiter (e.g. Redis `INCR`/`EXPIRE`). A KV-based attempt counter would be racy under concurrent requests anyway, since Spin's KV interface has no compare-and-swap. The only real mitigation in place is the PBKDF2 cost factor itself (100,000 iterations) slowing down each individual guess. If this becomes a real requirement, it needs a deliberate `allowed_outbound_hosts` expansion plus an external rate-limiting service — not a quiet KV-counter bolt-on.
- **Slug/link existence and password-protection status are enumerable.** A `404` (no such slug) vs. a `200` password prompt vs. a `302` redirect inherently tells a probing visitor whether a slug exists and whether it's password-protected. This is treated as an accepted characteristic of a public redirect service, not a vulnerability to fix — slugs aren't meant to be secret. Custom slugs are more guessable than random ones; pairing a custom slug with a link password is a sensible pattern worth surfacing in product UX, not something to enforce in code. **What stays indistinguishable, and what does not, since `docs/plans/redirect-read-failure-not-404.md`:** an absent slug, a disabled one, and one outside its `[start_at, end_at)` window all still produce a byte-identical `404` — that trio is deliberately never teased apart. Two disclosures are newly accepted in exchange for making the `/r/{slug}` status contract honest (see "The `/r/{slug}` status contract" above): a `500` reveals that a slug has a record which will not parse (accepted because it's not attacker-controllable — only `api` writes link records, and always valid JSON — and the same fact is already exposed on six authenticated `api` paths as `422 link_record_unreadable` and in the consistency report as `unreadable_value`); and a `503` reveals that the store is momentarily saturated (accepted because throughput and latency already tell a prober that, and 503 is the correct, standard answer to it — it is also emitted from a state of genuine ignorance about the link, so it cannot leak a fact the process never learned).
- **Security response headers are set** (CSP, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, HSTS) by `redirect`, `api`, and `gui-pages` — see "Security response headers" above. **There is no `'unsafe-inline'` anywhere in the application.** This is no longer a tradeoff entry at all, kept here only as a pointer.
- **Click counts are accurate below the app-wide ~50 clicks/second ceiling and lossy above it** (see "Analytics" above). The per-link contention that used to dominate — 25% loss at 9.4 clicks/s on one link — is fixed by 64-way counter sharding. What remains is Akamai's 50 KV writes/second app-wide cap, which sharding cannot touch and which binds across the whole service rather than per link — accepted as the cost of a KV-only, no-network hot path.
- **Reversible link passwords are not supported** — they're hashed one-way, so a link's creator can never have the plaintext redisplayed. If "show me the password I set" UX is ever wanted, that requires a materially different storage model (encryption with real key management), not a tweak to the current hashing approach.

## Deployment: Akamai Functions

The former blocker is resolved: `docs/plans/kv-store-consolidation.md` moved both `redirect` and `api` onto Spin's single auto-provisioned `"default"` KV store (see "KV store: the single `default` store and the prefixing view" above), which is the one thing Akamai Functions requires that the three-named-store design couldn't provide. **That consolidation would have silently handed the KV explorer the `users` keys, and it did — deliberately, on the user's decision.** See the `kv-explorer` bullet under Architecture for the accepted-exposure record; nothing further to do here.

**Confirmed quotas** (`techdocs.akamai.com/akamai-functions/docs/quotas-and-limits`, fetched 2026-08-04):

| Quota | Default limit |
|---|---|
| Memory (RAM per execution) | 128 MiB |
| **App size** | **50 MiB** |
| **Request handler duration** | **30 seconds** |
| Request/response size | 10 MiB |
| KV storage (all stores) | 2 GB |
| **KV read requests per app** | **1,000 RPS** |
| **KV write requests per app** | **50 RPS** |
| Max value size | 1 MB |
| Max key size | 8 KB |

The same page: SQLite storage, Redis triggers, wasi-blobstore, wasi-messaging and custom triggers are not supported, and **runtime configuration is unavailable** — `runtime-config.toml` has no deployment role at all there (it's read only by the local Spin CLI). Whether the 50 MiB app-size limit is compressed and/or per-component, and whether the RPS defaults above apply to any given account, are **unconfirmed** — raise both with Akamai directly before relying on them for production traffic.

**`wasi:keyvalue/batch`'s `get_many` is supported and does NOT bill as K reads against the 1,000 RPS cap** — confirmed measured (see "Parallel KV reads" above for the full mechanism and call sites). Akamai's own docs confirm the interface is supported but say nothing about its quota accounting, so this was verified with a positive/negative control pair rather than assumed.

**Deploy commands** (`techdocs.akamai.com/akamai-functions/docs/quickstart`, `docs/deploy-app-variables`):

```bash
spin plugin install aka
spin aka login
spin aka app deploy --app-id <app-id> --build --no-confirm \
  --variable admin_bootstrap_password=<pw> \
  --variable cookie_secure=true \
  --variable public_base_urls=https://<app-id>.fwf.app \
  --variable log_debug_token=<token-or-omit> \
  --variable app_version=<sha-or-label>
```

**Verified against the real CLI (`aka` plugin 0.7.4).** The subcommand is `spin aka app deploy`, not `spin aka deploy`; it takes `--app-id`, not `--app-name` (unlike `spin aka app status`, which takes `--app-name` and rejects `--app-id`'s positional form — the two subcommands genuinely differ); and it requires `--no-confirm` in any non-interactive shell, otherwise it fails with `No terminal available for interactive selection`. `--build` replaces the separate `spin build`. Find the app id with `spin aka app list` then `spin aka app status --app-name <name>`.

**Every response from `redirect`, `api` and `gui-pages` carries `X-SS-Version`**, whose value is the `app_version` Spin variable (default `"unknown"`). Pass it at deploy time — `--variable app_version=<sha-or-label>` — and **`curl -sI https://<app>/` then answers "which build is live?" with no auth and no debug token.** This exists because of the readiness-check behaviour described next: without it, the only way to tell whether a deploy had propagated was to probe for a behavioural difference, which is circular when the behaviour you are testing *is* the change. It is attached in each component's `app.py`/`setSecurityHeaders` rather than in the shared `SECURITY_HEADERS` dicts, because it comes from a Spin variable and `api/responses.py`/`gui-pages/routing.py` deliberately import nothing from `spin_sdk`. The value is opaque and operator-chosen, so how much it reveals about the build is the operator's call.

**`spin aka app deploy`'s readiness check times out at 60 seconds and reports `Error: failed to wait for deployment to go live` — this is NOT necessarily a failed deploy.** The deploy can succeed and go live shortly after the CLI gives up, with the new version already recorded in `spin aka app history`. **Do not redeploy on seeing this.** Check `curl -sI https://<app>/` and compare `X-SS-Version` against the `app_version` you passed — `spin aka app history` records a version row before the build is actually serving, so the header is the authoritative signal. A request made during the propagation window returns the OLD build, which can look like a clean negative result for a change that's actually working.

**Setting `log_debug_token` at deploy time is the only way to trace the deployed build**, and it cannot be added or changed later without another deploy. Omit the variable to restore the default `""`, which never matches. A deployed build whose token you do not know cannot be traced at all — which is why a "compare against a pre-change trace" verification has to take its baseline locally instead.

Three variables must be set on every deploy: `admin_bootstrap_password` (required secret, no default — seeds the first admin), `cookie_secure=true` (the local-dev `false` override must NOT ship — see "Commands" above), and `public_base_urls` pointing at the real deployed app URL (see "Multi-domain display" above for the silent-fallback-to-`localhost` trap if this is ever renamed or misconfigured on upgrade). Whether a `secret = true` variable like `admin_bootstrap_password` can be supplied through `--variable` is unconfirmed until a deploy is actually attempted.

**Upgrading an existing deployment is a backup → deploy → restore, never in-place**, because the KV store consolidation changed the physical key space (unprefixed `slug:<slug>` under three named stores → prefixed `links:slug:<slug>` under `default`) — a build from before the consolidation and one from after are reading disjoint physical keys. The backup file format needs no conversion for this: it already speaks logical store names and unprefixed keys, and `kvprefix`'s views map them onto the new physical keys transparently on the way in (`api/tests/test_store_isolation.py`'s pre-consolidation-fixture test pins exactly this). Concretely: `GET /api/admin/backup` on the old build, deploy the new build, `POST /api/admin/restore` with `{"confirm": "REPLACE", ...}` against it.

**Two operating ceilings this deploy surfaces, both a direct consequence of the 50 write RPS cap:**

- **Sustained redirect throughput ceilings around 50/second, manifesting as silent click loss rather than an error — the real and sole binding constraint on click accuracy now that the counter is sharded.** Since a recorded click performs one write (`analytics:count:<slug>:<shard>` only, since the events write was retired 2026-08-18), 50 write RPS / 1 write per click ≈ 50 redirects/second before writes are throttled. Any measurement above ~50 requests/second measures this cap rather than counter accuracy — use `dev/click-load.sh`, which computes the implied write rate and warns at 50. Reads (2 per click) are nowhere near the 1,000 RPS read cap. **This ceiling shouldn't be quoted without a fresh measurement**: a click costs ~95-120 ms of handler time on Akamai, mostly KV, so reaching 50 write RPS at all requires many concurrent in-flight requests — latency/concurrency may be the real binding constraint, not the write cap. Confirm against real load before asking Akamai for a rate increase.
- **A full-cap 5,000-entry restore (`MAX_BACKUP_ENTRIES`) needs roughly 100 seconds of writes at 50 write RPS and cannot complete inside Akamai's 30-second handler duration**, even though the same restore measured 84 ms locally. Restore is still sequential and must stay that way — writes are cap-bound, so gathering them would queue against the cap rather than overlap. Bulk create at its own 50-row cap (~100 KV ops) is fine. Chunked/resumable backup-restore is listed under `TASKS.md`'s Future work if real data ever exceeds what one request can move.
  - Export is **not** read-bound-and-safe the way a naive RPS calculation suggests: a sequential `for key in keys: await store.get(key)` is latency-bound (~20-50 reads/second, not 1,000), and a traced export over just 14 links (926 analytics keys) summed to 48s of KV time across 999 operations — at the 30s handler limit. **Export's read loop is now gathered** (`api/kvbatch.py`), measured at 999 ops, 48,135ms of summed KV time inside 957ms of wall — 50.3× overlap, no longer close to the handler limit. `GET /api/links` and the consistency walk use the same helper; see "Parallel KV reads" above.
