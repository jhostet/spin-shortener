# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`spin-shortener` is a polyglot WebAssembly URL shortener built on [Spin](https://spinframework.dev) (Fermyon's WASI HTTP framework), with three independently-built components composed via `spin.toml`. Shipped functionality: auto-generated and permission-gated custom short links, optional per-link passwords, optional start/end time windows, per-link QR codes (SVG/PNG), click analytics (totals, per-day, a best-effort recent-events sample), local username/password auth with session cookies, and admin user management. See `TASKS.md` for the full phase-by-phase build history and `README.md` for a user-facing overview.

## Architecture

`spin.toml` is the single source of truth for routing and build wiring. It defines four Wasm components across six HTTP triggers (two components — `gui` and `gui-pages` — split the GUI's routes between them):

- `route = "/r/..."` → **`redirect`** component (`redirect/`, Go) — resolves short links and issues redirects; the hot path, hit on every click. Built with `go tool componentize-go build`, compiling `redirect/main.go` (+ `passwordgate.go`, the embedded `prompt.html`, and the pure-logic `redirect/linkgate/` package) to `redirect/main.wasm`. Uses `github.com/spinframework/spin-go-sdk/v3/http` and registers a handler via `spinhttp.Handle`. `allowed_outbound_hosts = []` — no outbound network access, by design (see "Security tradeoffs" below for what this rules out). `key_value_stores = ["default"]` — see "KV store: the single `default` store and the prefixing view" below.
- `route = "/api/..."` → **`api`** component (`api/`, Python) — all authoring/auth/analytics logic: link CRUD, custom slugs, passwords, time windows, QR generation, analytics aggregation, local auth/sessions, and user management. Built with `uv run componentize-py -w spin:up/http-trigger@4.0.0 componentize app -o app.wasm`, compiling `api/app.py` (the WASI entrypoint/router) plus `auth.py`/`links.py`/`qr.py`/`analytics.py`/`users.py`/`responses.py`. Uses `spin_sdk.http.Handler`. `key_value_stores = ["default"]` — see "KV store: the single `default` store and the prefixing view" below.
- `route = "/app.js"`, `route = "/theme.css"`, `route = "/vendor/pico.min.css"`, `route = "/theme-init.js"`, plus one route per page-scoped asset (`/index.js`, `/login.js`, `/dashboard.js`, `/dashboard.css`, `/admin/users.js`, `/admin/users.css`, `/links/detail.js`, `/links/detail.css`) → **`gui`** component — a prebuilt static file server (`spin_static_fs.wasm`, fetched by digest from the `spin-fileserver` GitHub release) serving only these genuinely-static, non-HTML assets. Its `files` mapping still covers all of `gui/` (unchanged from before the route split — narrowing it broke file resolution, see below), but only these 12 exact routes are actually reachable. The 8 page-scoped ones exist because the CSP dropped `'unsafe-inline'`; adding a page's asset without its route serves a fully-rendered page whose script silently 404s. `/theme-init.js` is a different shape from the other 11: it isn't scoped to one page, it's loaded by every page (the light/dark theming bootstrap — see "Theming" below), so it lives in the same "Per-page scripts and styles" comment block in `spin.toml` but isn't actually page-scoped. **Route gotcha, confirmed live:** once this component has more than one trigger route, `spin_static_fs`'s internal path resolution breaks specifically for wildcard (`/...`) routes — a `/vendor/...` wildcard 404'd on every request; the identical file under the exact route `/vendor/pico.min.css` served correctly. Stick to exact routes for this component if any more assets are ever added to it.
- `route = "/..."` (catch-all) → **`gui-pages`** component (`gui-pages/`, Python, same `componentize-py` toolchain as `api`) — serves the GUI's actual HTML pages (`index.html`, `login.html`, `dashboard.html`, `admin/users.html`, `links/detail.html`) via a fixed path→file allowlist (`gui-pages/routing.py`), and attaches the security response headers below to every response. Introduced specifically because `spin_static_fs` has no custom-header capability at all (confirmed: only a `CACHE_CONTROL` env var) — security headers (CSP, `X-Frame-Options`, etc.) are only meaningful on the navigated document itself, not on a `.js`/`.css` subresource, so only the actual HTML pages needed to move off the static-fileserver.

A fifth component exists for local development only and is **deliberately absent from `spin.toml`**:

- `route = "/internal/kv-explorer/..."` → **`kv-explorer`** — [Fermyon's prebuilt KV explorer](https://github.com/fermyon/spin-kv-explorer) (v0.10.0), third-party and unmodified, added by URL + digest exactly like `gui`'s `spin_static_fs.wasm`. It browses raw key-value contents so store data can be verified during development. It lives in `dev/kv-explorer.toml`, which `dev/kv-explorer-up.sh` concatenates onto a copy of `spin.toml` to produce a gitignored `spin-dev.toml` on every local run — so the dev manifest can never drift from the real one, and `spin deploy` has nothing to pick up. **The reviewer's check is `grep -c kv-explorer spin.toml` → `0`**, and `gui-pages/tests/test_manifest_components.py` fails CI if the committed manifest ever gains a fifth component (a `tomllib` set comparison, not a grep — `grep -c '^\[component\.' spin.toml` returns 9, not 4, because sub-tables like `[component.api.build]` match, so a grep guard would never fire).
  - **It has full CRUD over the single `default` store** — every key in the app, `links:`/`users:`/`analytics:` prefixes included. It can overwrite and delete any key with no undo. That is deliberate (repairing bad local test data is half its value), but a stray click destroys local data.
  - **Since `docs/plans/kv-store-consolidation.md` collapsed the three named stores onto Spin's single `"default"` label (required by Akamai Functions, which allows only that one label), there is no longer any store-level separation for this component to respect.** Before that change, `users` was deliberately withheld via the `key_value_stores` list — the explorer takes the store name straight from the request path (`/api/stores/:store`) and hands it to `kv.OpenStore` with no allowlist of its own, so that list was the only thing enforcing it, at the Spin host boundary rather than in the UI. Granting `["default"]` grants everything in one grant, `users:user:*` PBKDF2 hashes and `users:session:*` tokens included — full read and write access to exactly the material that used to be withheld. This is accepted, not overlooked: the user explicitly chose it over inventing a config seam (e.g. a variable toggling one-store vs. three-store mode) to preserve the old separation, on the reasoning that a deployed-vs-developed configuration mismatch is a worse property to own than a dev-only credential exposure in a tool that already has full CRUD over everything else. It is acceptable *only* because this fragment is never part of a deployed manifest — the committed `spin.toml` has four components and no explorer, and `gui-pages/tests/test_manifest_components.py` fails CI if that ever stops being true. Confirmed live: listing keys in the `default` store now returns `users:user:admin`, `users:_meta:usernames`, `users:session:*` and every other prefixed key, where the old three-store split returned `500 access denied` for `users` specifically.
  - `allowed_outbound_hosts = []`, narrowed from upstream's `["redis://*:*", "mysql://*:*", "postgres://*:*"]` (those exist only for externally-backed KV; this app's store is sqlite-backed). Verified sufficient live.
  - Basic auth is required even locally rather than using upstream's `SPIN_APP_KV_SKIP_AUTH=1`: `--env` reaches every component, and unauthenticated CRUD on localhost is reachable from a cross-origin `text/plain` POST, since upstream's `AddKeyHandler` never checks `Content-Type`. Username defaults to `kv`; the password is a required secret variable.
  - **Whether local KV persists depends entirely on whether you pass `--runtime-config-file`, and the counter-intuitive part is that passing it is the NON-persistent option.** Measured on Spin 4.0.2, 2026-08-07, reading the startup log line each time:

| command | Spin logs | persists across restarts? |
|---|---|---|
| `spin up --build` (no runtime config) | `Storing default key-value data to ".spin/sqlite_key_value.db"` | **yes** |
| `spin up --build --runtime-config-file runtime-config.toml` | `Storing default key-value data to a temporary in-memory store.` | **no** |
| same, but with `path = "..."` added under `[key_value_store.default]` | `Storing default key-value data to "<path>"` | **yes** |

  **`type = "spin"` with no `path` means in-memory in Spin 4.0.2** — `runtime-config.toml`'s own comment calling it "Spin's built-in sqlite-backed local store" is wrong, as is the "Commands" section's claim that passing the flag keeps the local backing provider "explicit" rather than changing it. **The documented command passes the flag, and `dev/kv-explorer-up.sh` always passes it**, so anyone following the docs — and every KV-explorer session — gets a store wiped on every restart. That is what the earlier "Local KV appears to be non-persistent" note in this file was actually observing; its stated reason (no `.db` file exists anywhere) was wrong, and it did not notice the behaviour was conditional. A `path` is resolved **relative to the runtime-config file's own directory**, not the working directory. Adding one to `runtime-config.toml` would make the documented command persistent; that has not been done, because a wiped-per-run dev store is a defensible default and changing it is a behaviour decision, not a typo fix.
  - **When it is sqlite-backed, the file is an ordinary SQLite database** with a single `spin_key_value(key, value)` table, so `sqlite3` or Python's `sqlite3` module reads it directly — often faster than the KV explorer for a one-off check, and how the sharded click counter's key distribution was verified. `.spin/` is gitignored.

Each component is built independently and only in its own `workdir`; there is no shared build step or root-level package manifest. When editing one component, you generally don't need to touch the others' toolchains.

**Why Go for `redirect` but Python for `api`/`gui-pages`:** the redirect path is the hot path (every short-link click) and is written in Go for raw performance. The `api`/`gui-pages` surfaces (link creation, management, frontend) aren't on that hot path, so they're written in Python to prioritize developer velocity and code understandability over raw speed — the performance tradeoff isn't worth it there. Keep this split in mind when adding new functionality: if it's on the redirect hot path, it likely belongs in the Go component; otherwise default to Python for velocity.

`redirect/main.wasm`, `api/app.wasm`, and `gui-pages/app.wasm` are all build artifacts and are gitignored — they must be rebuilt via `spin up --build` (or the per-component build commands in `spin.toml`) after any source change; they are not checked into the repo.

### KV store: the single `default` store and the prefixing view

Since `docs/plans/kv-store-consolidation.md`, both `redirect` and `api` declare `key_value_stores = ["default"]` — Spin's single auto-provisioned store, required because Akamai Functions (the intended production target) allows only that one label. The app still has three logical namespaces (`links`, `users`, `analytics`); they're kept apart by prefixing every physical key (`links:slug:<slug>`, `users:user:<username>`, `analytics:count:<slug>:<shard>`, …) rather than by store name.

- **`api/kvprefix.py` is the only Python module that knows prefixes exist.** It exposes `PrefixedStore` (a `get`/`set`/`delete`/`exists` view over one namespace), `open_views(physical_store)` (returns the `{"links", "users", "analytics"}` view dict `api/app.py` binds once per request), and `scoped_list_keys(raw_list_keys)`. `links.py`, `auth.py`, `users.py`, `bulk.py`, `backup.py`, `consistency.py`, `urlpolicy.py` and `analytics.py` are all unaware of it and take a `store` parameter exactly as before.
- **`scoped_list_keys` is a security control, not tidiness.** It filters a raw physical-key enumeration down to one namespace's keys (prefix stripped) before any caller sees them. `backup.py`'s redaction/exclusion guards and `consistency.py`'s key-shape classification are all written against unprefixed keys, so an unfiltered enumeration would silently defeat every one of them — the concrete failure being a full PBKDF2 account hash written into a links-only backup.
- **`PrefixedStore` deliberately has no `get_keys` method.** Omitting it turns "a caller tried to enumerate through a view" into an `AttributeError` instead of a cross-namespace credential leak; enumeration only ever happens through `scoped_list_keys`, which additionally raises `TypeError` if handed the physical store directly instead of a view.
- **`redirect/linkgate/keys.go`** mirrors the Go side: `LinksPrefix`/`AnalyticsPrefix` constants (deliberately no `users:` one — the redirect component has no business constructing a users key) and `LinkKey`/`CountShardKey`/`EventKey` builders. It must stay byte-identical to `kvprefix.STORE_PREFIXES`, or the API writes links the redirect path can't find with no error anywhere — `api/tests/test_kvprefix.py` reads `keys.go` from the Python test suite and pins the two sides' equality as a CI-time guard rather than a runtime one.
- **`keys.go` also holds `CountShards = 64`, which is a second cross-language value with the same pinning obligation** — it must stay equal to `api/analytics.py`'s `COUNT_SHARDS`, and the same test file pins it by the same technique. It is not a prefix, but it fails the same way: silently, at runtime, with no error anywhere. **RAISE ONLY, NEVER LOWER** — a reader lower than the writer drops every click recorded into a higher shard. See "Click counting is sharded across 64 keys" under Analytics for why 64, and note that `gui/links/detail.html`'s accuracy caveat quotes a rate figure derived from it.
- The `api`/`gui-pages`/redirect suites cover this mechanism directly: `api/tests/test_kvprefix.py` (the view's four-method surface, the non-overlap invariant, the cross-language guard) and `api/tests/test_store_isolation.py` (the four cross-namespace hazards: a links-only backup can't leak a users hash, a links-only restore prunes only `links:` keys, a pre-consolidation backup fixture restores unchanged, and the consistency check never sees `analytics:` keys sharing the same physical store).

## Security response headers

Every response from `redirect`, `api`, and `gui-pages` sets `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, and `Strict-Transport-Security`. Each component's CSP is scoped to what it actually serves:

- `gui-pages` (the real HTML pages): `default-src 'self'` plus `script-src 'self'` and `style-src 'self'` — **no `'unsafe-inline'`.** Every page's script and style live in a sibling `.js`/`.css` file served by the `gui` component (e.g. `dashboard.html` → `dashboard.js` + `dashboard.css`), so no served page contains an inline `<script>`, a `<style>` block, or a `style="…"` attribute for the policy to have to allow. `gui-pages/tests/test_no_inline_code.py` enforces that — a CSP violation fails a page silently in a browser rather than failing a test, so the guard is what keeps the policy true. Hiding is done with the native `hidden` attribute plus `theme.css`'s `[hidden] { display: none !important; }` (the `!important` is load-bearing — Pico sets `display` on `label`, `nav li`, and buttons, all elements this app hides, and the UA stylesheet's `display: none` loses to them). Every other directive is locked down for real: no plugins/objects, no framing, no cross-origin form submission, no base-tag hijacking. `img-src` includes `data:` because Pico CSS renders several UI affordances (sortable-column chevrons, the search icon, the calendar icon) as inline `data:image/svg+xml` background-images — confirmed live that `img-src 'self'` alone produced real CSP-violation console errors blocking them, caught only by loading the actual pages, not by reading the CSS.
- `api` (pure JSON): `default-src 'none'` — nothing it returns should ever be rendered, executed, or framed.
- `redirect`'s password-prompt page (the one HTML `redirect` renders): the strictest policy in the app — `default-src 'none'`, `script-src 'none'` (the page loads and contains no script at all, deliberately: it is the one page where a visitor types a credential, which is worth more than the OS-following theme that loading `theme-init.js` would buy, so it always renders light), and `style-src 'self'`. It links `/vendor/pico.min.css` and `/theme.css` — already exact routes on `gui`, so styling it cost no new files or routes — and uses `theme.css`'s own `.form-error` for its error message, which is what retired its last inline style attribute and with it the last `'unsafe-inline'` anywhere in the app.
  - **`form-action` must list `https:`/`http:`, not just `'self'`.** A correct password answers the POST with a 302 to the link's target, and Chrome applies `form-action` to that redirect, not only to the form's action URL. With a bare `'self'` the browser silently blocked the navigation: the server sent a correct 302 and the visitor just stayed on the prompt, so **every password-protected link was a dead end in a real browser while working perfectly under `curl`**. The two schemes mirror exactly what `api/links.py`'s target-URL validation accepts, so `javascript:`/`data:` form targets stay blocked.

The `gui` component (the static asset routes above) gets none of these — headers on a `.js`/`.css` subresource response don't provide any real protection the navigated-document headers don't already cover.

**`/internal/kv-explorer/...` sits outside every guarantee in this section.** It is a separate third-party component that sets its own headers, so none of the above applies to it, and its UI contains an inline `<script>` and `<style>` block and loads jQuery, Bootstrap, Popper, Font Awesome and Google Fonts from external CDNs — the opposite of the vendored, `default-src 'self'` posture everything else holds. `gui-pages/tests/test_no_inline_code.py` **deliberately does not cover it**: the file is not ours to fix, so a guard over it could only ever fail, and failing on an upstream binary's markup would be noise rather than signal. This is acceptable solely because the route exists only in a local `spin-dev.toml` and is unreachable in any deployed manifest. If that ever changes, this is the paragraph that has to change with it.

### Redirect caching: `Cache-Control: no-store` and the 302-not-301/308 requirement

Every `redirect` response (302s, 404s, and the password prompt alike) now carries `Cache-Control: no-store`, set once in `setSecurityHeaders` (`redirect/main.go`) rather than at the three individual redirect call sites, so it covers `http.NotFound` too — a cached "not yet active" 404 would mean a not-yet-started link never starts working when its window opens.

**302 is a hard requirement for `/r/{slug}`; 301 and 308 are forbidden.** Akamai edge servers do not cache HTTP 302 (`Found`) or 307 (`Temporary Redirect`) responses by default, but they **do** cache 301 (`Moved Permanently`) and 308 (`Permanent Redirect`) by default (`techdocs.akamai.com/property-mgr/docs/cache-http-redirects`). `redirect/main.go`'s three redirect sites all use `http.StatusFound` (302) today — do not "simplify" this to a 301 for a URL that never changes; that single-line change would make Akamai start caching the response at the edge.

**The `no-store` header is defence-in-depth, not the actual control.** Akamai edge servers do **not** honour origin `Cache-Control`/`Expires` by default, so this header protects against browsers and intermediate proxies — the 302 status code is what actually keeps Akamai's own edge from caching the response. A cached redirect would silently break every one of: the `status` check (a disabled link keeps redirecting), the `[start_at, end_at)` window (a link keeps redirecting past `end_at`), deletion (a deleted slug keeps resolving), repointing (a repointed link keeps serving its old destination), and the destination-policy remediation path (a bulk-Disabled violator keeps resolving instead of 404ing).

**Akamai Functions itself publishes no caching documentation at all** (`docs/caching` 404s), but the behaviour is now **CONFIRMED MEASURED against the live deployment** (2026-08-06, `https://e96461a3-8bfe-4dea-83a5-9fed97601f59.fwf.app`, running the post-consolidation build): **a `*.fwf.app` app does inherit the "302 not cached by default" behaviour.** Twenty requests to one active `/r/{slug}` returned twenty `302`s with twenty *distinct* `akamai-grn` values, no `Age`, `X-Cache` or `X-Check-Cacheable` header on any of them, and an origin service time of 126–165 ms on every single request — a cached edge response would have returned in single-digit milliseconds. The click total moved from 45 to exactly 55 across the last ten, which additionally proves `recordAnalytics` ran and **both** its KV writes succeeded on every request, with no losses to the write-RPS cap at that rate. Fifteen further requests to a nonexistent slug confirmed the same for `404`s, which matters independently: a cached "not yet active" 404 would mean a scheduled link never starts working.

**Now measured directly, not inferred (2026-08-06, deployed logging build, `X-SS-Debug` tracing).** Mean over 6 traced redirects: `kv_us≈116.7 ms` of `dur_us≈120.4 ms` — **KV is ~97% of handler time on Akamai**, against 46% locally. The per-operation split is the useful part:

| operation | Akamai | local | ratio |
|---|---|---|---|
| `open` | ~154 µs | 12–33 µs | ~7× |
| `exists` | 21.7 ms | 13–18 µs | ~1,400× |
| `get` | 21.2 ms | 5–9 µs | ~2,900× |
| `set` | 26.1 ms | 5–12 µs | ~3,000× |

**Treat the absolute milliseconds above as one sample of a moving target, not a constant.** Measured again ~10 minutes later the same day, the identical 7 operations cost **38.8 ms rather than 116.7 ms — a 3× regime swing**, putting per-operation cost somewhere in **5.5–16.7 ms** depending on when you look. Any conclusion that depends on an absolute figure needs re-measuring; only ratios within a single window are trustworthy, and **two measurements taken minutes apart can differ by more than the change you are trying to attribute.** Quote proportions, not milliseconds.

**What is stable is that the cost is per *data operation*, not per store handle** — which inverts two things this repo had concluded from local measurement. First, **removing `recordAnalytics`'s second `kv.Open` is not worth doing**: it looked like an 8–20% win locally and is ~0.2% here. Second, **dropping the `Exists` in `lookupLink` was worth one operation — measured like-for-like at 5.2 ms of 38.8 ms, 13.5%** (done 2026-08-06; a successful redirect is now 6 operations). Third, and now the dominant cost: **`recordAnalytics` is ~78% of the redirect's KV time** (1 `get` + 2 `set`, and the `analytics:count` write is the single slowest operation in every trace). **CORRECTION 2026-08-18: the claim that once stood here — that it runs before `http.Redirect`, so every visitor waits for bookkeeping they have no stake in — is FALSE and has been since `398f391` (2026-08-06).** `sendRedirectThenRecord` in `redirect/main.go` sets `Location`, calls `w.WriteHeader(http.StatusFound)` and writes the body, and only *then* calls `recordClickCount`/`recordClickEvent`; its own comment reads "Both halves after the response." This file simply was not updated with the code, and the stale sentence has since been repeated as a justification for other work — check the code before reusing it. **What remains genuinely open is whether the ordering buys the visitor anything**: under WASI the host may not flush the response to the client until the handler returns, so "written before the KV writes" does not automatically mean "delivered before the KV writes." The 2026-08-06 A/B that motivated the reordering measured *click accuracy* (85 vs 86 of 100), not visitor latency, so **no measurement in this repo establishes the latency benefit either way.** Do not claim it without one. See `TASKS.md` Future work, including why "just make it async" is not automatically available under WASI.

**The earlier, cruder inference that produced these numbers, retained because it is how the question was first opened:** On the same deployment a `404` (2 KV operations) cost 26–40 ms of origin time while a `302` (7 operations) cost 126–165 ms — about **110 ms for the 5 extra operations, ≈22 ms each**, against 5–17 µs locally. Treat the per-operation figure as an inference rather than a measurement: `x-envoy-upstream-service-time` includes the network hop and Wasm instantiation, and the 302 path also does a JSON parse and the count read-modify-write, so the subtraction controls for fixed overhead but not for those. The direction is not in doubt, though, and it reframes the throughput ceiling below — at ~150 ms of origin time per click, latency and concurrency may bind well before the 50 write RPS cap does. **Use the `X-SS-Debug` header (see "Toggleable structured logging") against a deployed build to get the real per-operation split rather than this subtraction** — that is precisely what it was built for, and no build carrying it has been deployed yet.

### The `/r/{slug}` status contract: 404 is for product states, 5xx is for faults

Before `docs/plans/redirect-read-failure-not-404.md`, `lookupLink` collapsed a KV read failure, a genuinely absent key, and an unparseable record into one `false`, which every caller answered with `http.NotFound`. Measured on deployed build `43d66c6-no-events` with `hey -disable-redirects`: 0% wrongly-404 at 690 rps, **7% at 726, 31% at 947, 43% at 1292** — read-path saturation (a successful redirect performs 2 KV gets, so ~700 rps is ~1,400 reads/second against Akamai's documented 1,000/second cap) was being reported to a visitor as "this link does not exist," indistinguishable from a genuinely dead campaign URL.

**The organising principle: 404 is for product states — absent, disabled, out-of-window. 5xx is for faults — 503 transient, 500 permanent-data. A fault must never be dressed up as a product state.**

| condition | status | leaks about the link |
|---|---|---|
| active, in window, no password | 302 | destination |
| active, in window, password set | 200 prompt | that it is protected (already disclosed) |
| key absent | 404 | nothing |
| `status != "active"` | 404 | nothing |
| outside `[start_at, end_at)` | 404 | nothing |
| `Get` returned an error | **503** + `Retry-After: 2` | nothing — emitted from a state of ignorance |
| `kv.Open` returned an error | **503** + `Retry-After: 2` | nothing |
| record present, `ParseLink` failed | **500** | that the slug has a record |

`linkgate.Resolve` (`redirect/linkgate/resolve.go`) makes this decision and returns a `Disposition`; both `handleRedirectGet` and `handleRedirectPost` in `redirect/main.go` switch on it and are structurally identical except for the `DispositionPrompt` arm. Absent, disabled and out-of-window stay deliberately indistinguishable from each other (see "Security tradeoffs" below) — a probing-resistance property, not an oversight, and `redirect/linkgate/resolve_test.go` pins that the three produce *equal* values, not merely three values that each happen to map to 404. Every `Get`/`Open` error is treated identically regardless of cause (no variant check, no string match) — the SDK exposes no typed error to match on, and a substring match would be control flow a vendor wording change could silently defeat (see "Write-throttle resilience" below for the same rule on the write side). `redirect` still has no retry anywhere: a saturated read cap needs the client to back off, not the origin to spend more of the exact resource that is exhausted.

**Caching favours the fix.** Akamai's Property Manager docs (`techdocs.akamai.com/property-mgr/docs/cache-http-error-responses`, fetched 2026-08-19) list 404 as cached for 10 seconds by default; 500, 502, 503 and 504 are **not** cached unless the "Cache HTTP Error Responses" behaviour is explicitly enabled. The statuses this fix introduces are strictly safer to cache-poison than the 404 they replace. No redirect status changes, so the 302-not-301/308 rule above is untouched, and `Cache-Control: no-store` (set once in `setSecurityHeaders`) continues to cover both new statuses with no new code.

**Hot-path cost: zero.** `Resolve` performs the same single `Get` `lookupLink` did; a successful redirect stays at 5 KV operations and a miss stays at 2.

**MEASURED ON THE DEPLOYED FIX, 2026-08-19 (`cb4793d-resolve503`) — the 404s are gone, but the `503` arm has never run on Akamai and the read-cap diagnosis above is now IN DOUBT.** A `dev/redirect-load.sh` sweep from c=60 to c=500 (~9,200 requests against one live slug) returned **zero wrongly-404 at every concurrency**, including 0 of 2,000 at **1,314 rps** where the pre-fix build wrongly-404'd **43% at 1,292 rps**. Three controls confirm the origin genuinely served it: six mid-saturation probes all had distinct `akamai-grn` with no `age`/`x-cache` (so no edge caching), the slug recorded **566 clicks** (lossy per the write cap, but impossible unless the handler ran), and traces read `desc="5 ops"` (so `Resolve` added none). **But zero `503`s ever appeared** — no read failed, so `DispositionUnavailable` remains exercised only by a unit test and a locally forced `kv.Open` failure. **Two corrections follow.** First, **do not requote "a successful redirect performs 2 KV gets, so ~700 rps is ~1,400 reads/second against the documented 1,000/second cap" as the mechanism** — that same sweep sustained **2,195–2,628 implied reads/s with no failures of any kind**, 2.2–2.6× the documented cap, so either repeated `get`s of one hot key do not each bill as a read or the 2026-08-18 failures had another cause entirely (a transient regional condition, or the 3× latency-regime swing documented above). Second, **a 404 is CHEAPER than a 302** (2 KV operations and no write, against 5 and one write), so the pre-fix table's rising throughput column is a *consequence* of the failures, not evidence the client pushed harder: today's 1,314 rps of 100% 302s is strictly more origin work than the failing run's 1,292 rps of 57% 302s. The fix is correct and inert on the success path, but it is **insurance against a fault whose mechanism is no longer understood**, not a demonstrated repair.

**SUPERSEDED 2026-08-21 by `e0bd7ef-kvfail`, which added origin-side failure logging and inverted the paragraph above. Read the two together: the measurements stand, the interpretation does not.** With `ev=kv_fail` lines available for the first time, the same load shape shows **186 of 1,200 and 954 of 3,000 redirect link reads FAILING at the origin — 15.5% and ~32% — while every single client received a `302`.** Each failure ran the `DispositionUnavailable` arm and returned `503`; not one reached a client. **The Akamai edge retries a 5xx and serves the retry.** Three consequences, and the third is the one to carry. First, **the read cap binds roughly where the original arithmetic said it did** — the "IN DOUBT" verdict above was an absence of instrumentation, not an absence of failures, and the "2,195–2,628 implied reads/s ran clean" line is **retracted**. Second, **converting 404 → 503 was a functional repair, not a cosmetic one**: a `404` is a valid final answer so the edge passes it through (hence 43% client-visible 404s pre-fix), while a `503` is retryable so the edge absorbs it — the visitor now gets the correct redirect one retry later instead of being told the campaign link is dead. Third, and generally: **a clean client-side status distribution is not evidence the origin is healthy on a platform that retries.** Any future capacity claim about this app must rest on origin-side failure counts, never on response codes. **Also settled here: Akamai emits TWO throttle messages** — `key-value error: rate limit exceeded` and `too many requests` — both under `Err/Error_Other`, so `api/kvretry.py`'s `classify_write_error` substring match is *intermittently* right and the WIT variant cannot identify throttling at all.

**The absorption cliff is UNMEASURED, and failure onset is DURATION-dependent (2026-08-21).** A controlled sweep found the edge absorbing a measured **50.9% origin failure rate** (4,580 of 9,000 link reads failing at the origin) with **every one of 9,000 clients receiving a correct `302`** — so nothing here bounds where the edge stops absorbing. Two things this establishes for any future capacity claim. First, **quote a duration, not just a rate**: at a fixed concurrency the origin failure rate went 8.8% → 52.7% purely because the run lasted longer, at essentially unchanged rps, which is the signature of a burst allowance rather than a flat per-second cap. Onset is near ~700 rps and climbs with sustained load. Second, **the redirect's failure rate tracks the redirect's own arrival rate, not total app-wide read demand** — five concurrent backup fan-out sources dragged a redirect run to 150 rps and **0%** origin failure, against 52.7% for the same slug under no external pressure, so adding app load made the redirect path *healthier*. A consequence for monitoring: client-side monitoring of `/r/{slug}` is blind by construction, and `ev=kv_fail` is the only signal — but a 50% origin failure rate caused zero user harm, so alerting on it naively would page on a condition the platform is successfully handling. See TASKS.md's "## The edge's absorption cliff was NOT found".

## Theming

`gui/` ships a light theme and a custom dark theme (derived from the same navy identity, not Pico's stock dark palette), auto-following the OS by default with a manual override persisted client-side. See `DESIGN.md`'s Colors section for the palette and its measured contrast ratios; this section covers the mechanism.

**Three blocks in `gui/theme.css`, in this order:**

1. **Theme-independent** (`:root:not([data-theme="dark"]), :root[data-theme="dark"]`) — density/type-scale tokens (`--pico-font-size`, `--pico-line-height`, `--pico-spacing`, both `--pico-form-element-spacing-*`) plus the raw navy ramp (`--ss-navy-950`, `--ss-navy-800`). These must never live in a theme-specific block: a theme block's selector stops matching the instant the *other* theme's `data-theme` is set, so a density token placed there would silently hand that property back to Pico's own viewport-scaling defaults the moment the app switched themes.
2. **Light** (`:root:not([data-theme="dark"])`) — unchanged from before this feature, selector included. **This selector must stay exactly `:root:not([data-theme="dark"])`, never a plain `:root`.** Pico's own light block uses that same selector (`:host(:not([data-theme=dark])),:root:not([data-theme=dark]),[data-theme=light]`), so matching it exactly makes this an equal-specificity tie that load order (this file loads after `pico.min.css`) breaks in this file's favor. A plain `:root` would silently lose that tie regardless of load order — confirmed live once already, for a different reason, before this feature existed.
3. **Dark** (`:root[data-theme="dark"]`) — new. `(0,2,0)` specificity beats Pico's own bare `[data-theme=dark]` block (`(0,1,0)`) by specificity, not load order, which is strictly more robust than the light block's tie-plus-load-order arrangement.

**`gui/theme-init.js`** is a small (~90-line) script loaded render-blocking as the first real element of `<head>`, before any stylesheet link, on every page except `index.html` (a redirect stub with no stylesheet, which gets `<meta name="color-scheme" content="light dark">` instead). It reads the `ss-theme` `localStorage` key — one of three values, `"system"` (the default), `"light"`, or `"dark"` — and **always sets `document.documentElement.dataset.theme` to a literal `"light"` or `"dark"`, never `"system"` and never left unset**. Setting that attribute at all, to any value, is what disables Pico's own `@media (prefers-color-scheme: dark)` block entirely (that block is scoped to `:root:not([data-theme])`, which stops matching the instant any `data-theme` is present) — so once `theme-init.js` has run once, the app's own dark block is the only thing driving dark mode, not Pico's. It exposes `window.ssTheme` (`KEY`, `get()`, `set(mode)`, `resolve()`, `apply()`) as the one source of truth for the storage key and the resolution rule; `gui/app.js`'s nav theme control calls these rather than reimplementing them.

**No-JS fallback:** if `theme-init.js` never runs at all (blocked, 404, JS disabled), no `data-theme` attribute is ever set, and the app falls back to whatever `theme.css`'s unconditional light-block declarations render — light, regardless of OS preference. This is why those declarations must never be deleted even though they're no longer the sole defense against Pico's dark-mode leak (see `DESIGN.md`'s Inputs/Fields note for the full history).

**Two Pico dark-block traps**, both must be re-fixed in `theme.css`'s dark block independently of the light block's existing fixes: Pico's own `[data-theme=dark]` block (1) re-enables `--pico-card-box-shadow`/`--pico-dropdown-box-shadow` (both default to a real multi-layer drop shadow, violating the No-Shadow Rule) and (2) sets `--pico-card-border-color` equal to the card background (an invisible border, in a system whose depth comes from a hairline border plus background contrast with no shadow allowed).

**A guard worth knowing about, in `gui/app.js`:** `initHeader()` checks `window.ssTheme` exists before calling into it, because `theme-init.js` is served on its own separate `spin.toml` route (`/theme-init.js`) rather than being bundled into `app.js`. If that route ever 404s, an unguarded call would throw inside `initHeader()`'s async body — a promise no page `.catch()`s — which would silently kill the *entire* page's init chain (nav, identity chip, links table, everything), not just the theme control. The guard turns that failure mode into "the theme control doesn't render and the app stays light" instead of "the whole page is dead."

## Commands

Build and run the whole app (all four components) locally:

```bash
SPIN_VARIABLE_ADMIN_BOOTSTRAP_PASSWORD=<some-password> spin up --build --runtime-config-file runtime-config.toml
```

This invokes each component's `[component.<name>.build]` command from `spin.toml` and then serves all routes together. Requires the [Spin CLI](https://spinframework.dev) to be installed.

**`--runtime-config-file runtime-config.toml` is optional locally, and it is NOT a no-op — it decides whether your KV data survives a restart.** Spin auto-provisions the `"default"` store with no runtime config at all, backed by a sqlite file that persists; passing this file instead selects `type = "spin"` with no `path`, which on Spin 4.0.2 is a **temporary in-memory store wiped on every restart**. **Drop the flag if you want your local links and users to still be there after a restart; pass it (or use `dev/kv-explorer-up.sh`, which always passes it) if you want a clean store every run.** See the measured three-way comparison under the `kv-explorer` bullet in Architecture — including that `runtime-config.toml`'s own "sqlite-backed" comment is wrong. It is kept in the documented command so every existing script that passes it keeps working unchanged. It has no effect at all on an Akamai Functions deployment, which ignores runtime configuration entirely. `admin_bootstrap_password` is a required secret variable (seeds the first admin user on a fresh KV store) and has no default, so it must be supplied via env var (or another Spin variable provider) on every run.

When testing the `gui` in a real browser over plain `http://localhost`, also set `SPIN_VARIABLE_COOKIE_SECURE=false` — the session cookie's `Secure` flag otherwise stops the browser from storing/sending it over non-HTTPS, breaking login. Leave `cookie_secure` at its default `true` for any HTTPS deployment.

**Editing any file under `gui/` requires restarting `spin up` — the running server does NOT pick it up.** `spin_static_fs` serves a snapshot of the mapped directory taken at startup, so a `.js`/`.css` edit is invisible until the process restarts. This is worth knowing because of how it presents: a genuinely correct fix keeps reproducing the *old* error in the browser, with the old line numbers, which reads as "my fix is wrong" rather than "the server is stale" — confirmed 2026-08-10, where `curl localhost:3000/dashboard.js` returned the pre-edit file while the on-disk file already had the fix. **When a GUI change appears not to work, diff the served asset against the file on disk before doubting the change** (`curl localhost:3000/<asset>`), and note that a browser hard-reload does not help, because the staleness is server-side. This does not apply to `gui-pages`, `api` or `redirect`, which are rebuilt by `--build`.

## Time-windowed links

A link record's `start_at`/`end_at` fields (ISO8601 UTC, e.g. `2026-01-01T00:00:00Z`) make it active only in `[start_at, end_at)` — inclusive start, exclusive end. Either or both may be `null` (unbounded on that side). A link outside its window returns a plain `404`, identical to a nonexistent slug — deliberately no distinct "not yet active"/"expired" messaging, so a probing visitor can't learn a link's existence or schedule. The window is re-checked from a fresh KV fetch on every `/r/{slug}` request (`redirect/linkgate.IsWithinWindow`), the same "never cache" principle the password gate already uses — so editing a link's window via `PATCH /api/links/{slug}` takes effect on the very next request.

## Analytics

Every successful redirect updates one key in the `analytics` KV store, written by `redirect` (`recordClickCount` in `main.go`, pure logic in `redirect/linkgate/analytics.go`) and read by `GET /api/links/{slug}/analytics` (`api/analytics.py`):

- `count:<slug>:<shard>` — one JSON blob `{total, days: {"YYYY-MM-DD": n, ...}}`, read-modified-written on every click (one KV round trip), with `days` trimmed to `analytics_day_retention_days` (default 90) entries. **The counter is sharded across `linkgate.CountShards` (64) keys** — see "Click counting is sharded across 64 keys" below.

**`events:<slug>:<slot>` no longer exists as a live feature.** Since `docs/plans/drop-events-write.md` (2026-08-18), `redirect` no longer writes it at all — see "The recent-events ring buffer" below, now retired. Leftover `events:` keys from before that change still exist on real stores and are harmless; `api/analytics.py`'s `parse_analytics_key` keeps recognising the shape (so `analyticsorphans.classify_analytics_keys` doesn't misclassify them as `unrecognized_key`) and the Store maintenance page reports the residual as `totals.obsolete_event_keys`.

### The Clicks column's read cost scales with traffic, without bound — MEASURED 2026-08-11

**`GET /api/analytics/click-totals` reads every existing `count:` key for every visible slug, so its read count grows with traffic toward 64 per link.** `api/analytics.py`'s docstring calls this "proportional to real traffic rather than to links × shard count." That is true and it is **not a bound**: as a link gets busy, shards-touched → `COUNT_SHARDS`, and the endpoint converges on exactly the 65×N shape it was designed to avoid. The protection holds for quiet links and evaporates for the busy ones a real deployment cares about.

Measured on the deployed build by seeding 20 links and clicking them in stages (the `get` count in an `X-SS-Debug` trace **is** Σ shards-touched, so this is direct, not inferred):

| clicks/link | `get` measured | model | wall |
|---|---|---|---|
| 0 | **7** | 7 | 175 ms |
| 5 | 106 | 104 | 197 ms |
| 25 | 417 | 424 | 412 ms |
| 100 | **930** | 1022 | **792 ms** |

**Two consequences.** First, **wall time scales once reads exceed `gather_reads`' 100-concurrent bound** — below it gathering hides the cost, above it the fan-out serialises into waves. Second, extrapolated against Akamai's **1,000 reads/second app-wide cap that redirects also draw from**, one dashboard load at **100 links × 200 clicks issues ~6,126 reads — 613% of the entire app's per-second read budget.** That is a design limit, not a tuning problem.

**The measurement method is the lesson.** A 2026-08-10 run seeded 9,000 links and concluded the endpoint was cheap; it seeded links that were **deliberately never clicked**, so they created no count keys and the `get` count sat at 6 for the whole experiment. **Measuring this endpoint requires seeding clicks, not links** — seeding links alone measures only the enumeration axis and will report a false all-clear.

**The rejected denormalised `analytics:total:<slug>` deserves re-costing against these numbers**, not the ones available when it was rejected for "adding a THIRD KV write to every click". Writes are capped at 50/s and reads at 1,000/s, so the real trade is one extra write per click against thousands of reads per dashboard load. Re-argue it; do not assume either conclusion.

### Click counting is sharded across 64 keys

The write path (`recordClickCount` in `redirect/main.go`) picks a shard per click and read-modify-writes `analytics:count:<slug>:<shard>`. The read path (`api/analytics.py`'s `handle_analytics`) sums **65** keys: all 64 shards plus the legacy unsharded `count:<slug>`.

- **The shard is chosen from entropy, not from the slug.** `linkgate.ShardFor(clickEntropy(now), linkgate.CountShards)`, where `clickEntropy` XORs `math/rand/v2`'s `rand.Uint64()` with `now.UnixNano()`. Two sources deliberately: the RNG varies within one Wasm instance even if its seed does not, and the clock varies across instances even if WASI's `random_get` is stubbed and every instance seeds identically. A slug-derived shard would defeat the entire point — every click on one hot link would land on the same key.
- **`ShardFor` runs the value through a splitmix64 finalizer (`mix64`) before the modulo, and must not be "simplified" into `EventSlot`'s single multiply-then-reduce.** That is not a style preference: a single multiply is *linear over the modulus*, so clicks a fixed interval apart advance by a constant stride and reach only one additive cycle of the ring. Substituting it puts all 100,000 draws of the timestamp-distribution test into shard 0. `redirect/linkgate/analytics_test.go` pins the timestamp case specifically, and it is the load-bearing test in that file.
- **`CountShards` (Go) and `COUNT_SHARDS` (Python) must stay equal, and the rule is RAISE ONLY, NEVER LOWER.** The asymmetry is what makes it dangerous: a reader *higher* than the writer merely reads empty keys, but a reader *lower* than the writer silently drops every click recorded into a higher shard, with no error anywhere. `api/tests/test_kvprefix.py` pins the equality by reading `keys.go` from the Python suite, the same cross-language guard the key prefixes use.
- **No migration was needed and none should ever be written.** Nothing writes the legacy `count:<slug>` key any more, and the reader sums it in alongside the shards, so pre-sharding click history keeps showing up in the total forever. A slug can never contain a colon (`CUSTOM_SLUG_PATTERN` is `^[A-Za-z0-9_-]{3,32}$`), so a shard key can never collide with the legacy key.
- **A corrupt shard costs only its own clicks.** `_merge_counts` skips a blob that is absent, empty, non-JSON or the wrong shape rather than raising — one bad shard must never blank a link's whole history.
- **The merged `days` map can exceed the retention window, and that is accepted.** Each shard trims its own map independently, so a low-traffic link whose shards collected clicks on different days unions to more than `analytics_day_retention_days` entries. The data is correct and at most a few kilobytes; trimming at read time would mean declaring the retention variable for the `api` component purely to shorten a response.

**Two independent mechanisms lose clicks on Akamai, and sharding addresses exactly one of them.** Conflating them is how this repo previously reached a wrong conclusion, so keep them apart:

| | **M1 — per-key contention** | **M2 — the app-wide write cap** |
|---|---|---|
| cause | `count` is a read-modify-write and Spin's KV has no compare-and-swap, so overlapping clicks *on one key* lose increments | Akamai allows 50 KV writes/second per app; a recorded click costs one (one count shard — the events-slot write was retired 2026-08-18, see `docs/plans/drop-events-write.md`) |
| scope | one hot link | the whole service, all links combined |
| threshold | measured 25% loss at 9.4 clicks/s on a single slug | ~50 clicks/second app-wide |
| fixed by sharding? | **yes** | **no** — only writing less per click would |

The measurement that separates them (2026-08-06, live): **1 slug at 9.4 req/s lost 25%, while 16 slugs at 9.2 req/s — the identical app-wide write load — lost 0%.** Same writes per second, one hot key versus sixteen. 16 slugs at 19.7 req/s (39.4 writes/s) also lost 0%.

**How well sharding works — measured on the deployed build, 2026-08-07, at both 16 and 64 shards.** `CountShards` is **64**; it was raised from 16 after the 16-shard build measurably missed its accuracy target.

| rate | writes/s | 16 shards | **64 shards** |
|---|---|---|---|
| 9.5 req/s | 19.0 | 97, 100, 98 | **99** |
| 19.8 req/s | 39.6 | 95, 90 | **100, 99** |

(Per 100 clicks issued. Pre-sharding, 9.4 req/s recorded **75**.)

**Residual loss is driven by concurrency, not by per-shard rate, and the original design reasoning got this wrong.** The plan argued 16 shards suffice because at the app-wide ceiling each shard sees only ~1.6 clicks/s, inside a band measured lossless. But a rate does not lose an increment — **two clicks occupying the same shard's read-modify-write window at the same time** does. In-flight requests ≈ rate × KV latency, and KV latency on Akamai runs 250–400 ms, so ~20 req/s puts 5–8 requests in flight. Collision probability grows roughly as k²/2S, quadratic in concurrency — which matched the measured 1.7% → 7.5% loss as the rate doubled at 16 shards, and which quadrupling the shards duly removed.

**Consequences.** Click totals are essentially exact below ~10 clicks/second app-wide, drift a few percent by ~20/s, and remain lossy above that. **Raising `CountShards` further remains the lever if it is ever needed again** — RAISE ONLY, cross-language guard, no migration. **The 16 → 64 raise is done and measured, and the concurrency work paid for it:** the analytics read went from 50 to 98 `get`s, and **effective parallelism rose rather than saturating — 19–58× at 100 operations against 6.8–33.6× at 52** — so wall time went only 166 ms → 246 ms mean (148 → 175 ms median), against **373 ms** for the same page at *16* shards before the reads were gathered. **The page is ~34% faster than it was before any of this work, while the counter is now accurate at 20 clicks/second.** A pre-measurement extrapolation put 100 operations near 330 ms; the real figure was 246 ms, so the estimate was pessimistic. **If shards are ever raised again, re-measure rather than extrapolating — the parallelism scaling observed here is an empirical property of this host, not a guarantee.** The redirect hot path stays at 5 KV operations at any shard count (was 6 before the events write was retired 2026-08-18). **A single link above ~50 clicks/second is still lossy and sharding will not save it** — that is M2, and only fewer writes per click addresses it.

**Any measurement of counter accuracy must hold `request_rate × 1 < 50 writes/second`, i.e. stay under ~50 requests/second aggregate, or it measures M2 rather than M1.** (Before 2026-08-18 this was `request_rate × 2`, when a recorded click still cost two writes — see the retired-feature note below.) This is not a hypothetical caution — the gating probe for this very design was first run at 38.5 req/s (then 77 writes/s), showed 32.5% loss, and was read as a clean failure; re-run under the cap it passed unambiguously. `dev/click-load.sh` prints the implied write rate and warns at 50 precisely so that cannot happen silently again; use it rather than hand-rolled `curl` loops.

**The recent-events ring buffer was a separate problem, fixed separately, and then retired entirely** — see below. It was not sharded (it needed no counter; it was a blind overwrite), but `EventSlot` did share the counter's original hashing flaw and was corrected on 2026-08-07, before the whole feature (write, read and GUI) was removed on 2026-08-18.

### The recent-events ring buffer collided; cause was arithmetic, not the clock — FIXED 2026-08-07, RETIRED WITH THE FEATURE 2026-08-18

**This feature no longer exists.** `docs/plans/drop-events-write.md` removed the write (`redirect`'s `recordClickEvent`), the read (`api/analytics.py`'s `recent_events` field), and the GUI's Recent events table, taking a recorded click from two KV writes to one and roughly doubling the app-wide click ceiling (M2, above) — see "Analytics" at the top of this section. `EventSlot`'s splitmix64-finalizer derivation below is kept as history for one reason: it is the only written record of *why* `ShardFor` (which the click counter still calls, via `CountShards`) uses that finalizer instead of a single multiply — that derivation now lives on `ShardFor`'s own doc comment in `redirect/linkgate/analytics.go`, and `TestShardFor_DistributesUniformlyOverTimestampShapedInput` is the sole surviving pin on the property, since `EventSlot` (the caller that originally suffered the defect) no longer exists.

**Historical defect, fixed 2026-08-07, before the feature was retired.** The recent-events ring buffer used to lose far more entries to slot collisions than a uniform-random model predicts — 8 requests spaced 300 ms apart under local `spin up` retained only 3 distinct events. `EventSlot` delegated to `linkgate.ShardFor`, whose splitmix64 finalizer has no constant stride. **"Recent events" was always a best-effort sample, never a complete log** — a ring buffer with random-ish placement overwrites some entries no matter how good the hash is (20 clicks into 30 slots can fill at most ~63% of them; that is balls-in-bins, not a defect) — but the fix made it actually use the ring, for as long as the feature existed.

**The cause was `EventSlot`'s hashing, identified 2026-08-07.** Earlier revisions of this section blamed WASI clock resolution — *that was wrong and is retracted.* Direct measurement had already contradicted it (consecutive `time.Now()` calls differ by 750–1000 ns in Go, and requests 15–18 ms apart receive distinct microsecond-resolution timestamps), leaving the real cause open until it fell out of mutation-testing `ShardFor`.

`EventSlot` was `(unixNano × 2654435761) mod numSlots`. **A single multiply is linear over the modulus**, so for two clicks Δ nanoseconds apart the slot advances by a *constant stride* of `(Δ × 2654435761) mod numSlots`, and the reachable slots are one additive cycle rather than the full ring. Multiplying by a large odd constant was intended as a de-correlation trick and documented as such in the code; the flaw is that it cannot break up an arithmetic progression at all, which is exactly the shape steady-cadence click timestamps have.

**Two corrections to the original derivation, found while writing the fix's regression tests — the earlier numbers in this section were computed in Python and did not account for Go's arithmetic.**

1. **Go's `uint64` multiply wraps at 2^64; Python integers do not.** The clean `numSlots / gcd(stride, numSlots)` formula only commutes with that wraparound when **`numSlots` divides 2^64, i.e. is a power of two.** There the collapse is total and the derivation exact: at `numSlots = 16`, *every* spacing tested reaches **1 slot of 16**. At `numSlots = 30` the wraparound perturbs it, so the reachable set is larger than the naive formula predicted — the previously-tabulated "1 s → 3 of 30" was really **11 of 30** over 20 clicks. **That row was wrong.**
2. **The sharper and run-length-independent statement, which replaces the table:** 2^64 is divisible by 2, so wraparound preserves the low bit, and every realistic spacing in nanoseconds is even. **Slot parity was therefore pinned by the base timestamp's low bit forever** — a link whose first click landed on an even nanosecond could reach only even slots, for the life of the link. **Half the ring was permanently unreachable.** Verified against the old formula at 5,000 clicks across four spacings and both base parities: every run reached exactly one parity. `TestEventSlot_ReachesBothParitiesOfTheRing` pins it.

| spacing | old, `numSlots=30` | old, `numSlots=16` |
|---|---|---|
| 1 ms | 3 of 30 (20 clicks) | **1 of 16** |
| 107 ms | 3 of 30 (20 clicks) | **1 of 16** |
| 300 ms | 2 of 30 (20 clicks); **1** at 8 clicks | **1 of 16** |
| 1 s | 11 of 30 (20 clicks) | **1 of 16** |
| any | **≤ 15 of 30, one parity only, forever** | **1 of 16** |

The live observation (8 requests 300 ms apart → 3 distinct events) sits slightly above the idealized figure of 1, which is expected: **real request spacing has jitter, so live runs land between the idealized collapse and uniform.** Do not treat the agreement as exact — the mechanism is confirmed by the parity result and by the power-of-two case, not by that one number matching.

**Do not "simplify" `ShardFor` back into a multiply.** `EventSlot`'s own cadence/parity/original-bug-report tests were retired along with the feature (2026-08-18); the counter's `TestShardFor_DistributesUniformlyOverTimestampShapedInput` is now the sole surviving pin, and it fails against the old single-multiply implementation — mutation-verified, not assumed.

**Historical note on the click *counter*, retained because it is how the question was opened.** Before sharding, `analytics:count:<slug>` was a single key and lost 25% at 9.4 clicks/s, 70% at 34/s and 75% at 65/s on the live app. Losses were permanent, not lag — a 25-request burst recorded 19 and was still 19 a minute later. It was **ordering-independent**: a controlled A/B moving the write before and after the response changed nothing (85 vs 86 of 100), which is what established that only a different counter *shape* could fix it. The 34/s and 65/s figures are now known to be contaminated by the app-wide write cap (M2 above) and are unusable for reasoning about contention. Locally (sqlite) the same tests record no loss at all, so none of this reproduces outside a real deployment.

## Bulk link management

`POST /api/links/bulk` (bulk create) and `POST /api/links/bulk-action` (bulk delete/enable/disable), both in `api/bulk.py` and routed from `api/app.py` on exact-path match above the existing `/api/links/...` branches. **Validation is all-or-nothing**: any invalid row/slug in a submission means nothing is written and every problem is reported, never a partial result — with no atomic KV operations available (see "Security tradeoffs" below), a partial-success design would leave the user needing to diff what they submitted against what exists just to know what to retry. **Execution, since "Write-throttle resilience" below, is best-effort and fully reported** rather than all-or-nothing: a throttled write mid-run no longer means nothing landed, it means the response says exactly what did.

- **`POST /api/links/bulk`** takes raw pasted/uploaded text plus batch-level `password`/`start_at`/`end_at` (applied to every link created in that submission, not per-row) and parses it with `parse_bulk_text`/validates it with `validate_bulk_rows`. Text format, briefly: one row per line, `slug,destination` or `slug<TAB>destination` (first delimiter wins; commas after the first stay in the destination); a bare URL line has no slug (blank = auto-generate); `#` and blank lines are skipped; a leading UTF-8 BOM is stripped; a first row whose fields match a small `HEADER_WORDS` set is dropped as a header. Slugs are case-sensitive. Full spec and worked examples are in `docs/plans/bulk-link-management.md`.
- **`POST /api/links/bulk-action`** takes `{"slugs": [...], "action": "delete"|"enable"|"disable"}`. **Bulk enable/disable is the only path in the GUI that changes a link's `status` at all** — there is still no single-link status toggle anywhere in the dashboard, so disabling one link means selecting it and using the "bulk" action.
- **Caps: `MAX_BULK_ROWS = 50` rows/slugs per request, `MAX_BULK_BODY_BYTES = 262144` (256 KB) per request body.** Both are plain module constants in `api/bulk.py`, not Spin variables — unlike a variable that two components must agree on, the cap is read by exactly one function in one component, and it expresses a safety rail tied to what a single `componentize-py` request can do, not an operator-tunable policy. Both error responses carry the limit and (for `too_many_rows`) the actual `row_count`, so the client never hardcodes either number. **Raising `MAX_BULK_ROWS` needs real timing evidence from a full-cap submission, not just "50 felt limiting"** — the cap was deliberately dropped from an original 200 to 50 specifically to keep a submission's per-request work (~100 KV ops, at most one PBKDF2 hash) comfortably bounded; going back up should be a deliberate decision made with that evidence in hand, and if it goes much past ~100 the bulk-create error table's now-removed "first 50, then …and N more" truncation needs to come back too.
- **A record's existence is the only truth — there is no index left to order writes around.** Before `docs/plans/derived-link-indexes.md`'s Stage 2, bulk create wrote every `slug:<slug>` record before a single `add_slugs_to_indexes` call, and bulk delete removed every record before a single `remove_slugs_from_indexes` call ("records first, indexes last"); an interrupted create left link records with no index entry (recoverable, merely invisible until repaired), and an interrupted delete left index entries with no backing record (`handle_list` already tolerated this by skipping a slug whose record is `None`). Both indexes are gone now, so both interruption stories collapse to the same one: whatever records landed are exactly what's listed, since listing is derived from the records themselves.

## Multi-domain display

The app can be reachable at more than one base domain (e.g. a branded `go.example.com` alongside `localhost:3000` in dev), and the GUI lets a viewer pick which one every short URL, Copy button, CSV column and QR code is built from. This is display-only: **there is no per-link `domain` field, and nothing enforces a link to a domain.** `redirect/main.go` never reads the `Host` header — resolution is purely `slug:{slug}` → KV → 302 — so every link already works on every domain that points at this deployment, regardless of which one a link was created or shared under. Domains are a **viewer preference**, in the same category as the light/dark theme: chosen in the persistent nav, persisted client-side in `localStorage` (`ss-domain`), and read fresh at the moment each URL is built (`shortUrlFor(slug)` in `gui/app.js`) rather than stored anywhere server-side.

- **`public_base_urls`** (plural) is a comma-separated Spin variable, e.g. `SPIN_VARIABLE_PUBLIC_BASE_URLS="https://go.example.com,http://localhost:3000"`. Each entry is a bare `scheme://host[:port]` — no path, query or fragment — normalized (lowercased, no trailing slash) and de-duplicated by `api/domains.py`. **Order is meaningful: the first entry is the default** — the nav selector's initial choice for a viewer who hasn't chosen one, and what the QR endpoint uses when no `?base=` is supplied.
- **This variable replaced the old singular `public_base_url`, which no longer exists anywhere in `spin.toml`.** Spin's env-var provider looks up declared variables by name, so a deployment that upgrades without renaming its env var (`SPIN_VARIABLE_PUBLIC_BASE_URL` → `SPIN_VARIABLE_PUBLIC_BASE_URLS`) gets the default `http://localhost:3000` **silently** — the stale variable is simply never read, with no warning anywhere in the server log. Confirmed live. Check this first if a deployed app's QR codes or copied links unexpectedly point at `localhost` after an upgrade.
- **`assigned_domains`**, an optional list on each user record, restricts which of the configured domains that user's nav selector offers. Absent or `[]` means **unrestricted** (every configured domain), not "no domains" — no existing user record needs a backfill. It is a convenience guardrail against handing out an off-brand URL by accident, **not a security control**: it is deliberately not in `auth.py`'s `KNOWN_PERMISSIONS` (a small, fixed, hardcoded vocabulary that would lose its "reject anything outside this set" property if permission strings were generated per configured domain), and it gates nothing server-side — a user can still obtain a link or QR code for any configured domain by hand-crafting a request. The admin Users page manages it via `gui/admin/users.html`/`users.js`.
- **`GET /api/links/{slug}/qr`'s `?base=` parameter is allowlist-validated against `public_base_urls`, never trusted directly.** An endpoint that encoded an arbitrary client-supplied base URL into a QR code would be a QR-poisoning vector — the image is printed and handed out, outliving any later fix. A `base` not in the configured list returns `400 {"error": "invalid_base_url"}`; an empty configured list returns `500 {"error": "no_base_url_configured"}` rather than quietly falling back to `localhost`; a valid, differently-cased or trailing-slashed match is accepted and the response always encodes the server's own canonical string, never the caller's.

Local dev with two domains:

```bash
SPIN_VARIABLE_PUBLIC_BASE_URLS="http://localhost:3000,http://127.0.0.1:3000" \
SPIN_VARIABLE_ADMIN_BOOTSTRAP_PASSWORD=<some-password> \
SPIN_VARIABLE_COOKIE_SECURE=false \
  spin up --build --runtime-config-file runtime-config.toml
```

Plan: `docs/plans/multi-domain-display.md` (also records the rejected per-link `domain` field and `Host`-header enforcement designs, and why).

## Link tags and ownership

Links carry free-form tags, and a `users.manage` holder can reassign a link's owner. Plan: `docs/plans/link-tags-and-ownership.md`.

**Tags live only inside the `slug:<slug>` record, as a `tags` array — there is no `tag:` index and no `_meta:tags` registry.** Vocabulary rules are in `api/tags.py`: lowercase, `^[a-z0-9][a-z0-9_-]*$`, 1–32 chars, **max 10 per link**, stored normalized, de-duplicated and sorted. The character set is deliberately narrower than the slug's (no uppercase) so that `Sale` and `sale` can never become two tags; the 10-per-link cap exists because tags render as chips inside the links table's existing Short-link cell, and a row with dozens of them would wreck the column.

**Why no index.** The dashboard already holds every link in `allLinks` (`GET /api/links` has no pagination), so filtering and autocomplete are pure client-side work over data already in memory. A `tag:<tag>` index would have bought nothing for that and cost a two-index read-modify-write on every single-link `PATCH` — up to 20 of them at the 10-tag cap, with no compare-and-swap available anywhere in Spin's KV. It would also have created a new KV key type, which obliges a matching `api/backup.py` change (`INDEX_KEYS`, `restore_write_order`). **If either an index or a registry is ever added, that `backup.py` change is mandatory, not optional** — a new key type that `backup.py` doesn't know about is silently dropped on restore. **Since 2026-08-04 there is a second obligation:** `api/consistency.py` must learn the new key's shape too, or the consistency check reports it as `unrecognized_key` on every run (see "KV consistency check"). A test in `api/tests/test_backup.py` pins that today's tags round-trip needs no such change.

**The cost of that choice:** tag suggestions are ownership-scoped. A user without `links.view_all` is only ever offered tags they have personally used, because the suggestion list is derived from the links they can see. Filtering still works correctly on everything they can see.

**`links.tag` gates bulk tag/untag only.** Setting tags on a single link — at create, or via `PATCH /api/links/{slug}` — needs only the edit rights that link already required. The permission exists for `POST /api/links/bulk-action` with `action` of `tag` or `untag`, which still applies the per-row `can_edit` check on top. `PATCH {"tags": [...]}` is a **full replacement**, not a merge; omitting the key entirely leaves existing tags untouched.

**Owner reassignment is `action: "reassign"` on the same bulk endpoint, gated on `users.manage` alone.** It deliberately **skips the per-row `can_edit` check** every other bulk action applies. That is the point of the feature: the motivating case is an employee leaving, whose links the operator by definition cannot edit. It is not a weaker bar than an `admin` role check either — `api/users.py`'s `handle_update` already lets a `users.manage` holder promote themselves to admin.

- **The permission check runs before the owner lookup, and must stay that way.** Reversed, a caller without `users.manage` gets `400 unknown_owner` for a name that doesn't exist and `403 forbidden` for one that does — enumerating the username list that `GET /api/users` gates behind that same permission. `test_bulk_action_reassign_without_permission_cannot_distinguish_a_real_owner_from_a_fake_one` is the guard.
- **Reassignment is a pure record rewrite — since `docs/plans/derived-link-indexes.md`'s Stage 2, there is no owner index to move a slug between at all.** Before that change, records were written first, then the new owner's index, then the old owners' (`links.move_slugs_between_owners`, since deleted), so an interruption mid-move left a slug listed under *both* owners' indexes — visible, harmless, self-correcting. That whole story collapses now: an interruption partway through a multi-slug reassignment simply leaves some records rewritten to the new owner and some not, and every one of them is correctly listed under whichever owner its record currently names, because listing is derived from the record.
- A **disabled** user is an acceptable reassignment target (parking links on a deactivated account is a legitimate move); a nonexistent one is not.

**`redirect` is untouched.** `linkgate.Link` has no `Tags` field and gains none — Go's `encoding/json` ignores unknown fields unless a decoder opts into `DisallowUnknownFields`, so the new field costs the hot path nothing. `redirect/linkgate/link_test.go` pins both halves of that.

**Bulk tag, untag and reassign share the 50-slug `MAX_BULK_ROWS` cap** with the existing actions, and are all-or-nothing like them: if adding a tag would push any one link past 10, nothing is written and every offending slug is reported. The dashboard disables all six bulk buttons past the cap and tells the user to narrow the filter, since a tag filter is the easy way to select 200 links at once.

## User deletion and link ownership

**`DELETE /api/users/{username}` refuses with `409 {"error": "user_owns_links", "username", "link_count"}` while the user still owns links**, writing nothing to either store. The operator disposes of the links first — reassign or delete, via the bulk actions above — and then deletes the account. Plan: `docs/plans/user-deletion-link-ownership.md`.

**This exists because deleting a user used to leave two things behind, both of which were reproduced against a running app before the fix.**

1. **Link inheritance.** The link records kept `owner: "<deleted-username>"` and `owner_links:<deleted-username>` survived in the `links` store. **There is no user identity anywhere beyond the username string** — `links.can_edit` is `record["owner"] == principal.username` and `handle_list` reads `owner_links:<principal.username>` — so recreating the username handed the new account every link the old one owned, editable and repointable, while the short URL kept resolving for everyone who already had it.
2. **Session revival, the worse one.** `auth.resolve_session` builds the `Principal` from the **current** `user:` record and keys only on the username stored inside the session, and deletion never purged `session:*`. A deleted user's cookie correctly 401'd *while the username was absent* — and then came back to life the moment the name was recreated, carrying **the new account's role and permissions**. A plain user's revoked cookie was observed returning as an admin's, without its holder ever learning the new password. Deleting a user was never actually revoking their sessions; it was making them temporarily unresolvable.

Both scenarios are pinned by `api/tests/test_user_deletion.py` rather than merely fixed, and both are mutation-verified: removing the 409 gate fails the first, removing the session purge fails the second.

**There is deliberately no tombstone or reserved-username list.** Purging sessions at deletion is what makes username reuse *safe*, which is a better property than making it forbidden — a reserved list would grow forever, would need its own admin UI to ever release a name, and would still not have fixed the session bug. `auth.delete_sessions_for_user(store, username, list_keys)` takes the key-listing callable as a parameter, the same way `backup.py` does, so `auth.py` stays free of `spin_sdk` imports and host-testable.

**Cross-store write ordering on the success path** (deletion touches both the `links` and `users` stores, with no transaction and no compare-and-swap): sessions → `user:` → `_meta:usernames`. Every interruption point leaves the stronger invariant — a crash after this point never leaves a live session for a nonexistent user. **Since `docs/plans/derived-link-indexes.md`'s Stage 2, there is no `owner_links:` key to delete here at all** — the original ordering led with `owner_links:` → sessions → `user:` → `_meta:usernames`, and that first step is simply gone now that there's no index for it to touch.

**`links.slugs_owned_by`** (public, the same "shared, not module-private" convention `can_view`/`can_edit` already carry) is what `users.py` calls to make the 409 decision — derived from the records themselves (`links.enumerate_slugs` plus a `get_many` and an `owner` field check), not from a maintained `owner_links:<username>` index, which no longer exists. See "Derived link indexes" for why.

**The GUI turns the refusal into an action.** `gui/admin/users.html` names the username and count, and offers a link to `dashboard.html?owner=<username>` **only when the viewer holds admin/`links.view_all`/`links.edit_all`** — an operator with `users.manage` alone would land on an empty dashboard, so they get the missing permission named instead of a dead link. That is accepted rather than fixed: such an operator can already self-promote through `handle_update`.

- The dashboard's `#owner-filter` is **derived from the `owner` field on the loaded records, not from `owner_links:`**, so it is ownership-scoped for free and additionally surfaces links whose owner no longer exists. **That makes it the repair path** for any deployment that orphaned links before this gate existed; those owners render with a `— deleted account` marker reusing the existing `status-disabled` treatment (no new token).
- `?owner=` is **consumed once**. A reload after a bulk action keeps whatever filter the operator has since chosen instead of snapping back to the URL.

## Destination URL policy

Admin-managed rules on what a link may point at, enforced at authoring time. Pure logic in `api/urlpolicy.py`; the admin page is `gui/admin/url-policy.html`, reached by an in-body anchor on `admin/users.html` (the nav is full). Plan: `docs/plans/destination-url-policy.md`.

**A destination URL is also length-capped, separately from policy.** `links.MAX_TARGET_URL_BYTES` (4096) is enforced at all three authoring paths through the single `links.target_url_error` choke point — `handle_create`, `handle_update` and `bulk.validate_bulk_rows` all call it rather than repeating the checks, for exactly the reason this section gives below: a constraint enforced in two of three places is not enforced, and the bulk path is the one that stays open. **The cap is measured in bytes, not characters**, because the bound protects a stored value's size and a non-ASCII or percent-encoded URL costs more bytes than it has characters. A link record otherwise had no size bound of its own below Akamai's 1 MB max value size, which matters more since the link indexes were derived: *every* visible record is now fetched on every dashboard load, so the population paying for an oversized record is everyone rather than its owner. The error body echoes `max_bytes`.

**Why it exists:** a short link *launders* its destination. A recipient sees `go.example.com/r/promo` and cannot tell where it leads, so a bad destination borrows the organization's credibility. Before this, `links.is_valid_target_url` accepted any `http`/`https` URL with a netloc, and any account could shorten anything.

**Rules live in one `_meta:url_policy` key in the `links` store.** An absent key means everything is allowed, so no deployment changes behaviour on upgrade and nothing needs a migration. **No rules are seeded** — a list shipped in the repo needs a deploy to change and carries false-positive risk, the same reasoning that retired the banned-word slug list.

**Precedence is one sentence: a deny rule always wins, then an allow rule or a `default_action` of `allow`, otherwise blocked.** This was chosen over "most specific match wins" for one reason — **a misunderstood specificity rule fails open, and deny-wins fails closed.** Do not "improve" it into specificity ordering.

**Matching covers a host and every subdomain of it**, via `host == rule or host.endswith("." + rule)`. The dot is load-bearing: a bare `endswith("example.com")` would also match `notexample.com` and silently mis-scope every rule. Verified live in both directions — under a deny rule for `example.com`, `evil.example.com` and `a.b.example.com` are blocked while `notexample.com` and `myexample.com` are not; and under an allow-list with `default_action: "deny"`, the classic bypasses `example.com.attacker.net` and `user@example.com.evil.net` are both blocked (the host comes from `urlparse(...).hostname`, so userinfo can't spoof it).

**Enforced at all three authoring paths — `links.handle_create`, `links.handle_update` and `bulk.handle_bulk_create`.** A policy enforced in two of three places is not enforced, and `api/tests/test_url_policy_enforcement.py` exists to prove all three reject the same destination and write nothing. **`validate_bulk_rows` takes the policy as a required fourth parameter with no default** — deliberately, because a default is exactly how the bulk path would stay silently open. Rejections carry `host` and `reason` so the GUI can name what caught the link rather than saying "not allowed".

**Existing links that violate a newly-added rule are reported, never mutated.** `GET /api/admin/url-policy/violations` lists them; remediation is the operator's existing bulk Disable/Delete. Nothing is retroactively protected until a human acts — that is the accepted trade, taken so that a config edit can never become an unpreviewable bulk mutation with no compare-and-swap and no undo. It is the same posture restore and the consistency check already hold. **Violations are deliberately *not* a thirteenth consistency check:** `consistency.py` is scoped to structural drift, a policy finding would pin `ok: false` on a structurally flawless store, and its "re-run to confirm" and "never repairs" framings are both wrong for policy.

**`redirect` is untouched.** Enforcement is at authoring time; the hot path keeps its single KV read per click and never consults the policy. A link created before a rule existed keeps resolving.

**`_meta:url_policy` carries both obligations a new KV key type now imposes** (see "KV consistency check"): `consistency.py` recognises its shape, and `backup.py` round-trips it — verified byte-identically, because otherwise restoring a backup would silently wipe an operator's policy.

## Derived link indexes

`links:all_links` and `links:owner_links:<owner>` used to be maintained, read-modify-write indexes over the `slug:` records — a shared JSON array, no compare-and-swap available anywhere in Spin's KV. Concurrent authoring requests each read the index, added their own slugs, and wrote back: last writer wins, and everyone else's index additions were silently lost. The link *records* all landed and resolved at `/r/{slug}`; only their appearance in `GET /api/links`/`GET /api/analytics/click-totals` and the `owner_links:` gate on user deletion depended on the index surviving the race.

**Measured directly on `751f368-throttle-resilience`, 2026-08-17:** four concurrent 5-row bulk creates (~28 writes, far under the write cap) produced 20 real link records and lost 10 of them from the index with zero write failures anywhere in the trace — proving the loss was the race itself, not write throttling. Since `docs/plans/derived-link-indexes.md`, both indexes are **gone**. `links.enumerate_slugs(store, list_keys)` derives the slug list from a `slug:` key enumeration; `links.slugs_owned_by(store, username, list_keys, get_many)` derives ownership the same way, by reading every record and checking its `owner` field. `GET /api/links`, `GET /api/analytics/click-totals`'s visible set, and `users.handle_delete`'s `409 user_owns_links` gate all use these instead of an index read. **A record's existence is now the only truth** — this replaces "records first, indexes last" everywhere that rule used to apply (bulk create/delete, single create/delete, reassignment): every interruption point leaves exactly the records that landed, all of them listed, none of them advertised-but-missing, because there is no longer a second write that could fall out of step with the first.

**Cost, measured on the deployed trace the day this shipped:** `GET /api/links` swaps one `get` of `all_links` (~25 ms) for one `list_keys` (~24 ms at the store's size that day) — a wash today, but `list_keys` costs `~24 ms + 68.7 µs per physical key in the WHOLE default store` (see "Parallel KV reads" below) and grows without bound as click volume grows, where the old index read did not. **Revisit trigger: a traced `list_keys` inside `GET /api/links` above ~250 ms** (roughly 3,300 physical keys) — the same trigger `docs/plans/derived-link-indexes.md`'s Recommendation section already costs. The `events:` ring-buffer write, one of the levers that section named, was dropped 2026-08-18 (`docs/plans/drop-events-write.md`) — it bent the slope by roughly a third but did not remove the underlying trigger.

**Two residual read-modify-write keys remain, and no others are proposed.** `users:_meta:usernames` (still a maintained index — see `unindexed_user`/`missing_user_record` below) and `links:_meta:url_policy` (a single admin's rule edit, single-writer in practice); both are accepted as-is, on the same reasoning: low frequency, no user-visible authoring hot path depends on them.

**The leftover `all_links`/`owner_links:<owner>` keys are not deleted.** They stay in the store, inert, forever — at ~68.7 µs per key to enumerate, deleting them is a follow-up not worth its own endpoint (see `docs/plans/derived-link-indexes.md`'s "Out of scope" section). `consistency.collect` recognises both shapes as known-and-ignored, the same treatment `_meta:bootstrapped` already gets, so a store that predates this change reports exactly as clean as one that never had the keys at all. `backup.py` needed **no change**: `INDEX_KEYS`/`restore_write_order` already understood both shapes, so a backup taken before this change round-trips byte-identically — `api/tests/test_backup.py` pins it.

## KV consistency check

`GET /api/admin/consistency` walks the `links` and `users` stores and reports where the users index and sessions have drifted, plus corrupt/unrecognized values in either store. **The check itself stays write-free**: there is no `?fix=` on this endpoint, and `collect`/`analyze` perform no writes at all — a separate repair endpoint now exists (see "Consistency repair" below), but it re-derives everything itself rather than trusting this endpoint's output, and this endpoint never gained a mutating side effect of its own. Gated on `users.manage`. Pure logic in `api/consistency.py` (zero WASI SDK imports, `store` objects and the `list_keys` callable passed in, `api/backup.py` as the model); the GUI is a third article on `gui/admin/backup.html`. Plan: `docs/plans/kv-consistency-check.md` for the original twelve-check design, `docs/plans/derived-link-indexes.md` for why six of them were retired.

**Six checks**, always all present in every report at `count: 0` when clean, in this order:

| id | severity | means |
|---|---|---|
| `unknown_link_owner` | warning | a record whose `owner` has no user record |
| `unindexed_user` | warning | a `user:` record missing from `_meta:usernames` — can sign in, invisible to administration |
| `missing_user_record` | info | `_meta:usernames` names a user with no record |
| `orphan_session` | warning | a `session:` naming a user with no record |
| `unreadable_value` | warning | a value that wouldn't parse into its expected shape |
| `unrecognized_key` | info | a key matching none of the known shapes for its store |

**Six checks were retired, not merely renumbered.** `unindexed_link`, `missing_link_record`, `unindexed_owner_link`, `owner_index_mismatch`, `orphan_owner_index_entry` and `dangling_owner_index` all described drift in `all_links`/`owner_links:<owner>` — indexes that no longer exist, since "Derived link indexes" above. There is nothing left for those checks to find drift *in*: a record's existence is the only truth now, and a fact with no counterpart can't drift from it. `unknown_link_owner` is the one owner-related check that survives, unchanged in meaning: a record naming an owner with no user record is still real drift, derived entirely from `link_records` with no index involved.

**The `analytics` store is never opened or scanned.** `links.handle_delete` inline-purges the deleted slug's own analytics keys (see "Orphaned analytics purge" below) but bulk delete still doesn't, so `count:<slug>:<shard>`/`events:<slug>:<slot>` for a deleted slug is **normal state, not drift** — reporting it would make every healthy deployment show findings, which is how a checker gets ignored. **Expired `session:` records are excluded for the same reason.**

**A report can never carry credential material.** A `user:` record's *value* is never read — only its key name; `unindexed_user`/`missing_user_record` need nothing else, and `orphan_session` reads only the `username` field of a `session:` value. A test generates a report over a store holding a real PBKDF2 hash and asserts neither `password_hash` nor `pbkdf2_sha256` appears in the body.

**`MAX_FINDINGS_PER_CHECK = 100`, per check, not global** — one noisy check would otherwise starve every other one out of the report. It is a plain module constant, not a Spin variable, on the same reasoning as `MAX_BULK_ROWS`: one function in one component reads it. **When a check truncates, `count` stays exact and `truncated` is set**, and the GUI says "Showing the first N of M" — a capped list must never read as complete.

**The walk has no snapshot.** Spin KV offers no transaction, so a concurrent write can produce a transient finding. That is why the page tells the operator to re-run: a real finding appears on both runs. Do not "fix" this with locking; there is nothing to lock with.

**A new KV key type now obliges *three* changes, not two** (see also "Link tags and ownership"): `backup.py`'s `INDEX_KEYS`/`restore_write_order`, `consistency.py`'s key-shape recognition — otherwise the new key reports itself as `unrecognized_key` on every single run — **and, since the KV store consolidation, the key must live under one of the three prefixes (`links:`, `users:`, `analytics:`) in `api/kvprefix.py`'s `STORE_PREFIXES`, or it is invisible to the whole application**: no view will ever return it, so it won't appear in a backup, won't be seen by the consistency check, and will be silently pruned by the next restore.

## Consistency repair

`POST /api/admin/consistency/repair` is the write-side companion to the read-only check above. Three of the six checks have exactly one safe, derivable, automatic repair; three never do because repairing them requires a judgment call the store can't answer on its own. Gated on `users.manage`, matching the check, backup/restore and the analytics purge. Pure logic in `api/consistencyrepair.py` (zero WASI SDK imports, `store` views/`request`/`list_keys`/`get_many` taken as plain parameters, `api/consistency.py` and `api/analyticsorphans.py` as the models); the GUI lives inside the existing consistency article on `gui/admin/backup.html`/`backup.js` — no new page, route, or `spin.toml` entry. Plan: `docs/plans/consistency-repair.md` for the original design, `docs/plans/derived-link-indexes.md` for why five of the eight original repairs were retired.

**Why this shipped now rather than when the check did:** the original plan deliberately deferred a repair tool until a real deployment had shown real drift, on the reasoning that "a repair tool designed before anyone has seen a real report is designed from imagination." That trigger fired on 2026-08-15: throttled index writes past Akamai's 50-write/second cap during ordinary bulk operation left 344 findings across four now-retired checks, with no API path able to fix any of it. That whole incident class is now structurally impossible — see "Derived link indexes" above — but the repair tool itself survives for the three checks that can still drift.

**The repairable/non-repairable split, and why:**

| check | verdict | repair |
|---|---|---|
| `unknown_link_owner` | **never** | fix is reassign-or-delete, both product decisions with shipped bulk tools and a dashboard owner filter already built for exactly this |
| `unindexed_user` | repair | add username to `_meta:usernames` |
| `missing_user_record` | repair | remove username from `_meta:usernames` |
| `orphan_session` | repair | delete each `session:<token>` |
| `unreadable_value` | **never** | content is unknown by definition — delete and rewrite are both guesses |
| `unrecognized_key` | **never** | deleting an unrecognised key is exactly how a future key type this checker hasn't learned about yet gets destroyed — `analyticsorphans.classify_analytics_keys` already holds the identical rule |

`consistency.REPAIRABLE_CHECKS` names the three, in `CHECKS` order, and is published in every report as `repairable_checks` — the GUI never decides for itself which findings have a button; that is a correctness question the server owns.

**The client submits check ids, never findings — that is what satisfies "re-detect before repairing."** The report the operator is looking at contributes nothing but intent; `handle_repair` always re-runs `consistency.collect`/`consistency.analyze` in-request, calling `analyze(collected, max_findings=None)` so it acts on every finding rather than just the first `MAX_FINDINGS_PER_CHECK` (100) the report happened to display.

**Index repair is O(distinct index keys), not O(findings).** `unindexed_user` and `missing_user_record` share exactly one key (`_meta:usernames`); only `orphan_session` costs one key per finding, since each session is its own key.

**`MAX_REPAIR_WRITES = 100`, a plain module constant** (the same reasoning `MAX_BULK_ROWS`/`MAX_BACKUP_ENTRIES`/`MAX_PURGE_KEYS_PER_REQUEST` carry — one function in one component reads it). Sized from a write costing ~75 ms on Akamai (measured on the inline analytics-purge delete, a different handler shape, 2026-08-15): 100 × ~75 ms ≈ 7.5 s against the 30-second handler limit, roughly the same ~4× margin the analytics purge's own cap was accepted at. Because every repair unit costs exactly one write, any budget ≥ 1 makes progress — no equivalent to the purge's "at least one slug is always planned" special case is needed. **Raising it needs real timing evidence from a full-cap repair, not a hunch**, the same rule every sibling cap in this codebase carries.

**Deletes are always sequential, never gathered — the same rule the analytics purge and every bulk handler follow.** `apply_repairs` never fans a write out concurrently; `api/kvbatch.py`'s concurrency helper is reads-only by design, and the WASI key-value batch interface's multi-key write functions are already rejected repo-wide (`TASKS.md`, "Considered and rejected", 2026-08-15) — writes are cap-bound at 50/second app-wide while reads have 1,000/second of headroom, so issuing them concurrently would queue against the cap rather than overlap, and would compete with live click recording.

**No new KV key type.** The repair only mutates keys `backup.py`'s `INDEX_KEYS`, `consistency.py`'s key-shape recognition, and `kvprefix.STORE_PREFIXES` already understand — `_meta:usernames`, `session:<token>`. The links store is never read or written by this repair any more. It is stateless: it records nothing about past repairs, exactly like the analytics purge.

**The lost-update window, and why "run it again" is the worst case.** Spin's KV has no compare-and-swap and the consistency walk has no snapshot, so a concurrent write between `collect` and `apply_repairs` can produce a lost update. Three things bound it: every delta write re-reads `_meta:usernames` immediately before writing it, so the window is one `get` + one `set` rather than the whole collect-to-write span; a repair never writes a wholesale computed list, only the specific members `collect` formed an opinion about, so a concurrently-created username survives untouched; and the only reachable residual failure mode is therefore a lost *removal*, which surfaces as ordinary drift on the next consistency run and is fixed by re-running.

## Orphaned analytics purge

`links.handle_delete` and `bulk.handle_bulk_action`'s delete branch remove a `slug:<slug>` record; **neither one used to touch the `analytics` store** — a deliberate decision, argued in `docs/plans/kv-consistency-check.md`'s rejected alternative #1 on the grounds that "orphan analytics are harmless in a way orphan links are not." **That clause was falsified by measurement on 2026-08-10:** a key enumeration costs ~68.7 µs per physical key in the whole `default` store (linear, R² = 0.997), `GET /api/analytics/click-totals` makes exactly one such enumeration on every dashboard load, and a measured live store was 964 keys, 943 of them analytics, 907 of those (96%) belonging to 28 slugs with no link record at all, against only 14 live links (2 of which had any analytics). The audience — marketing staff who create and delete links heavily as they correct mistakes — makes this a permanent, unbounded leak rather than a curiosity: live links plateau, orphaned analytics does not.

**Since `docs/plans/inline-analytics-purge-on-delete.md` (2026-08-12), `links.handle_delete` purges the deleted slug's analytics keys inline, in the same request; `bulk.handle_bulk_action`'s delete branch still does not, and that asymmetry is deliberate, not an oversight.** The gap being closed is organisational rather than arithmetic: the manual tool below is operator-driven, and the audience creating the orphans — non-technical marketing staff correcting a mistake — has no reason to ever open the Store maintenance page, so every single-link delete used to ratchet the store up until an administrator remembered to run the tool. Bulk delete stays out because the arithmetic doesn't close: 50 slugs at the shipped-configuration ceiling of ~95 analytics keys each is 4,750 sequential writes, ~95–123 s at the measured 20–26 ms/write, against Akamai's 30-second handler limit — even the cheap ~6-key case adds ~6.9 s to a 50-row bulk delete. Single-link delete has no such multiplier.

- **Mechanism**: `links.handle_delete` takes an injected `purge_analytics` callable (a plain parameter, not an import — `analytics.py` already imports `links`, so `links.py` importing `analyticsorphans` would be a cycle, the same reason `list_keys`/`read_file` arrive as parameters elsewhere in this codebase). `api/app.py`'s `DELETE /api/links/{slug}` branch wires it to `analyticsorphans.purge_slug_analytics`, which reuses the existing enumerate-then-classify logic (`classify_analytics_keys`) rather than constructing candidate keys — so it picks up the legacy unsharded `count:<slug>` key, keys left over from the retired `analytics_event_slots`-configured recent-events ring buffer (see "Analytics" above), and any future analytics key type for free, exactly like the manual purge below. Omitting `purge_analytics` (as `bulk.py`'s delete branch does) reproduces today's exact `{"ok": true}` response with zero analytics access.
- **Write ordering is record → analytics, and it is load-bearing, not incidental** (since `docs/plans/derived-link-indexes.md`'s Stage 2, there is no index step between them any more). Every interruption before the analytics purge leaves a *recoverable* state — orphan analytics keys, which is the pre-existing, expected steady state the manual tool below already exists to clean up. The reverse ordering (analytics first) would risk leaving a **live, resolving link whose click history silently vanished**, with no tool anywhere able to restore it — an unrecoverable loss traded for a recoverable one, which is the wrong trade every time. A KV failure inside the purge callable is caught and reported as `{"status": "failed", ...}` rather than allowed to turn an already-successful deletion into a `500` — the link is gone regardless of what happened to its analytics, and the response must say so.
- **`MAX_INLINE_PURGE_KEYS = 128` is a safety rail, not a policy, and cannot fire at shipped configuration.** The maximum possible per-slug key count today is 95 (64 count shards + 1 legacy unsharded key + 30 event slots, the last now historical since redirect stopped writing them 2026-08-18 — see "Analytics" above), so the rail exists only against a slug carrying leftover keys from the retired, once-larger `analytics_event_slots` configuration or a future analytics key type — a policy cap that deliberately deferred expensive links was considered and rejected, because the links it would defer are exactly the links carrying the most keys, opting out of most of the benefit while keeping all the complexity. `api/tests/test_analytics_orphans.py` pins `MAX_INLINE_PURGE_KEYS >= analytics.COUNT_SHARDS + 1 + 30`, so a future raise-only bump to `CountShards` cannot silently start deferring every single-link delete's purge.
- **Nothing changes in the GUI beyond disabling the Delete button for the request's duration** (`gui/dashboard.js`, matching the existing enable/disable toggle's pattern) — the confirmation copy is unchanged and the response's `analytics_purge` field is never rendered. Deleting a link already made its analytics unreachable (the analytics endpoint 404s on the missing link first), so nothing observable changes for the user regardless of purge outcome; the field exists for `curl`, for tests, and for a builder tracing a deployed run.
- Plan: `docs/plans/inline-analytics-purge-on-delete.md`.

Plan: `docs/plans/analytics-orphan-purge.md`. Shape: a cheap report (`GET /api/admin/analytics/orphans`, exactly 2 KV operations regardless of how many orphans exist — one `list_keys` on the analytics namespace and one on the links namespace) plus a chunked, client-driven purge (`POST /api/admin/analytics/purge`, at most `MAX_PURGE_SLUGS` (50) slugs and `MAX_PURGE_KEYS_PER_REQUEST` (250) deletes per request), both gated on `users.manage`, both on the existing maintenance page (`gui/admin/backup.html`, retitled "Store maintenance" — see below). Pure logic lives in `api/analyticsorphans.py` (zero `spin_sdk` imports, `store` views/`request`/`list_keys` taken as plain parameters, matching `consistency.py` and `backup.py`); `api/analytics.py` gained a shape-only `parse_analytics_key` extraction that `handle_click_totals` now shares. **Since `docs/plans/derived-link-indexes.md`'s Stage 2, the report derives liveness from `links.enumerate_slugs` (a `slug:` key enumeration) rather than a maintained `all_links` index** — the original design read `links.all_slugs`, a now-deleted function, and that index-liveness coupling is exactly what the next paragraph used to warn about; it no longer applies, because there's no index left to be misled by.

**No new KV key type.** The purge is stateless: it deletes only keys it just enumerated and returns what it did. It never constructs a key (e.g. `count:<slug>:<n>` for `n in range(COUNT_SHARDS)`), which is what lets it pick up the legacy unsharded `count:<slug>` key, keys left over from the retired `analytics_event_slots`-configured ring buffer, and any future raise of `CountShards`, all for free.

**Deliberately NOT a 13th consistency check, and inline purging on delete does not change that.** Orphaned analytics is expected, normal, intended state between purges — a check over it would pin `ok: false` on a structurally flawless store on every deployment that has ever deleted a link, exactly the same reasoning CLAUDE.md already applies to destination-policy violations. The precedent that supplied the answer instead: a separate endpoint pair plus its own article, like `/api/admin/url-policy/violations`. See the plan's Trade-offs #1 for the full argument, and "KV consistency check" above, whose own "analytics store is never scanned" paragraph now points here. **`docs/plans/kv-consistency-check.md`'s rejected alternative #1 names its own revisit trigger as "deletion being changed to purge analytics" — checked, not assumed, against the inline-purge change, and it does not fire:** four independent sources of orphan analytics survive it — bulk delete (unchanged, out of scope), every orphan created before this shipped, a `failed` inline purge, and a `deferred` one (see `MAX_INLINE_PURGE_KEYS` above). Orphan analytics remains expected, normal, intended state between purges, so the check stays a separate tool rather than a 13th consistency finding.

**The report can be misled by a stale enumeration; the purge cannot be — this is the load-bearing safety property, not a nicety.** Since `docs/plans/derived-link-indexes.md`'s Stage 2, the report's own liveness set is a `slug:` key enumeration rather than a maintained index, so index drift specifically can no longer mislead it — but the enumeration is still a snapshot at report time, and a link created moments later wouldn't yet be in it. The purge does not lean on that snapshot at all: it re-checks `exists("slug:<S>")` on the record itself, via a bounded `gather_reads` fan-out, immediately before deciding what to delete for each submitted slug. That re-check is what makes it safe to confirm a purge with a count-bearing `confirmDialog` rather than a typed GUI field like restore's (see the plan's "Decisions taken 2026-08-10" section) — a stale report can misinform the operator, but it cannot make the purge delete a live link's analytics, because the purge never trusts the report's liveness judgement. The one reachable bad outcome, accepted rather than mitigated further: an operator purges a slug and, in the same few seconds, someone recreates a link with that exact slug and it's clicked before the purge's own delete runs — the new link loses a handful of seconds of its own brand-new clicks, never history, because it has none yet.

**Deletes are always sequential, never gathered — the one rule a well-meaning optimisation is most likely to break.** `for key in keys_to_delete: await analytics_store.delete(key)`, exactly like `backup.handle_restore`'s write loop and every bulk handler. `gather_reads` is used only for the purge's liveness pre-check and the report's enumeration — both reads — never for a delete; see "Parallel KV reads" above for why that asymmetry (1,000 read RPS vs. 50 write RPS, app-wide) is the whole safety argument.

**`MAX_PURGE_KEYS_PER_REQUEST = 250` and `MAX_PURGE_SLUGS = 50` are both plain module constants in `api/analyticsorphans.py`, not Spin variables** — one function in one component reads each, on the same reasoning `MAX_BULK_ROWS` and `MAX_BACKUP_ENTRIES` carry. 250 sequential deletes is ~5 s of wall clock at the measured 20–26 ms/write, with real headroom under Akamai's 30-second handler limit even at the documented 3× latency swing (~15–19 s pessimistic). **Raising either needs real timing evidence from a full-cap purge, not a hunch — the same rule `MAX_BULK_ROWS` and `MAX_BACKUP_ENTRIES` carry.** Both responses echo the limit that bounded them (`max_slugs`/`max_keys_per_request`), so no client ever hardcodes either number.

**The maintenance page was retitled "Store maintenance" (2026-08-10/11), file path unchanged.** `gui/admin/backup.html`'s `<h1>`, `<title>`, `initHeader`'s `pageLabel`, and `gui/admin/users.html`'s inbound anchor all changed; the file itself was deliberately not renamed (would need a new `gui-pages/routing.py` entry, a new `spin.toml` route, and would break bookmarks, for no functional gain — see the plan's "Decisions taken" section). TASKS.md's Future-work entry for a full rename keeps the file-rename half open.

**Retroactive measurement, still open:** the plan's projected post-purge saving on `click-totals` (~64 ms → ~4 ms of enumeration) and the purge's own wall time on Akamai are both **unconfirmed until a deployed build is purged and traced with `X-SS-Debug`** — see TASKS.md's "Re-measure list_keys after the first purge on a deployed build," blocked pending a deploy of this change.

## KV backup and restore

`GET /api/admin/backup` downloads a JSON snapshot of the `links`, `users` and `analytics` stores; `POST /api/admin/restore` replaces them from one. Both live in `api/backup.py` (pure logic, zero `spin_sdk` imports) and are routed on exact paths from `api/app.py`. The GUI is `gui/admin/backup.html` + `backup.js`. Plan: `docs/plans/kv-backup-restore.md`.

**File format.** `{"format": "spin-shortener-kv-backup", "schema_version": 1, "created_at", "created_by", "fidelity", "counts", "stores": {...}}`. Keys are plaintext, **every value is base64** — uniformly, regardless of whether it happens to be JSON, so the format never has to care what a value contains. `?stores=links,users` exports a subset, allowlist-validated against `BACKUP_STORES` exactly the way `qr.handle_qr` validates `?base=` (unknown name → `400 unknown_store` naming `allowed_stores`; empty → `400 no_stores`). `fidelity` is `"full"`: the `get_keys` spike confirmed Spin's KV can enumerate keys, so the planned index-walk fallback (and its `"index-walk"`/`incomplete: true` labelling) was never needed and is not implemented.

**A backup carries no *account* credentials — but it does carry link password hashes. It is a sensitive file.** Three exclusions are applied at export: `redact_user_value` strips `password_hash` from every `user:` record, and `is_excluded_key` drops every `session:*` key and `_meta:bootstrapped`. So the file cannot be replayed into a session and cannot leak an *account* hash. **`validate_backup` independently refuses a file containing any of that material on the way back in** — a second guard on the same property, not a redundant one, since it means a hand-edited file can't inject a session or an account hash either. Both halves are mutation-tested: disabling redaction fails 5 tests, disabling exclusion fails 6, and both additionally fail a *restore* test.

**What is deliberately *not* stripped: a link's own `password_hash`, inside its `slug:` record in the `links` store.** `redact_user_value` is scoped to `user:` keys and `is_excluded_key` returns `False` for every store but `users`, so a password-protected link exports with its full PBKDF2 hash. That is the right call — stripping it would make restore silently *unprotect* every protected link, a security downgrade invisible to the operator — but it means **the file must be treated as sensitive**, not as the freely-shareable artifact the account-hash exclusion alone would suggest. Link passwords are the weaker population, too: the GUI enforces only `minlength="4"`, so a short link password behind PBKDF2-100k is realistically crackable offline by anyone holding the file. Store backups somewhere access-controlled.

**Do not verify this property with `grep password_hash <file>`.** Every value in the document is base64, so that grep cannot see inside a record — it only ever matches the plaintext `excluded` array, which lists `"users/user:*#password_hash"` as documentation and therefore always returns a nonzero count. A grep of the raw file both misses real embedded credential material and reports a false positive; decode the values and inspect them (the `docs/plans/kv-backup-restore.md` verification step that specified this grep was wrong on both counts, and this is how the link-password exposure went unnoticed).

**Restore is all-or-nothing and it replaces, it does not merge.** `validate_backup` runs to completion before a single write. Then each store is written and pruned: any pre-existing key absent from the file is deleted. Store order is `links` → `analytics` → `users` (`RESTORE_STORE_ORDER`) — **users last, deliberately**, so a mid-restore failure leaves the operator's own session intact to retry with. Within each store, **records are written before indexes** (`restore_write_order`, using `INDEX_KEYS` plus the `owner_links:` prefix) — the same rule the bulk handlers follow, for the same reason: an interruption leaves records with no index entry, which resolve at `/r/<slug>` and are merely invisible in the dashboard, rather than index entries advertising slugs that 404.

**Recovery walkthrough, confirmed live end to end.** Restore a backup → the response carries `signed_out: true` and every session is gone, including the caller's. **No `spin up` restart is needed**: `ensure_bootstrap_admin` runs on *every request* (`api/app.py:60`), and since restore deleted `_meta:bootstrapped`, the next request re-seeds the bootstrap admin from `admin_bootstrap_password`. Sign in as that admin and the restored links resolve immediately. **The disclosed corner: that re-seed overwrites a restored user record named `admin`** — same username, but a fresh record with `role: "admin"`, `permissions: []` and `assigned_domains: []`, so any custom permissions or domain assignments that account had are lost. Every *other* restored account survives intact but **has no usable `password_hash` and can therefore never authenticate** — `LocalAuthProvider.authenticate` returns a clean `401`, not a `500`. An admin must set each one a new password; the users table flags them (see DESIGN.md's Status Badges).

**Caps: `MAX_BACKUP_BODY_BYTES = 5_242_880` (5 MiB) and `MAX_BACKUP_ENTRIES = 5_000`,** plain module constants in `api/backup.py`. Export refuses with `500 backup_too_large` naming both the cap and the actual size; restore refuses with `413 body_too_large`. **Raising either needs real timing evidence from a full-cap restore, not a hunch** — the same rule `MAX_BULK_ROWS` carries above, and for the same reason: a restore is a single `componentize-py` request doing thousands of sequential KV writes with no batching available.

**Both endpoints gate on the `users.manage` permission**, returning `users.py`'s exact `_forbidden()` body. That is deliberately the same bar as user administration rather than a `role == "admin"` check, and it is not the weaker of the two: a `users.manage` holder can already create an admin account, or promote themselves, via `handle_update`. Gating backup on the role instead would add no real protection while inventing a second, inconsistent notion of "admin" in a codebase whose whole permission model is the granular one.

**Restore requires `{"confirm": "REPLACE"}` in the body** (`400 confirmation_required` otherwise), and the GUI additionally requires the literal string typed into a field *plus* a count-bearing confirmation dialog. Server-side confirmation is the one that matters — the endpoint is reachable by `curl`.

## Write-throttle resilience

**This section is historical for its index half, and current for its record half — read it with `docs/plans/derived-link-indexes.md` in mind.** That later plan deleted `all_links`/`owner_links:<owner>` entirely (see "Derived link indexes" above), so everything below about `add_slugs_to_indexes`, `INDEX_WRITE`, `index_updated` and `"consistency_repair"` describes machinery that no longer exists — **the "abandon-and-index-what-landed" rule is moot, because there is no longer an index write to abandon or land.** What survives unchanged: the **record**-write retry (`RECORD_WRITE`, the `_RetryBudget`/backoff mechanism, `kvretry.py` itself, the `"partial": true` response contract, and the `redirect`/`backup.py` exceptions below) — a record write can still be throttled and still gets retried exactly as described.

Akamai caps KV writes at 50/second app-wide (see "Deployment: Akamai Functions" below). Before this, a throttled write anywhere in `api/bulk.py` propagated straight to `api/app.py`'s catch-all and became a bare `500 {"error": "internal_error"}` — telling the operator nothing about which rows landed, in a state where retrying could create duplicates or hit `slug_taken`. This happened twice in ordinary operation (TASKS.md's 2026-08-15 and 2026-08-17 incidents), both times because `bulk.handle_bulk_create` wrote every `slug:` record and called `links.add_slugs_to_indexes` **last**, so a throttled run left records written and the index never updated — links that resolve at `/r/{slug}` but were invisible in the dashboard. Plan: `docs/plans/write-throttle-resilience.md`.

**Two independent changes, and the second matters more than the first.** Retry (below) makes a throttled write less likely to fail. **Abandon-and-index-what-landed** is what makes its failure harmless: every multi-write handler that writes records then an index now breaks its record loop on exhaustion and indexes exactly the records that did land, rather than continuing to hammer a throttled store. A throttled bulk run therefore produces a **structurally clean store with zero `unindexed_link` findings**, not drift that needs a repair. If anything here has to be compromised, retry is the thing to compromise — never the index-what-landed rule.

**That "structurally clean" claim holds PER REQUEST ONLY, and concurrent bulk creates still drift — MEASURED 2026-08-17 on the deployed build.** Six concurrent 50-row creates all returned `200` with `"partial": true` and `index_updated: true`, exactly as designed, and left **37 `unindexed_link` + 28 `unindexed_owner_link`** behind. The cause is not throttling and no retry setting affects it: a control run of 4 concurrent 5-row creates (~28 writes, far under the 50/s cap) returned four clean `201`s with **zero retries and zero write failures** and still produced 5 `unindexed_link`. `links:all_links` and `links:owner_links:<owner>` are read-modify-write with no compare-and-swap, so concurrent requests overwrite each other's index additions — last writer wins, and in the 6×50 run exactly one request's 13 additions survived. **Do not read this section as making concurrent bulk work safe; it makes a single throttled request safe.** See `TASKS.md`'s `### DEPLOYED AND TRACED (2026-08-17)` for the traces and the Future-work entry for the options.

**Throttling has no dedicated error variant.** The generated WIT bindings define `Error = Union[Error_StoreTableFull, Error_NoSuchStore, Error_AccessDenied, Error_Other]`, and a throttled write arrives as `Err(Error_Other(value='too many requests'))` — the same shape any other KV failure takes. Worse, `componentize_py_types` (which defines `Err`/the `Error_*` dataclasses) is injected by componentize-py at build time and **does not exist in the host venv**, so a pure, host-testable module cannot import the WIT error types at all. **The consequence: every write error is treated as retryable, unconditionally, in the control path — no variant check, no string match.** A message-substring match used for control flow would degrade in exactly the wrong direction: if Akamai rewords "too many requests", the match silently stops firing and the app reverts to today's bug (no retries, bare 500, invisible drift) — a vendor copy-edit must not be able to un-ship a feature. `api/kvretry.py`'s `classify_write_error` still does a substring check, but purely to **label** the failure for the log line and the response body (`"throttled"` vs `"other"`) — never to decide whether to retry. **CORRECTED 2026-08-21: it matches TWO markers, not one.** `kvretry.THROTTLE_MESSAGE_MARKERS = ("too many requests", "rate limit exceeded")`, because Akamai was measured emitting both — a bulk create over the write cap produced only `key-value error: rate limit exceeded`, while a read-pressure run produced both, from the same op in the same run. The single-marker version that shipped until then was **intermittently right**, which is why every throttling incident in this file reported `write_error=other`. Two further points hold permanently: **both messages arrive as `Err(Error_Other(...))`, so the WIT variant cannot identify throttling** even though `obs.error_type_name` can now name the variant without importing it — there is no wording-independent check available, only a string match plus the acceptance that a third message may exist. And **`api/backup.py` inlines the same tuple** rather than importing it (keeping the restore path free of the retry seam), so `test_backup_and_kvretry_agree_on_throttle_markers` reads the literal back out of `backup.py` and pins the two equal — the same technique `api/tests/test_kvprefix.py` uses on `keys.go`. A label enforced in one of two places is not enforced.

**Correction, `docs/plans/observable-kv-failures.md`: "a pure module cannot import the WIT error types" is true, and it does NOT mean a pure module cannot identify the variant.** `componentize_py_types.Err` is a frozen dataclass that *subclasses* `Exception`, and its `.value` field holds the inner `Error_*` variant instance — so `type(exc.value).__name__` (`obs.error_type_name`) yields `Error_Other` / `Error_AccessDenied` / `Error_StoreTableFull` / `Error_NoSuchStore` with **no import at all**, duck-typed via `getattr(exc, "value", None)`, never an `isinstance` check against a type this module cannot import. This gives `etype` a wording-independent signal a vendor copy-edit cannot break — unlike `classify_write_error`'s substring match, which breaks the moment Akamai rewords "too many requests". The Go side is simpler still: `spin-go-sdk/v3/kv.go`'s `errorVariantToError` flattens the variant to one of four fixed English strings (or the raw host message for `Other`), so `redirect`'s `classifyKVFailure` matches those fixed strings directly. **`etype` is deliberately NOT control flow** — nothing in either language branches a retry/business decision on it, only a log field's spelling; promoting it to control flow (e.g. "don't retry `Error_AccessDenied`") is filed as Future work, gated on first observing which variants actually occur, not on this correction alone.

**`await asyncio.sleep(d)` for any `d > 0` raises inside the component.** `componentize_py_async_support`'s `_Loop` (the event loop componentize-py substitutes) leaves `call_later`, `call_at` and `time` all `raise NotImplementedError`, and CPython's `asyncio.sleep` calls `loop.call_later` for any positive delay — confirmed directly with a temporary token-gated spike route in `api/app.py` before this was built (TASKS.md's task-1 note). The real primitive is `wasi_clocks_monotonic_clock_0_3_0_rc_2026_03_15.wait_for(nanoseconds)`, confirmed reachable through componentize-py's bundler **and** confirmed to actually sleep (traced at ~502.6 ms for a requested 500 ms) — reading the SDK on the host proves nothing about what's in the built component (the same lesson `wasi:keyvalue/batch` taught earlier), so this was verified with a real `spin up --build`, not inferred. `api/app.py` imports it at MODULE scope, guarded by the same `try/except ImportError` shape `wasi_batch` already uses, and `_sleep_ns` is a documented no-op (retries collapse to immediate re-issue, spaced only by the KV round trip) if a future toolchain ever fails to bundle it.

**The retry seam — `api/kvretry.py`.** `make_writer(sleep, collector=None, jitter=random.random)` returns `async def write(make_coro, policy=RECORD_WRITE)`, closing over **one `_RetryBudget` per request** with two independent nanosecond counters, `record_ns` (`MAX_RECORD_RETRY_SLEEP_NS = 2_000_000_000`, 2 s) and `index_ns` (`MAX_INDEX_RETRY_SLEEP_NS = 3_000_000_000`, 3 s). Two budgets rather than one shared pool, deliberately: records are written before indexes (the repo's one write-ordering rule), so a single pool would be drained by 50 cheap-to-lose record writes before the one expensive-to-lose index write ever ran. `RECORD_WRITE` is 3 attempts (backoff 100 ms, 300 ms); `INDEX_WRITE` is 6 attempts (backoff 100 ms, 300 ms, 700 ms, 1.2 s, 2 s) — index writes get a deeper budget because losing one is the failure mode this whole plan exists to prevent. Once a counter's budget can't cover the next scheduled backoff, that kind of write gets zero further retries and fails immediately; the two counters are otherwise unrelated. `kvretry.direct` (the default for every helper's `write` parameter) calls straight through with no retry, so ~20 existing test call sites that seed fixtures via `links.add_slugs_to_indexes`/etc. are unaffected. **Raising any of these four constants (`RECORD_WRITE.attempts`, `INDEX_WRITE.attempts`, `MAX_RECORD_RETRY_SLEEP_NS`, `MAX_INDEX_RETRY_SLEEP_NS`) needs real timing evidence from a full-cap run, not a hunch** — the shipped values are modelled, not measured: a full 50-row bulk create's worst case is ≈11.2 s (52 base writes × 75 ms measured write cost + both retry budgets + their round trips) against Akamai's 30-second handler limit, a 2.7× margin, ≈21 s at the documented 3× latency-regime swing. The abandon-on-exhaustion rule is the second, more important bound: without it, 50 rows each retrying to exhaustion would alone approach ≈31 s.

**The response contract: `200` with `"partial": true`, not `207`.** (The plan that designed this originally argued for `207 Multi-Status`, on the reasoning that `gui/app.js`'s `apiCall` would route it to `ok: true` and let the GUI branch on detail — but `apiCall` returns `{ ok: res.ok, ... }`, and `res.ok` is true for *every* 2xx, so 200 and 207 look identical to every caller in this codebase. That argument doesn't hold, and the decision was corrected before implementation.) `POST /api/admin/analytics/purge` already established the convention — `200` with `complete: false` for a partial run — and a second partial-execution endpoint answering differently would make the API inconsistent with itself for no gain. **A successful run's response is byte-identical to today; only a partial run carries `"partial": true`, and clients that check only `res.ok` still see `"ok": false` in the body.** The new sentence, extending the analytics purge's own 2026-08-10 precedent: **validation is all-or-nothing; execution is best-effort and fully reported.**

**Where retry-and-report landed, by handler:**

- **`links.add_slugs_to_indexes` / `remove_slugs_from_indexes` / `move_slugs_between_owners`** each take `write=kvretry.direct` and route every `store.set` through `INDEX_WRITE`.
- **`bulk.handle_bulk_create`** breaks its record-write loop on `kvretry.WriteFailed`, then calls `add_slugs_to_indexes` with exactly the records that landed. A partial response carries `partial`/`count`/`links`/`not_created` (the existing `{line, slug, error}` shape, error `"write_failed"`)/`index_updated`/`write_error`/`next_step` (`"consistency_repair"` when `index_updated` is false, `"resubmit"` otherwise).
- **`bulk.handle_bulk_action`** breaks all six action branches the same way; delete/reassign call their index step with only the slugs actually removed/rewritten; enable/disable/tag/untag report `index_updated: true` unconditionally (they have no index step, so they're structurally incapable of drift).
- **`consistencyrepair.apply_repairs`** routes every `set`/`delete` through `INDEX_WRITE` and **stops** on exhaustion (never continues to the next key) — the repair tool is what an operator reaches for *during* an incident, i.e. exactly when the app is throttling, and retrying into a saturated cap would make the incident worse. `handle_repair` surfaces a `write_failed` list and forces `complete: false` when it's non-empty.
- **`analyticsorphans.handle_orphan_purge`** retries its deletes under `RECORD_WRITE` and stops the same way, putting the failed slug (and everything unattempted) back into `remaining_slugs` so the GUI's existing chunked loop picks it up. **`gui/admin/backup.js`'s purge loop gained a no-progress guard** (mirroring the repair loop's existing one) — before write-failure reporting existed, `plan_purge` always planned at least one slug, so progress was guaranteed; a throttled delete can now return "0 deleted, same slugs remaining," which without the guard is an infinite loop.
- **`links.handle_create`** retries its record write, then reports `partial: true` / `index_updated: false` / `next_step: "consistency_repair"` if the index write is exhausted — the one single-link path that can drift, since it's the only one with a record-then-index pair. `handle_update` and `handle_set_password` are single writes with no index, so they gain retry only. `handle_delete` retries the record delete and the index step, reporting `index_updated` on its existing `200` body.

**Two deliberate exceptions — where retry does NOT apply, and why:**

- **`analyticsorphans.purge_slug_analytics`** (the inline purge on single-link delete) takes no `write` and never retries. It runs *after* the link is already deleted, so its own failure cannot corrupt anything; its failure mode (orphaned analytics keys) is already documented above as "expected, normal, intended state between purges," with a shipped operator tool; and it already catches every exception and reports `{"status": "failed", ...}` without turning a successful deletion into a 500. Retrying here would spend write budget on the least valuable writes in the app, worsening cap pressure for everyone else.
- **`backup.handle_restore`** takes no `write` parameter and `api/backup.py` imports nothing from `kvretry` — report only, deliberately no retry. A full-cap restore (`MAX_BACKUP_ENTRIES = 5,000`) is already documented as unable to finish inside Akamai's 30-second handler limit at the write cap, so adding retry sleeps would make an already-doomed request slower for no gain. On a write failure, `handle_restore` stops and returns `200` with `partial: true`, the `restored`/`pruned` counts achieved so far, `stopped_at_store`, `write_error` (classified with a small logic inlined rather than importing `kvretry`, so this path stays free of any retry-seam dependency) and `next_step: "retry_restore"` — restore replaces rather than merges and is therefore idempotent, so "run it again" is a genuine next step.

**Writes are still never gathered or batched — the one rule this whole plan had to not break.** Retry makes writes survivable, not faster; `wasi:keyvalue/batch`'s `set_many`/`delete_many` remain rejected repo-wide (see "Parallel KV reads" below), and every sequential write loop in `bulk.py`, `backup.py`, `consistencyrepair.py` and `analyticsorphans.py` stays sequential.

**`redirect` is untouched, and deliberately so** (Trade-offs #2 in the plan). Its analytics writes are already documented as best-effort lossy (mechanism M2 above), and the hot path stays at 6 KV operations. A retry there would add wall time to a visitor's redirect for bookkeeping they have no stake in, and would worsen M2 for every other caller, since the redirect path is the largest consumer of the write budget. `api/obs.py`'s `_KV_OP_ORDER` gained `"write_retry"`/`"write_failed"` fields immediately after `"delete"`; `redirect/linkgate/obs.go` was NOT given matching fields, the same divergence `get_many`/`get_many_error` already established for the same reason.

## Toggleable structured logging

The app has KV-timing instrumentation in `redirect` (Go) and `api` (Python) only — `gui-pages` and `gui` are untouched (`gui-pages` does no KV work at all; `gui` is a prebuilt third-party binary). Plan: `docs/plans/toggleable-logging.md`.

**Two Spin variables, both read once and cached for the lifetime of the Wasm instance** (`sync.Once` in Go, a module-level cache in Python) — sound because a Spin variable cannot change without a redeploy on Akamai (`spin aka` has no command to change a deployed app's variables) or a restart locally, both of which produce a fresh instance:

- **`log_level`** — `"off"` (default) or `"summary"`; any other value is treated as `"off"`, fail-closed. **This must stay `off` in production.** At ~130 bytes/line and a sustained ~50 redirects/second (the Akamai write-RPS ceiling documented above, since the events write was retired 2026-08-18), baseline logging is on the order of 280 MB/day into a 7-day `spin aka logs` retention window — the same order-of-magnitude figure as before that change, since it was already an approximate "sustained ceiling" estimate rather than a precise one.
- **`log_debug_token`** — a shared secret (default `""`), compared against a request's `X-SS-Debug` header. A match traces that one request and adds a `Server-Timing` response header **regardless of `log_level`** — this is what lets one request be traced with no redeploy, since the variable alone would mean one redeploy to turn logging on and a second to turn it off. **An empty configured token never matches anything**, including an empty or absent header — checked explicitly before any comparison (`crypto/subtle.ConstantTimeCompare` in Go, `hmac.compare_digest` in Python), not as an incidental property of the comparison. Getting this backwards makes the default configuration "anyone can enable tracing." **The token cannot be rotated without a redeploy either** — there is no runtime-variable-update path on Akamai.

**Output: one logfmt line per request to stderr**, prefixed `ss ` so it's greppable and distinguishable from Spin's own output, e.g.:

```
ss comp=redirect route=/r/{slug} slug=M7RyJVC status=302 dur_us=140 kv_ops=5 kv_us=65 kv_bytes=262 open=2/24 get=2/25 set=1/16 slow=open:-:21
```

Per-op-type fields are `count/total_µs`, one per non-empty operation type (`open`/`exists`/`get`/`set`/`delete`/`list_keys`) — a zero-count type is omitted entirely, never `=0/0`. `slow` names the single slowest operation as `type:namespace:µs`. `api` additionally logs `method` and, on the exception path, `err=1` alongside `status=500`. **`Server-Timing` durations are milliseconds as floats** — 80 µs renders as `0.080`, never `80` — and are only emitted for a valid token, never merely because `log_level=summary`, so a baseline-logging deployment never hands internal timing to every visitor.

**CORRECTION, `docs/plans/redirect-read-failure-not-404.md`: this log line did NOT distinguish a read failure from a genuine miss, and a claim once made elsewhere in this repo that it did was wrong.** `linkgate.TimedStore.Get` records the op regardless of the error and discards the error itself; it records `len(v)` bytes, which is 0 for both a `Get` error (`v` is `nil`) and a genuinely absent key (`v` is `[]byte("")`); and `redirect`'s log line has no `err` field (`err=1` is `api`-only). So a read failure and a genuine miss used to produce a **field-for-field identical** line: `status=404 kv_ops=2 open=1/… get=1/…`. A `log_level=summary` build could not have answered "did this ever happen in real traffic" before `redirect`'s status-code fix landed. After it, **the status code itself is the signal** — grep a `log_level=summary` build for `status=503` — so no new log field was added for this; see "The `/r/{slug}` status contract" above.

**The collector structurally cannot log a KV key.** Its record method takes an operation type, a namespace and a duration (plus a byte count) — it has no parameter that could accept a key, the same move `PrefixedStore` makes by having no `get_keys`. This matters because `users:session:<token>` is a live session credential and `spin aka logs` retains 7 days by default; a key-logging design would put working session tokens in a week-long retention window. `redirect` does log the raw **slug** (not the key), deliberately — correlating a slow resolution to a specific link is the entire point of instrumenting that path, and slugs are already treated as non-secret (see "Security tradeoffs" below). `api` logs only a route **template** (e.g. `/api/users/{username}`, `/api/links/{slug}/analytics`) — the actual username or slug embedded in the URL never reaches the log line.

**`redirect`'s off path is deliberately byte-identical to the uninstrumented component.** Its profile is **5 KV operations per successful redirect** (2 `open`, 2 `get`, 1 `set`) and **2 for a miss** (1 `open`, 1 `get`). It was 7 and 2 when the logging landed, then 6 and 2 after `lookupLink`'s `Exists` probe was removed on 2026-08-06 once the deployed measurement showed it cost 21.7 ms there (see the Akamai section's per-operation table), then 5 and 2 after the recent-events ring buffer's second write (`recordClickEvent`) was retired 2026-08-18 (`docs/plans/drop-events-write.md`). The second `kv.Open` inside `recordClickCount`'s caller is still kept rather than threaded from the handler's already-open store — that looked like an 8–20% win locally but measured ~0.2% on Akamai, where `open` is ~154 µs against ~20 ms per data operation. Note a miss stays at **2** operations rather than dropping to 1, because `open` counts as an operation: it swapped `exists` for `get` rather than shedding one. The original reason for holding the op profile still while the instrument was built was doing so here would change the very baseline this instrument exists to measure against. When no collector is attached (the off path), KV calls go straight to the real `*kv.Store` with no wrapper and no timer calls at all — never a wrapped-but-no-op collector — which is what keeps the off path cheap, not merely silent. The collector itself is **never a package-level variable** in either language: it is attached to the Go request's `context` (retrieved by a `collectorFrom(ctx)` helper that returns `nil` — every `Collector` method is nil-safe) or passed as an explicit `_dispatch(self, request, collector)` parameter in Python, precisely because `componentize_py_async_support.spawn` dispatches each request independently and a shared collector would silently interleave concurrent requests' operations into one another's line — confirmed live: a 20-way concurrent burst against one slug produced exactly 20 log lines, every one reporting `kv_ops=7`.

**A new pure Python module for this lives at `api/obs.py` — never `logging.py`, and the same rule applies to any future module named after a stdlib module (`time.py`, `json.py`, ...).** `componentize-py` compiles `app.py` alongside its siblings with the component's own directory on the import path, so a module shadowing a stdlib name would break every stdlib module that imports the real one, for the whole component.

### Observable KV failures: unconditional failure lines, independent of `log_level`/`X-SS-Debug`

Since `docs/plans/observable-kv-failures.md` (2026-08-19), a SECOND, separate line kind exists alongside the summary line above: one sanitized failure line per distinct KV operation failure or unhandled exception, emitted to stderr on failure only — **completely independent of `log_level` and of whether `X-SS-Debug` was sent.** This is deliberate, not an oversight of the toggle doctrine above: the summary line's gating exists because it costs ~130 bytes on *every* request at a sustained rate, while a failure line costs nothing on the (overwhelmingly common) success path and only fires on a fault that, twice already, has failed to reproduce on demand under tracing — gating a diagnostic behind the very toggle it exists to catch failures without would defeat the point.

**Vocabulary: `ev=kv_fail` and `ev=exc`.** `ev=kv_fail` is a single KV operation failure (an `open`/`get`/`set`/`delete`/`exists`/`get_many` raising) — `redirect`'s `openTimedStore`/`Resolve` fault arms and `api`'s `PrefixedStore`/`scoped_get_many`. `ev=exc` is `api`'s catch-all `except Exception`, carrying `etype` and `at=<file>:<line>` (the innermost traceback frame — never a traceback, never source text) instead of `op`/`ns`/`op_us`. Neither line kind has an `ev` field on the pre-existing summary line — the two are additive and structurally distinct (`grep 'ev=kv_fail'` and `grep 'ev=exc'` cannot collide with a summary line, which has no `ev` field at all).

**`msg` is always the final field, and NOTHING may ever be appended after it.** The message is unquoted and may contain spaces; any flag about it (`msg_redacted=1`, `msg_truncated=1`) goes *before* `msg`, never after. This is enforced by construction: `render_failure_line`/`RenderFailureLine` are separate functions from `render_log_line`/`RenderLogLine`, specifically so nothing (a `dur_us`, a `kv_ops` summary, anything) can ever land after the message field the way it can on the summary line.

**The message is sanitized by construction — never logged raw — and `msg_redacted=1` is the greppable answer to "does an Akamai KV error string ever embed a key?"** Three rules, in order, in both languages (`api/obs.py`'s `sanitize_error_message`, `redirect/linkgate/obs.go`'s `SanitizeErrorMessage`): redact any key-shaped substring (`[A-Za-z][A-Za-z0-9_-]*:[^\s'")\]]+`) to `[key:<leading-word>]`; redact any `pbkdf2_sha256`-bearing token to `[hash]`; replace control characters/newlines with `_`; then truncate to `MAX_ERROR_MESSAGE_CHARS` (200), setting `msg_truncated=1`. The key-shaped redaction is complete for keys because of an existing invariant, not luck: every physical key this app sends is prefixed (`kvprefix.STORE_PREFIXES`; `keys.go`'s `LinkKey`/`CountShardKey`), so a host that echoes a key echoes a prefixed one. Whenever either redaction fires, `msg_redacted=1` is set — obtainable with no key ever having reached the log, which is the entire point: a raw `str(exc)` could embed `users:session:<token>`, a live 7-day-retained credential, and nobody had checked until this sanitizer made the question answerable without the risk.

**Bounded differently in the two components, and the asymmetry is deliberate, not an oversight — the "rare failure, negligible volume" reasoning does NOT hold as stated.** In `api`, a single throttled 50-row bulk create can fail the same write up to 150 times *in one request* ("rare" is wrong per-request), so `make_failure_reporter` deduplicates on `(op, ns, etype, msg)` and caps at `MAX_FAILURE_LINES_PER_REQUEST = 3` distinct tuples **per request** — a fresh reporter, and a fresh dedup set, is built once per request in `handle_request`, never module-level, for the identical reason `obs.Collector` never is. In `redirect`, a read failure is at most one per request by construction, but the request rate is 1,000+/s and instance count is not bounded (an Akamai request may get a fresh Wasm instance every time, for all this repo can confirm), so a per-request cap would not bound anything — instead, a package-scope, mutex-guarded `map[string]struct{}` deduplicates on `(op, msg)` **per Wasm instance**, capped at 32 distinct pairs for the *life of the instance*. This is NOT the forbidden shared-collector pattern even though the shape (package-scope state touched by concurrent requests) looks similar: a shared `Collector` is forbidden because it *accumulates* per-request statistics that must never be attributed to the wrong request, where this map accumulates nothing about any request and correctness never depends on which concurrent request wins the race to insert a given tuple — the tuple gets logged once, system-wide, for the instance's life, which is exactly the deduplication this section provides. See the comment beside `failureDedupMu` in `redirect/main.go`.

**The collector still structurally cannot accept a key — this section changes nothing about that.** `PrefixedStore.on_error`/`scoped_get_many`'s `on_error` and `redirect`'s `emitFailureLine` all take `(op, namespace, duration_ns, exc)`; nothing here has a parameter that could carry a key, and nothing is recorded into `obs.Collector`/`linkgate.Collector` on a failure — a traced line's `kv_ops`/`kv_us`/`kv_bytes` stay byte-identical to before this section existed, because the whole point of this change is diagnosis, not altering what tracing already measures.

## Parallel KV reads

**On Akamai the host genuinely overlaps concurrent KV reads, and a handler that awaits one read at a time pays full KV latency per key.** This is invisible locally, where an operation costs 5–20 µs against 5–20 ms deployed, so it can only ever be found or verified against a real deployment. `api/kvbatch.py` holds two helpers over this: `gather_reads` (bounded concurrent fan-out) and, since `docs/plans/batch-kv-reads.md`, `scoped_get_many` (a single `wasi:keyvalue/batch` `get_many` host call for K keys in one namespace). `analytics.handle_click_totals`/`handle_analytics`, `links.handle_list`, `bulk.handle_bulk_create`/`handle_bulk_action` and `consistency.collect` all use `scoped_get_many` today; `backup.handle_export` deliberately still uses `gather_reads` (see below).

**Which one to use:** `gather_reads` for heterogeneous coroutines or for `exists` probes, which have no batch equivalent (`analyticsorphans`' liveness pre-check is the one place that still applies). `scoped_get_many` for a set of plain key reads in one `PrefixedStore` namespace — it collapses K host round trips into one, which `gather_reads` cannot do (it still issues K reads, just concurrently).

**`api/kvbatch.py`'s `gather_reads` holds the original rule** — bounded (100 concurrent), order-preserving, **reads only**. Order preservation is load-bearing for every remaining caller: `backup.py` zips results back against its key list, and `scoped_get_many` itself uses `gather_reads` as its per-chunk fallback (see below). The bound is not decoration — export reads every key in the store, so an unbounded fan-out over a large store trades a latency problem for a read-cap one.

**`scoped_get_many` normalises `get_many`'s two hostile host semantics into `dict[str, bytes | None]` containing every requested key.** It requires a `PrefixedStore` (raises `TypeError` otherwise, exactly like `scoped_list_keys`), builds physical keys internally so no caller ever sees or supplies one, drops any returned key not carrying the view's prefix, and de-duplicates the request. **Missing keys and result order are where the two real hosts disagree, and this is not hypothetical — it was measured both ways.** Local Spin **omits** an absent key from the reply entirely; Akamai returns it as a `(key, None)` pair, exactly per the `wasi:keyvalue/batch` WIT spec. `scoped_get_many` absorbs both into an identical result, and its own reply is never assumed to preserve request order (a 2026-08-15 spike observed it coming back reordered) — it is **always** keyed by name, never zipped positionally. Getting this wrong is a silent wrong-value-on-the-wrong-key bug, not a crash, which is why `api/tests/test_kvbatch.py` includes a pinned mutation check (swap the keyed merge for a positional zip and confirm three tests fail).

**The bindings are SYNCHRONOUS, unlike Spin's own KV bindings, so `get_many` chunks cannot be overlapped.** `wasi_keyvalue_batch_0_2_0_draft2.get_many` and `wasi_keyvalue_store_0_2_0_draft2.open` are plain `def`, not `async def` — `asyncio.gather` over several `get_many` calls would simply run them one after another. `scoped_get_many` therefore chunks **sequentially** at `MAX_KEYS_PER_GET_MANY` (1000, measured — see below), and it is `async def` purely for call-site uniformity, never actually awaiting the raw call itself.

**`get_many` measured as one host round trip regardless of K, up to a cap — MEASURED ON AKAMAI, 2026-08-15/16.** `get_many` worked at K=100 through K=5,000 with flat latency (~10 ms at K=1,000) and failed at K=10,000 with `Error_Other('key-value error: internal server error')`. `MAX_KEYS_PER_GET_MANY = 1000` was chosen comfortably inside the working range, not at the observed ceiling — raise it only with a fresh measurement, the same rule `MAX_CONCURRENT_READS` carries.

**The same measurement answered the quota-accounting question this whole feature turned on: `get_many(K)` does NOT bill as K reads against Akamai's 1,000 RPS app-wide read cap.** A positive control (10 parallel requests × 200 single gathered reads = 2,000 reads/s) was throttled 9/10 with a clean `Error_Other('too many requests')`, establishing that exceeding the cap is observable. A test arm at 2.5× that load (10 parallel × `get_many(500)` = 5,000 keys/s) was throttled 0/10, with `returned=500` confirming genuinely distinct keys were fetched. **This retires `handle_click_totals`'s read-cap problem for every batched path** — at the modelled ceiling of ~6,100 keys for a 100-link × 200-click dashboard load, that collapses to a handful of chunked host calls rather than thousands of individual reads against the cap. It does **not** touch the separate `list_keys` enumeration cost documented below, which `get_many` cannot address at all.

**The `spin.toml` `key_value_stores` allowlist still applies to a wasi-opened bucket.** `get_many` needs a `wasi_keyvalue_store.Bucket`, a different WIT resource type from the `spin_key_value.Store` the rest of the app opens, so `api/app.py` opens a second handle (`wasi_store.open(kvprefix.PHYSICAL_STORE)`) — lazily, at most once per request, in a per-request closure, never at module level (the same reason `obs.Collector` is never module-level: `Handler.handle()` dispatches each request through `componentize_py_async_support.spawn`, so a shared handle would be shared across concurrently-dispatched requests). Opening `"users"` or `"links"` directly through this interface was refused during the 2026-08-15 spike; only `"default"` opened — so this opens no new security hole, and `kvprefix.py`'s prefixing remains the only namespace boundary, exactly as before.

**Writes are still never batched, and the reasoning is unchanged from `gather_reads`'s original rule — if anything it's stronger for `set_many`/`delete_many`, which don't exist in this codebase at all.** Akamai allows 1,000 KV reads/second per app but only 50 writes; a batch of K writes either still counts as K against the cap (in which case batching only hides the queueing) or it doesn't (in which case one handler could blow through the write budget the whole service shares) — and the WIT itself disclaims atomicity for batched writes, which would turn every "a record's existence is the only truth" interruption story in this app into a partially-applied batch with no way to know what landed. `backup.py`'s restore loop and every bulk handler's writes are deliberately sequential for this reason. **That asymmetry is the entire safety argument for every change in this section, batched or gathered.**

**`api/obs.py` now diverges from `redirect/linkgate/obs.go`'s op-type vocabulary by design.** `Collector.record` gained a fifth, keyword-defaulted `num_keys=1` parameter, and `_KV_OP_ORDER` gained `"get_many"`/`"get_many_error"` after `"get"` — but `redirect/linkgate/obs.go`'s `kvOpOrder` was **not** touched, because `redirect` never batches (it reads exactly one key per click) and a Go-side field would be dead code. Nothing pins the two vocabularies against each other the way `api/tests/test_kvprefix.py` pins `keys.go`'s prefixes and `CountShards` — this divergence is deliberate and permanent, not a gap to close later.

**`kv_ops` still counts host operations; `kv_keys` is the new number to watch instead of the traced `get` count.** A single `get_many` call covers K keys but is one host operation, so `kv_ops` alone would make a batched request look artificially cheap. `render_log_line` emits `kv_keys=<n>` immediately after `kv_bytes`, but **only when the key total differs from the op total** — so every non-batching request's line stays byte-identical to before this field existed. Once `handle_click_totals` batches, its traced `get` count reads `1` forever, so the monitoring number this file previously named for the cached-totals-blob's second trigger ("a traced `get` count above ~500") moves to `kv_keys`, at the same ~500 threshold — see `TASKS.md`'s cached-totals-blob Future-work entry, which this points back to.

**A memoized enumeration deliberately records NO operation, and that is what makes `kv_ops` mean what it says.** Since `docs/plans/derived-link-indexes.md`, `api/app.py` builds one memoized raw `get_keys` walk per request (`kvprefix.memoized_raw_list_keys`) so `handle_click_totals` pays for one whole-store walk rather than two. Until 2026-08-18 the cached hit was still recorded, so that endpoint traced as **`list_keys=2` while performing exactly one walk** — measured on the deployed build, where the two ops totalled 26,400 µs and the slower one alone was 26,396 µs, i.e. the second cost 4 µs. `scoped_list_keys` now skips recording when the raw callable reports `cache_hit`; the attribute is read with `getattr(..., False)`, so every non-memoized call site records exactly as before. **Do not "fix" this back by recording cache hits under their own op name** — `Collector.totals()` sums every op type into `kv_ops`, so any recorded hit inflates a count this file defines as counting host operations, and the memoization's effect is already visible as `list_keys=1` instead of 2.

**`backup.handle_export` deliberately still uses `gather_reads`, not `scoped_get_many` — a byte-safety decision, not an oversight.** The 2026-08-15/16 measurement above was run entirely over small blobs (~1.9 KB analytics shards, small link/user records); it never exercised anything near Akamai's documented 1 MB max value size, and `backup.handle_export` is the one call site whose store can legitimately contain values that large (a link record has no size cap of its own). A `MAX_KEYS_PER_GET_MANY = 1000` chunk there is bounded only by whatever the still-unmeasured value-size ceiling turns out to be — 1000 keys × up to 1 MB each is up to ~1 GB in a single host call and a single HTTP response, against Akamai's documented 10 MiB request/response limit. That is not a safe assumption to ship. Export already performs well on `gather_reads` (999 ops summing to 48,135 ms of KV time inside 957 ms of wall, 50.3× overlap — see the table below), so there is no latency pressure forcing an unmeasured change. Revisit only with a real byte-ceiling measurement taken at backup-realistic value sizes, and use a materially smaller constant than 1000 if it is ever adopted, justified by that measurement rather than borrowed from `MAX_KEYS_PER_GET_MANY`.

**`MAX_CONCURRENT_READS = 100` is empirical, not derived** — it is the largest fan-out actually measured working against the deployed app (the 64-shard analytics endpoint's 98 `get`s, whose effective parallelism was still *rising* rather than saturating). Raise it only with a fresh measurement; the read cap is app-wide, so one handler monopolising it degrades every concurrent request.

**The overlap is proven, not inferred.** `Server-Timing`'s `kv` is the **sum** of per-operation durations while `handler` is **wall time**, so `kv > handler` is arithmetically impossible under serial execution. Measured on `ac650c9-gatherreads`, 2026-08-07:

| path | ops | kv sum | wall | overlap |
|---|---|---|---|---|
| `GET /api/links` (14 links) | 19 | 433–1039 ms | 135–278 ms | 2.7–4.8× |
| `GET /api/links` (50 links) | 55 | 1579–6421 ms | 143–283 ms | 9.2–22.7× |
| `GET /api/admin/backup` | 999 | 48,135 ms | 957 ms | 50.3× |
| `GET /api/admin/consistency` | 69 | 1912 ms | 280 ms | 6.8× |

**Read the first two rows together: wall time stopped scaling with link count.** ~173 ms median at 50 links against ~178 ms at 14, while ops went 19 → 55. The pre-change baseline was 0.99× overlap and ~115 ms fixed plus ~23 ms *per link*, which projected ~1,265 ms at 50. **Effective parallelism rises with fan-out rather than saturating**, the same scaling the analytics endpoint showed going 50 → 98 `get`s — but that is an empirical property of this host, not a guarantee, so re-measure rather than extrapolate.

**`consistency.collect` fetches its two stores asymmetrically, on purpose.** The **links** store is fetched wholesale, *including* keys the loop classifies as `unrecognized` and discards — an allowlist there would have to restate the loop's branch conditions, and a condition that drifted out of it would silently hand the loop `None` and report a healthy key as `unreadable_value`. The **users** store gets an explicit two-shape allowlist (`_meta:usernames`, `session:*`) instead, because a `user:` record's value holds a PBKDF2 hash and no check reads one; fetching wholesale would pull every account hash in the store into the handler for zero benefit. **Do not "simplify" the users side to match the links side.** `test_handle_consistency_never_leaks_password_hash` would not catch it — that test inspects the report body, and a `collect` that reads every user value and discards it still passes. `test_collect_never_even_reads_a_user_record_value` is the guard that does, asserting `get()` is never called on a `user:` key at all.

**A key enumeration costs the whole physical store, and gathering cannot hide it — measured 2026-08-10 on `051cfa7-clicks`.** `scoped_list_keys` calls `raw_list_keys(store.raw)` and filters by prefix *afterwards*, so enumerating any namespace walks every key in the `default` store. Proof rather than inference: `consistency.collect` enumerates `users` (**3 keys**) and `links` (**~18 keys**) and each `list_keys` still cost **~62 ms**, essentially the same as the **941-key** analytics namespace's **69–162 ms**. Two consequences. First, a `list_keys` is **~4× a single `get`** (~24 ms) and is **un-overlappable** — `gather_reads` cannot issue a read until the key list exists — so `handle_click_totals`, whose 9 operations are one `open`, one session `exists`, one `list_keys` and six gathered `get`s, shows only **~1.2× effective parallelism** against `handle_list`'s 3.2–4.6×, with the enumeration alone **~44% of its wall time**. Second, and the one that scales: the store is **962 keys, 941 of them analytics**, analytics grows at up to 94 keys per link (64 shards + 30 slots), and **every dashboard load now pays a full-store walk.**

**The growth rate is now MEASURED, and it is linear: `list_keys` costs ~68.7 µs per physical key in the store, with essentially zero fixed cost (R² = 0.997).** Taken on the deployed `051cfa7-clicks` build over four store sizes spanning 10.4×, by seeding junk links (never clicked, so they add no analytics keys and delete cleanly) and re-tracing `click-totals`, whose `get` count is pinned by real click data and so does not move:

| physical keys | `list_keys` median | ratio to one `get` | `click-totals` wall |
|---|---|---|---|
| 962 | 64.2 ms | 2.59× | 193 ms |
| 1,962 | 144.9 ms | 5.45× | 274 ms |
| 4,962 | 315.4 ms | 12.33× | 450 ms |
| 9,962 | 689.9 ms | 26.23× | 852 ms |

Two controls make this a measurement rather than a correlation: **`get` never moved** (25.4–28.6 ms at every size), so the latency regime held for the whole run and no 3× swing is hiding in the curve; and after deleting all 9,000 seeded links the cost returned to **69.2 ms**, i.e. the effect rose 10× and came back down. **The warm baseline is 64 ms, not the ~99 ms recorded earlier that day** — the first traced sample after idle measures ~175 ms and the rest sit at 60–70 ms, so **discard the first sample after idle.**

**There is also a FIXED cost of about one KV round trip, which the fit above could not see — measured 2026-08-11.** Every store size in that table is ≥ 962 keys, where a ~20 ms fixed cost is 2–30% of the total and gets absorbed into noise as the ~0 intercept. Purging the deployed store from 968 physical keys to 57 put `list_keys` at **23.9 ms, not the ~1 ms the fit predicted** — a floor of **0.85× a single `get`**. So the real shape is **`list_keys ≈ one KV operation + ~68.7 µs per key`**, and **enumeration can never be made free, only proportional-to-nothing.** ~24 ms is the hard ceiling on any win from shrinking the store. The slope is confirmed unchanged by that measurement (refitting all six points regime-normalised: `lk/get = 2.53e-3 × keys + 0.31`, R² = 0.9989), so the growth projections below stand; only the low end was wrong. Do not trust the refit's intercept as the floor either — it still under-predicts the 57-key point by 45%, because least squares over a range dominated by large values fits the low end badly. **Use "about one KV operation" as the floor.**

**The practical statement: every key in the store costs ~69 µs on every dashboard load.** Akamai's 30-second handler limit is ~434,000 keys away and is not the concern; the usable limit is much closer — ~14,100 keys (about 150 links at the 94-keys-per-link ceiling) puts a full second of enumeration on every dashboard load, and ~1,000 links puts ~6.5 seconds there. The enumeration is 33% of `click-totals`' wall time at 962 keys and 81% at 9,962.

**A prefix-scoped enumeration does not exist — confirmed, so do not go looking for one.** `spin:key-value/key-value@3.0.0`'s `get-keys()` takes **no arguments at all**: no prefix, no cursor (`Store.get_keys(self)`; the Go SDK's `(*Store).GetKeys()` is the same). Any fix must **avoid** the enumeration, not narrow it. The "cache the physical key enumeration per request" Future-work entry collapses `consistency.collect`'s two walks into one but does nothing for `click-totals`, which makes only one.

**The `events:` ring-buffer write has been dropped — done 2026-08-18, see `docs/plans/drop-events-write.md`.** 30 of the up-to-94 keys per link were event slots for a feature that was a best-effort sample the dashboard never read; removing the write doubled the app-wide click ceiling (M2, see "Analytics" above) **and** cut analytics key growth by a modelled 32-48% depending on how busy a link is (busier links converge toward ⅓; quiet ones are closer to half, since both key types grow ~1-per-click until they saturate) — the two justifications turned out to be independent, and neither original write-up cited the other. **This is a slope change, not a shape change**: the enumeration remains linear and unbounded in link/click count, so the ~250 ms `list_keys` trigger for `GET /api/links` recorded in `docs/plans/derived-link-indexes.md` still stands, just reached later.

**Still unfixed: `GET /api/links` has no pagination.** Gathering converts ~23 ms/link into roughly a constant, but the handler still issues one read per link, so a large deployment fires one bounded burst per dashboard load. Pagination is the real answer if link counts ever get large — this bought a lot of headroom, not unlimited headroom.

## Security tradeoffs (accepted for v1)

These are deliberate, disclosed limitations, not oversights — each stems from a real architectural constraint (no outbound network from either component by default, no atomic KV operations) rather than an easy fix that was skipped.

- **No brute-force rate limiting on login or link passwords.** Neither `redirect` nor `api` has any `allowed_outbound_hosts` entries (confirmed: Spin denies all outbound HTTP by default when the key is omitted from a component's manifest), so neither component can reach an external atomic rate limiter (e.g. Redis `INCR`/`EXPIRE`). A KV-based attempt counter would be racy under concurrent requests anyway, since Spin's KV interface has no compare-and-swap. The only real mitigation in place is the PBKDF2 cost factor itself (100,000 iterations) slowing down each individual guess. If this becomes a real requirement, it needs a deliberate `allowed_outbound_hosts` expansion plus an external rate-limiting service — not a quiet KV-counter bolt-on.
- **Slug/link existence and password-protection status are enumerable.** A `404` (no such slug) vs. a `200` password prompt vs. a `302` redirect inherently tells a probing visitor whether a slug exists and whether it's password-protected. This is treated as an accepted characteristic of a public redirect service, not a vulnerability to fix — slugs aren't meant to be secret. Custom slugs are more guessable than random ones; pairing a custom slug with a link password is a sensible pattern worth surfacing in product UX, not something to enforce in code. **What stays indistinguishable, and what does not, since `docs/plans/redirect-read-failure-not-404.md`:** an absent slug, a disabled one, and one outside its `[start_at, end_at)` window all still produce a byte-identical `404` — that trio is deliberately never teased apart. Two disclosures are newly accepted in exchange for making the `/r/{slug}` status contract honest (see "The `/r/{slug}` status contract" above): a `500` reveals that a slug has a record which will not parse (accepted because it's not attacker-controllable — only `api` writes link records, and always valid JSON — and the same fact is already exposed on six authenticated `api` paths as `422 link_record_unreadable` and in the consistency report as `unreadable_value`); and a `503` reveals that the store is momentarily saturated (accepted because throughput and latency already tell a prober that, and 503 is the correct, standard answer to it — it is also emitted from a state of genuine ignorance about the link, so it cannot leak a fact the process never learned).
- **Security response headers are now set** (CSP, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, HSTS) by `redirect`, `api`, and `gui-pages` — see "Security response headers" above for exactly what each component sends. This is no longer a tradeoff entry at all: `gui-pages`'s CSP dropped `'unsafe-inline'` on 2026-07-31, and `redirect`'s password prompt followed on 2026-08-01. **There is no `'unsafe-inline'` anywhere in the application.** The prompt page turned out to be far cheaper than the deferral assumed — it needed no new file and no new route, since `/vendor/pico.min.css` and `/theme.css` were already routed and `theme.css` already had the `.form-error` class DESIGN.md required it to use.
- **Click counts are accurate below the app-wide ~50 clicks/second ceiling and lossy above it** (documented above; this was ~25 before 2026-08-18, when a recorded click cost two writes rather than one — see `docs/plans/drop-events-write.md`). The per-link contention that used to dominate — 25% loss at 9.4 clicks/s on one link — is fixed: the counter is sharded over **64** keys, which removes the per-link penalty entirely within the reachable envelope. What remains is Akamai's 50 KV writes/second app-wide cap at one write per recorded click, which sharding cannot touch and which binds across the whole service rather than per link. **The recent-events feature's disproportionate slot collisions were also fixed** (`EventSlot` used the same splitmix64 finalizer; cause was arithmetic aliasing, documented above) before the whole feature was retired 2026-08-18 — the write cap is accepted as the cost of a KV-only, no-network hot path.
- **Reversible link passwords are not supported** — they're hashed one-way, so a link's creator can never have the plaintext redisplayed. If "show me the password I set" UX is ever wanted, that requires a materially different storage model (encryption with real key management), not a tweak to the current hashing approach.

The former blocker is resolved: `docs/plans/kv-store-consolidation.md` moved both `redirect` and `api` onto Spin's single auto-provisioned `"default"` KV store (see "KV store: the single `default` store and the prefixing view" above), which is the one thing Akamai Functions requires that the three-named-store design couldn't provide. **That consolidation would have silently handed the KV explorer the `users` keys, and it did — deliberately, on the user's decision.** See the `kv-explorer` bullet under Architecture for the accepted-exposure record; nothing further to do here.

**Corrected against the real CLI on 2026-08-07 (`aka` plugin 0.7.4) — the previous version of this block did not work.** Three things: the subcommand is `spin aka app deploy`, not `spin aka deploy`; it takes **`--app-id`, not `--app-name`** (unlike `spin aka app status`, which takes `--app-name` and rejects `--app-id`'s positional form — the two subcommands genuinely differ); and it **requires `--no-confirm` in any non-interactive shell**, otherwise it fails with `No terminal available for interactive selection`. Both mistakes fail before anything uploads, so they are safe, just slow. `--build` replaces the separate `spin build`. Find the app id with `spin aka app list` then `spin aka app status --app-name <name>`.

**Every response from `redirect`, `api` and `gui-pages` carries `X-SS-Version`**, whose value is the `app_version` Spin variable (default `"unknown"`). Pass it at deploy time — `--variable app_version=<sha-or-label>` — and **`curl -sI https://<app>/` then answers "which build is live?" with no auth and no debug token.** This exists because of the readiness-check behaviour described next: without it, the only way to tell whether a deploy had propagated was to probe for a behavioural difference, which is circular when the behaviour you are testing *is* the change. It is attached in each component's `app.py`/`setSecurityHeaders` rather than in the shared `SECURITY_HEADERS` dicts, because it comes from a Spin variable and `api/responses.py`/`gui-pages/routing.py` deliberately import nothing from `spin_sdk`. The value is opaque and operator-chosen, so how much it reveals about the build is the operator's call.

**`spin aka app deploy`'s readiness check times out at 60 seconds and reports `Error: failed to wait for deployment to go live` — this is NOT necessarily a failed deploy.** Observed 2026-08-07: the deploy had in fact succeeded and went live shortly after the CLI gave up, with the new version already recorded in `spin aka app history`. **Do not redeploy on seeing this.** Check the actual state instead: `curl -sI https://<app>/` and compare `X-SS-Version` against what you passed as `app_version` — that is exactly what the header is for. `spin aka app history --app-name <name>` also shows a new version row, but a row is recorded before the build is actually serving, so the header is the authoritative signal. **A request made during the propagation window returns the OLD build and is actively misleading** — this produced a wrong conclusion once, when an early sample looked like a clean negative result for a change that was in fact working.

**Setting `log_debug_token` at deploy time is the only way to trace the deployed build**, and it cannot be added or changed later without another deploy. Omit the variable to restore the default `""`, which never matches. A deployed build whose token you do not know cannot be traced at all — which is why a "compare against a pre-change trace" verification has to take its baseline locally instead.

Three variables must be set on every deploy: `admin_bootstrap_password` (required secret, no default — seeds the first admin), `cookie_secure=true` (the local-dev `false` override must NOT ship — see "Commands" above), and `public_base_urls` pointing at the real deployed app URL (see "Multi-domain display" above for the silent-fallback-to-`localhost` trap if this is ever renamed or misconfigured on upgrade). Whether a `secret = true` variable like `admin_bootstrap_password` can be supplied through `--variable` is unconfirmed until a deploy is actually attempted.

**Upgrading an existing deployment is a backup → deploy → restore, never in-place**, because the KV store consolidation changed the physical key space (unprefixed `slug:<slug>` under three named stores → prefixed `links:slug:<slug>` under `default`) — a build from before the consolidation and one from after are reading disjoint physical keys. The backup file format needs no conversion for this: it already speaks logical store names and unprefixed keys, and `kvprefix`'s views map them onto the new physical keys transparently on the way in (`api/tests/test_store_isolation.py`'s pre-consolidation-fixture test pins exactly this). Concretely: `GET /api/admin/backup` on the old build, deploy the new build, `POST /api/admin/restore` with `{"confirm": "REPLACE", ...}` against it.
